# P7-T06 — prepare a single-VPS staging and production deployment path

Registry: [ROADMAP](../../ROADMAP.md#p7); current status and owner live there.

## Scope and acceptance

Prepare a coherent, repository-backed deployment path for the Python modular monolith on one VPS, with an isolated staging project on `dev` and production gated from `master`. This is configuration and documentation work only; it does not provision the VPS, create DNS/TLS certificates, read or write production data, or deploy services.

- Make the Python application topology authoritative: `/app` and `/admin` are routes/modules in the FastAPI application, not separate Node/web containers. Keep PostgreSQL separate with distinct production and staging volumes, env files, Compose project names, and loopback-only ingress ports. Define one production `app.runtime` owner separately from HTTP API; do not start runtime or provider effects in staging.
- Reconcile the existing root `docker-compose.yml` and `nginx/` files with the supported `docker/docker-compose*.yml` Python deployment, avoiding two competing stacks or a route that sends the public site to an unrelated `web:3000` service. Preserve a safe migration path and document any legacy config that cannot be retired without a host inventory.
- Keep external host Nginx as the TLS boundary. Provide a domain-placeholder vhost example for production and staging that proxies to the correct loopback API ports, redirects HTTP to HTTPS, preserves proxy headers, and can be completed later without hardcoding the user's future domain or certificates.
- Prepare GitHub Actions so `dev` builds/publishes a commit-pinned GHCR image and deploys only to staging; `master` uses a protected production environment/review gate. Configure Buildx/cache correctly and use the checked-in `docker/Dockerfile`. Keep the image reference immutable for each rollout.
- Run one explicit migration step before starting/replacing the API; API startup must not race a second workflow migrator. Include rollback/health/deployment notes and list the owner-only GitHub/VPS setup that remains.
- Keep the staging stack isolated and non-provider-facing. No production credentials, real domain, DNS changes, live TLS files, public database copy, destructive migration/retention action, or host command is in scope.

Acceptance evidence:

1. Compose/configuration statically verifies as two isolated deployments with non-overlapping loopback ports and separate volumes/env files; public app/admin requests reach the FastAPI service through host Nginx.
2. Workflow syntax and static checks show the `dev`/`master` split, immutable image tags, Buildx setup, environment-scoped secrets/production approval, and single migration ordering.
3. Nginx sample has placeholder-only hostnames/cert paths and a valid HTTP-to-HTTPS split; include the exact validation available in the workspace.
4. Documentation explains same-VPS limits, one runtime owner, staging isolation, the manual GitHub/VPS/domain/TLS actions, and the checks not run without Docker/host access.
5. No DB schema/data or application behavior changes. Required runtime VPS, DNS/TLS, deployment, backup/restore, and P4-T01/P7-T02/P6-T01 acceptance remain separate evidence.
