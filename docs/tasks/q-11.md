# Q-11

[Active queue](../../ROADMAP.md#questions).

how do clients (individuals and companies) enter the platform?

**Status: RESOLVED** (owner decision 2026-10-25, [PR #238](https://github.com/Starck43/social-media-ai/pull/238),
merge `beaa9ee`). This card is the record of the decision; the question is no
longer open.

## Decision (owner, 2026-10-25)

- **Individual** — self-service: `/app/register` creates the account and its own
  workspace, where the registrant is the workspace **owner**. Unchanged; it is
  what the code already does.
- **Company** — the owner invites people into an existing workspace. **An
  invited person can never become the workspace owner.** The owner is the one
  who created the workspace (or was promoted by an owner); the platform
  `SUPERUSER` role is unrelated and never reaches a workspace through an invite.
  The highest level an invite may carry is **admin** («Соадминистратор»), and
  only the workspace owner may hand it out — an admin cannot invite another
  admin.
- **Team size** — a new configuration knob, `MAX_WORKSPACE_MEMBERS`, default
  **2** (owner + one). It is a deployment-wide ceiling, not a per-tier number:
  per-tier `max_team_members` still applies whichever is tighter. Moving the
  limit into platform-admin settings tables is a later task, not this one.
- **Repeat invitations** — see the contract below: inviting again always mints
  a **new** link and leaves the old one live until it is used, expires or is
  revoked; nothing is re-sent, because the platform has no mail channel.

### What already holds (verified in source, not assumed)

| Property | Where it is enforced |
| --- | --- |
| Invites cannot carry `owner` | `member_roles.INVITABLE` excludes it; `issue()` raises for `owner`; `redeem_web` accepts only `admin/manager/analyst/viewer` |
| Only an owner may invite an admin | `invite_issue` → 403 unless `perms.is_owner`; `issue()` also checks the actor's role |
| Code is single-use, hashed, expiring | `code_hash`, atomic `used_count + 1` under `with_for_update` |
| Duplicate redemption is idempotent | existing active member → `already`, seat not consumed twice |
| Seat ceiling blocks the join cleanly | `no_seat` → HTTP 409 page, not a 500 |
| Revocation is immediate and workspace-bound | `revoke(tenant_id=…, invite_id=…)` sets `is_active=False` |

### Gaps this question resolves

1. `max_team_members` was only a tier number, so a starter workspace of one
   person could never invite anybody — the cheapest tier had no team path at
   all. The owner wants an explicit deployment ceiling of 2 for the pilot.
2. Repeat-invite behaviour was undocumented and different screens implied
   different answers (re-open the dialog, or press the button twice).

### Repeat-invitation contract (adopted industry practice)

Every "invite again" action is **new invite, old invite still live** — this
is the conventional team-invite behaviour (the first link may be sitting in
a chat the inviter cannot see, so silently killing it strands the person
who was about to use it). Unlike mail-based products, here the platform
sends nothing and has no delivery receipt, so the inviter keeps full control
through the list below instead of relying on a product that resends. The inviter decides what dies:

- the dialog lists every redeemable invite of the workspace with its role,
  expiry, remaining uses, and a **revoke** button;
- revoking is immediate: the code stops working mid-flow;
- a consumed invite disappears from the list (it is no longer redeemable);
- no mail is sent, so there is no "resend" to deduplicate — the inviter copies
  the link or scans the QR code, exactly as today.

## Follow-up: `MAX_WORKSPACE_MEMBERS` reddens two suites on `dev`

Reported by the P10-T19 lane, 2026-10-26, against `dev` = `53eef0d`
([announcement](https://github.com/Starck43/social-media-ai/pull/241#issuecomment-6409463751)).
**Not** a P10-T19 regression: both reproduce on a clean `origin/dev` in an
isolated worktree.

| Suite | Symptom | Cause |
| --- | --- | --- |
| `tests/security/test_vk_oauth.py` | 5 errors | fixture `owner_user` calls `add_web_member` on the **bootstrap tenant**; from the second member on, `check_member_limit` refuses (`default=2`, `.env` does not set it) |
| `tests/ai/test_plan_tiers.py` | 2 failed (`test_an_invite_to_a_full_workspace_reports_rather_than_raises`, `test_learn_and_reflect_stop_on_starter`) | same deployment ceiling interacting with invite/learning setup |

The suite that genuinely tests the ceiling
(`test_the_deployment_member_ceiling_caps_every_tier`) already pins it with
`monkeypatch.setattr(limits.settings, "MAX_WORKSPACE_MEMBERS", n)` — that pattern
is the precedent.

Two options, neither chosen yet:

1. **Pin the ceiling per test** where it is not under test (extend the
   `monkeypatch` pattern to the affected fixtures).
2. **Give test fixtures their own workspace** instead of the shared bootstrap
   tenant, so a deployment-wide ceiling stops being a shared-suite hazard.

Option 2 is the durable fix — the bootstrap tenant accumulates members across
runs and made this failure order-dependent. Whoever picks up the Q-11 follow-up
owns the choice; the P10-T19 lane does not edit this line.
