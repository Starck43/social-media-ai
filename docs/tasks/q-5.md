# Q-5

Parent: none (standalone question).

[Active queue](../../ROADMAP.md#questions).

Which registered VK application profile and credentials should deployment use
for the global search method family? The open decision is whether to use a
Standalone app profile or reconfigure the current web app. The API is the
required integration surface; internal vk.ru search endpoints are not evidence
of API capability.

## Historical evidence

The 2026-10-20 audit reported that `newsfeed.search`, `groups.search`,
`users.search`, `database.getCities` and `utils.resolveScreenName` returned
`1051 "Method is not available for this profile type"` with the service key
and personal user token for app `54798450` (web profile, localhost redirect).
It reported `wall.get`, `users.get` and `groups.getById` working. Treat these as
historical results; they were not reproduced by the current probe below.
Communities had been imported from an operator list. See the
[VK search audit](../audit/2026-10-20-vk-search-and-task-2027.md).

## Current observation — 2026-10-26

A bounded read-only probe using the configured service credential, API 5.199,
and an 8-second request timeout attempted `newsfeed.search(q=repair,count=1)`
and `wall.get(domain=apiclub,count=1)` against the official API host. Both
ended in `ConnectTimeout`; neither returned a response. This shows only that
these requests could not connect from the current environment. It neither
confirms nor refutes the historical 1051 permission error, and does not
establish availability from the deployment network or identify a suitable app
profile. No browser, token refresh, personal-token lookup or write was used;
no response body or credential was logged.

Q-5 remains open. Resolve it with a bounded API check from the intended
application profile and deployment network, recording method-level success or
the returned VK error. Until then, global search availability is unverified.
