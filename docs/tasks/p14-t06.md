## Goal

Deliver personalized batch campaigns (`{name}`, `{company}`) for 100+ contacts over email, Telegram bot, or MAX bot through the existing `P15-T05` outbox (`OutboxStore`), enforcing per-channel/per-purpose opt-in consent with explicit coverage warnings (`D15`), one-click unsubscribe without login (`D16`), and audited manual consent recording (`D17`).

## Plan

1. **Personalization & consent coverage (`app/services/crm/messaging.py`)**:
   - Render `{name}` and `{company}` placeholders single-pass without recursive template expansion or header injection.
   - Verify active `ContactConsent` per `(contact_id, channel, purpose)` (`marketing` or `greeting`). Contacts with a Bitrix24 identity but no granted `ContactConsent` are excluded from sending and surfaced in `skipped_no_consent` + `coverage_warning` (`D15`).
2. **Scheduling through `P15-T05` Outbox (`D10`) & batch status tracking**:
   - Create a parent `BusinessCommand` (`approval_policy="per_batch"`, integer `id` = `batch_id`) and schedule each consented contact's personalized message (with its contact-specific absolute unsubscribe link appended via `settings.PUBLIC_BASE_URL`, without promising `/stop` in the footer) through `OutboxStore` (`draft` + `schedule`).
   - **D10 / D14 approval semantics:** `POST /api/v1/integrations/bitrix/messaging/batch` requires `comms.outbox` `CONFIGURE` (`D14`), which is the operator's explicit campaign approval action. Per `D10`, approval state, `approved_hash`, `approval_expires_at`, and cancellation live in `OutboxStore` (`OutboxMessage` / `OutboxTarget` / `BusinessCommand`), so recording `state="approved"` on the scheduled outbox items and parent batch `BusinessCommand` reflects the operator's `OutboxStore.schedule` approval rather than silent auto-approval.
   - Separate `OutboxConflict` (e.g., `outbox_idempotency_mismatch`) into its own bucket (`skipped_conflict_count`, `skipped_conflict_contact_ids`) distinct from `skipped_no_route`.
   - Project live delivery tracking counts (`approved`, `claimed`, `sent`, `failed`, `uncertain_delivery`, `cancelled`, `skipped`) and per-target outcomes in `GET /api/v1/integrations/bitrix/messaging/status/{batch_id}` using SQL `WHERE` filters on `BusinessCommand`, `BusinessCommandTarget`, `OutboxMessage`, and `OutboxTarget`.
3. **One-click unsubscribe without login (`D16`)**:
   - Generate and verify HMAC-SHA256 signed tokens (`create_unsubscribe_token`, `verify_unsubscribe_token`) binding `(tenant_id, contact_id, channel, purpose, iat)`. Fail closed (`503 unsubscribe_secret_unconfigured`) when `settings.SECRET_KEY` is empty/whitespace; enforce maximum token age (`settings.UNSUBSCRIBE_TOKEN_TTL_SECONDS`, default 90 days) and reject expired or future-`iat` tokens (`422 invalid_unsubscribe_token`).
   - Public endpoints `GET /api/v1/integrations/bitrix/messaging/unsubscribe` and `POST /api/v1/integrations/bitrix/messaging/unsubscribe` (no bearer token/login required) record a `ContactConsent` withdrawal row (`withdrawn_at = now`) through `ContactManager.record_consent` (acquiring the same `SELECT ... FOR UPDATE` row lock on `Contact` as manual consent updates), cancel any unclaimed scheduled `OutboxMessage` / `OutboxTarget` (and `GreetingHistory`) rows for that contact/channel/purpose in the current calendar year (`effective_now.year`), and return a uniform `422 invalid_unsubscribe_token` error shape for both invalid tokens and deleted/merged contacts.
   - **Token reuse:** An unsubscribe link can be submitted repeatedly until its signed `iat` reaches the configured TTL. Each successful request appends a withdrawal; therefore a still-valid link can withdraw consent again after a later grant. Every new batch run issues fresh per-contact tokens. Replaying an existing batch idempotency key returns its original outbox items and tokenized bodies, even after the clock advances; it does not create another message.
   - Public success responses contain only `unsubscribed` and a confirmation message; tenant, contact, channel, purpose, timestamp, and cancellation details remain internal.
4. **Audited manual consent recording (`D17`)**:
   - `POST /api/v1/integrations/bitrix/contacts/{contact_id}/consents` requires `contact` `UPDATE`, validates `basis` and `source_evidence` with an explicit timezone-aware timestamp via `ContactManager.record_consent`, and writes an `ActionAuditEvent` (`action="crm.contact_update"`, `resource_kind="contact"`, `resource_id=contact_id`, `actor_kind="user"`, `actor_id=manager.id`).
