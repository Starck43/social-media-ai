## Behaviour verified in review

Pending credentials are bound to `<session>:<actor>:<tenant>`, so a workspace
switch invalidates the handle; confirm is single-use and re-checks owner and
`source.view` immediately before the provider call; the Yandex disk root cannot be
confirmed; connection and encrypted secret are written in one transaction;
disabling clears the secret; listing requires an active connection, `verified`
state for Mail.ru, matching platform/provider/auth method and catalog version;
WebDAV `href`s are decoded once, re-encoded and refused when ambiguous, external or
traversal-shaped; DTD/entity payloads are refused; only `PROPFIND` `Depth: 1`
reaches the fixed authority through the pinned TLS path; 401/403/429 map to
distinct messages; provider secrets never reach HTML (`no-store`, CSP,
`no-referrer`).

## Limitations and unrun checks

- UNRUN: live Yandex consent, live Mail.ru WebDAV, browser session on the owner's
  runtime, deployment, full suite. A verified folder is verification at setup
  time, not continuous health.
- The Yandex flow needs `PUBLIC_BASE_URL`, `YANDEX_DISK_CLIENT_ID` and
  `YANDEX_DISK_CLIENT_SECRET` from the owner's application registration
  ([checklist](../../platform/CONFIGURATION.md#registering-the-yandex-application)).
  Without them the button stays hidden and the manual token path remains.
- Mail.ru needs the user's own WebDAV app password; the provider reports no
  server-side paging, so a folder whose listing exceeds 256 KiB is refused with an
  actionable message rather than paged.
- Both pickers require one application process (documented), and a runtime restart
  drops a pending selection.
- Pre-existing and unrelated: `test_member_templates_have_no_hidden_budget_team_or_agent_fields`
  fails from `60155288`'s `mobile_nav` in the shared test double; handed to
  [P20-T17](../../tasks/p20-t17.md#handoff-from-the-p12-t19-audit-2026-11-20).
