## Outcome

An inbound thread message can now be answered from the unified interface with provenance that a
client cannot invent. The schedule and dispatch paths no longer have a stub guard; they require
verified evidence instead.

## Delivered

| Surface | Entry point | Bound by |
| --- | --- | --- |
| API | `POST /api/v1/communication/outbox/reply` (`ReplyIn`) | `comms.outbox.update`, idempotency key; extra fields rejected with 422 |
| Web | `POST /app/communications/reply` | CSRF + `comms.outbox.update` |
| CLI | `communications reply-preview`, `reply-draft [--dry-run]` | same scope as the API; no send/schedule command |
| Chat | `reply_preview` | read-only; cannot create or schedule |
| Outbox | `schedule`, claim, `verify_approval`, dispatch | verified evidence required; a marker alone is not a credential (D15) |

- Migration `0149_outbox_reply_evidence`, `down_revision = "0148"`; single head.
- Provenance (thread, sender account, identity, inbound id, `In-Reply-To`/`References`) is read
  from locked server records; the request body carries text only.
- `create_reply_draft` binds the evidence into the existing outbox content digest rather than next
  to it.
