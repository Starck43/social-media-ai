# P11-T28 — Workspace deletion is unreachable from the admin console

Registry: [ROADMAP](../../ROADMAP.md#p11). Parent: [P11](../phases/p11-structure.md) (navigation only).

## Scope, evidence and acceptance

**Evidence:** found while reproducing an owner report during the P11-T27 audit
(2026-10-31). The owner tried "Удалить выбранные" on
`/admin/tenant/list` and got `?error=403%3A+Console+operation+denied`, while
holding a superuser account.

Reproduced on a synthetic superuser (`role=superuser`, `is_superuser=True`,
`has_admin_access()=True`) against a synthetic workspace:

- login and `/admin/tenant/list` succeed (200);
- `DELETE /admin/tenant/delete?pks=<id>` returns **403**;
- `user.has_perm_for("Tenant", ActionType.DELETE)` is **False** for that
  superuser.

The cause is a gap in the access catalog, not a missing grant on the account.
`app/core/access_catalog.py` declares the `tenancy.workspace` resource
(model `tenant`) with three actions only:

```
['configure', 'update', 'view']
```

`DELETE` is not among them, so `User.has_perm_for` returns False for every
actor. It has no `is_superuser` bypass — it only asks whether the action is
declared on the resource. The write gate in `app/admin/session.py`
(`_scope_writes`, the `private` branch) therefore refuses the delete before it
reaches the database:

```python
if private and writes_row and not actor.has_perm_for(model.__name__, action):
    raise HTTPException(status_code=403, detail="Console operation denied")
```

**Blast radius is exactly one view.** Cross-checked every console view with
`can_delete=True` against the catalog: `User`, `CollectedItem`, `AgentScenario`,
`AgentTask`, `AIAnalytics`, `LLMProvider`, `LLMModel`, `UserCredential` all
declare `delete`. `Tenant` is the only view that renders the bulk-delete control
and can never execute it. Eleven resources lack `delete` in total, but the other
ten are either `can_delete=False` in the console or not console-exposed at all
(`platform_role`, `permission`, `model_type`, `workspace_role`, `llm_attempt`,
`llm_budget_day`, `llm_budget_reservation`, `llm_dispatch_receipt`,
`llm_outcome_event`, `action_audit`).

Not a P11-T27 regression: `app/core/access_catalog.py` is untouched by that
branch, and `origin/dev` declares the same three actions.

**Decision required before implementation.** Two shapes, and the owner must pick
one — they differ in what the platform's access model promises:

- **Narrow (recommended):** declare `delete` on `tenancy.workspace` and grant it
  to the `superuser` platform role only. Workspace deletion is irreversible and
  cascades across tenant-owned rows; a permission that exists but is held by one
  role is auditable and reviewable.
- **Broad:** give `User.has_perm_for` an explicit `is_superuser` bypass, mirroring
  the `is_bypass()` branch already present in `app/core/permissions.has_permission`.
  This closes the whole class of "declared action missing" gaps at once, but it
  also means any future catalog omission silently becomes a superuser right.

Do not implement either without the owner's choice. The narrow shape touches one
catalog entry and one role grant; the broad shape changes the meaning of
`has_perm_for` for every resource.

**Acceptance:**
- A superuser can delete a workspace from the console, and the delete is recorded
  in `action_audit_events` like every other console write.
- A non-superuser operator still cannot delete a workspace, and the refusal is a
  clean 403 rather than a 500.
- A focused regression test pins the chosen shape (superuser allowed, operator
  denied) and runs without a shared database where possible.
- If the narrow shape is chosen, the catalog change is covered by the existing
  access-catalog drift checks.
- Black/isort (line 120) clean; no schema migration.

**Out of scope:** the other ten resources without `delete`. They are not console
reachable today; if one becomes reachable, it gets its own decision.

**Rollback:** revert the scoped branch. No data migration, no runtime topology
change.
