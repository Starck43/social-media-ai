# P22-T27 — Connector settings live in the catalog, not in `Platform.params`

[Phase](../phases/p22-universal-tasks.md) · [Connector extension seam](../connectors/CONNECTOR_JOB_EXTENSION_SPEC.md) ·
[Connector configuration](../connectors/CONNECTOR_CONFIGURATION.md)

**Dependencies.** [P22-T02](../audit/p22/p22-02.md) (capabilities and grants),
[P22-T23](p22-t23.md) (the resource extension seam).

**Handoff.** [P22-T24](p22-t24.md) is being reworked by Codex and owns publication and execution;
this card must not touch the runtime map, admission or the worker. T23 owns the pin shape; this
card owns where a provider's static settings live and how a plan gates a connector. Coordinate the
`Capability` dataclass with T23 so both edit it once.

## Problem

A provider's settings are spread across four places, and the database copy is mostly dead.

**`Platform.params` is a JSON bag with no schema.** The VK row carries
`api_base_url`, `api_version`, `auth_type`, `oauth_base_url`, `oauth_token_url`, `redirect_uri`,
`category`, `data_boundary`, `capabilities`, `write_capabilities` and `rate_limit_per_hour`
(`app/services/social/platform_config.py:18-40`). An admin edits it by hand in SQLAdmin
(`app/admin/view_modules/sources.py:33`, field «Настройки API запросов»). A typo in
`api_base_url` is caught only by `require_config_param` at the first provider request.

**Five of those eleven keys are read by nothing.** Counting production readers:

| Key | Read by code |
| --- | --- |
| `api_base_url` | yes — `vk_client.py:384`, `tg_client.py:364`, `base.py:230`, `load_platform_config` |
| `api_version` | yes — `vk_client.py:385,484,946,1072,1158`, `adapters/vk.py:891` |
| `redirect_uri` | yes — `vk_oauth.py:189` |
| `oauth_base_url` | yes — `vk_oauth.py:203` |
| `oauth_token_url` | yes — `vk_oauth.py:216` |
| `auth_type` | **no** |
| `category` | **no** |
| `data_boundary` | **no** |
| `capabilities` | **no** |
| `write_capabilities` | **no** |
| `rate_limit_per_hour` | **no** — all nine occurrences are `AgentTask.rate_limit_per_hour` |

So `rate_limit_per_hour: 1000` in the VK row limits nothing. `capabilities:
["groups.getById", "wall.get", "newsfeed.search"]` gates nothing either.

**The same facts already exist in code, twice.** `app/integrations/catalog/__init__.py` holds
`Provider` with `id`, `platform`, `label`, `methods`, `defaults`, `capabilities`, `auth_protocol`,
`category`; `_provider_spec` in `app/services/social/connections.py:86-99` builds the connection
card from it. `platform_config._BOOTSTRAP` then holds a second copy of the API endpoints. Two
sources of truth for one fact, and the database is a third.

**Plan gating already works, and does not use `params`.** `app/services/collection/entitlements.py`
declares `CAPABILITIES = {"connector.vk.read", "connector.vk.search", "connector.telegram.read"}`,
`source_capabilities()` derives the required right from the sources and `intent_capabilities()`
from the plan (a `queries`/`discovery` collection needs `connector.vk.search`). An unknown adapter
produces an unregistered key and fails closed. `decide()`
(`app/services/tenancy/entitlements.py:40-94`) refuses `unknown_capability`, `unknown_plan`,
`plan_expired` and `not_granted` through `grants_capability`, which understands exact keys, `*`
and `connector.vk.*` wildcards.

**But nothing is gated today.** `PLAN_CATALOG = {name: PlanGrant(("*",)) for name in ("starter",
"pro", "business")}` (`app/services/tenancy/plan_catalog.py:16`) grants everything to every plan.
And the connections page never asks: `app/web/settings.py:271-340` builds every card from
`CONNECTIONS` with no plan check, so a starter workspace sees and can connect every connector.

## Deliverable

1. **Move provider constants into the catalog.** `api_base_url`, `api_version`, `oauth_base_url`,
   `oauth_token_url`, `auth_type`, `category`, `data_boundary` become fields or `defaults` entries
   on `Provider` (`app/integrations/catalog/__init__.py`), which already carries most of them.
   `load_platform_config` and `require_platform_param` read the catalog instead of the row.
2. **Keep deployment-dependent values out of both.** `redirect_uri` depends on the installation's
   domain, so it stays in `app/core/config.py` / `.env` beside the existing `VK_APP_ID`,
   `VK_SERVICE_KEY` and `TELEGRAM_*` keys. That is the one value that legitimately varies per
   deployment and cannot be a code constant.
3. **Delete the dead keys.** `capabilities`, `write_capabilities` and `rate_limit_per_hour` are
   removed from `params` rather than migrated: they gate nothing, and a limit that is not enforced
   is worse than an absent one. Provider API methods belong in the catalog's `capabilities` tuple;
   product rights belong in `PLAN_CATALOG`; per-task action limits stay on `AgentTask`.
4. **Drop `Platform.params`.** The `platforms` table stays as a directory — `id`, `platform_type`,
   `is_active` — because `sources.platform_id` is a foreign key to it (`source.py:50-51`,
   `ondelete="CASCADE"`). Removing the table would mean replacing that FK with a string key and
   migrating every source row; removing the column does not. State the migration and the rollback.
5. **Declare the product right on the capability.** Add a `capability` field to `Capability`
   (`app/integrations/catalog/task_capabilities.py:22-30`) so a provider states its own right
   (`connector.vk.read`) instead of `collection/entitlements.py` building the string as
   `f"connector.{platform}.{operation}"`. Coordinate this edit with T23, which adds a pin field to
   the same dataclass.
6. **Fill `PLAN_CATALOG` and gate the connections page.** Replace `("*",)` with real grants per
   plan, and filter `CONNECTIONS` in `app/web/settings.py` by the workspace's plan so an ungranted
   connector is shown as unavailable with a reason, not hidden and not silently connectable. The
   gate must refuse at connect time too, not only in the UI.

## Out of scope

- **The runtime map, admission, the worker and publication.** That is
  [P22-T24](p22-t24.md), which Codex is reworking. This card changes where settings live and how a
  plan gates a connector; it does not make an operation executable.
- **The pin shape.** [P22-T23](p22-t23.md). Only the `Capability` dataclass is shared.
- **Secrets.** Tokens and passwords stay in `WorkspaceConnectionSecret` and the existing encrypted
  stores. Nothing here moves a secret.
- **Per-connection configuration.** `portal_domain`, `calendar_id`, `file_policy` and
  `account_login` stay in `workspace_connections.config`, where they already are and where they
  belong: they are chosen by the user per account, not by the provider.

## Acceptance

`Platform.params` no longer exists. Every value the code reads comes from the catalog or from
deployment settings, and a test asserts that no production module reads `platform.params`.

The VK and Telegram clients, the OAuth flow and the connection cards work unchanged: a full
authorization and a collection run behave exactly as before the change.

`PLAN_CATALOG` grants differ per plan, and a workspace on a plan without `connector.vk.search` sees
the VK card as unavailable with a stated reason and cannot connect it — refused at the connect
route, not only hidden in the template. A workspace with the grant is unaffected.

The migration removes the column, is reversible, and states what happens to any row whose `params`
held a non-default value: the value is either reproduced from the catalog or reported as dropped,
never silently lost.
