## Scope and acceptance

Owner-requested audit of `notifications`, `bot_actions` and `agent_sessions`
for the business-assistant direction, plus a bounded refactor inside `app/models`.
No schema, migration, mapper fingerprint, API-route or admin changes. Manager
behavior intentionally changes: tenant-scoped ledger reads, stricter transitions,
SQL-side notification operations and deterministic list tie-breaking.
Owns: `app/models/{notification,bot_action,agent_session}.py`,
`app/models/notifications/notification.py`,
`app/models/managers/{notification,bot_action,agent_session}_manager.py`,
`tests/models/test_p10_t26_notification_action_managers.py`.

Accept:

- Root modules `app.models.notification|bot_action|agent_session` are pure
  re-exports with explicit `__all__`; no unused SQLAlchemy/type imports, no
  declarations, no manager construction. Pinned legacy symbols stay available.
- The three managers import their model from the canonical domain leaf, not
  from the root compatibility module.
- `NotificationManager` filters, counts, bulk-updates, deletes and aggregates in
  SQL through tenant-scoped querysets (no full-table loads, no per-row loops).
- `BotActionManager` raw `select` reads carry the tenant criterion; status
  transitions follow PENDING → APPROVED|REJECTED, APPROVED → EXECUTED|FAILED.
- Focused new tests pass and the focused regression set has no new failures
  against the same-environment baseline of the source revision.

## Findings (why)

- `notifications`: workspace-wide feed with a shared `is_read`; writers are job
  outcomes (`app/jobs/dispatcher.py`), collection failures
  (`app/services/monitoring/collector.py`) and `POST /api/v1/notifications/...`.
  Readers: web bell projection (`app/services/notifications/attention.py`),
  legacy API, SQLAdmin. Useful as an event inbox, but it has no recipient,
  per-user read state, severity, dedup key or retention policy → P4-T02.
  Manager loaded all rows into Python for recent/cleanup/stats and looped
  `update_by_id` for read-all.
- `bot_actions`: ledger of *proposed* external actions. Only the analyze handler
  creates rows (PENDING, `dry_run=True`); `action_send` is preview-only; admin can
  edit `status` only. Approve/reject/execute/fail methods have no production
  caller; `get_pending_actions`/`get_recent_actions` ignored the tenant guard;
  `mark_executed` accepted any prior status. Row is hard-wired to social
  (`source_id`, `agent_scenario_id` NOT NULL) → generalisation in P9-T08.
- `agent_sessions`: core conversation/state row, correctly scoped and used by
  runtime/web chat. Only the root module carried dead imports; behavior unchanged.
- Root compatibility modules (≈25) remain across `app/models`, and ≈100 manager
  imports still use them → P10-T28.
