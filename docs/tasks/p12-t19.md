# P12-T19 — Cloud disk connections: provider folder picker and Mail.ru Cloud WebDAV

Registry: [ROADMAP](../../ROADMAP.md); parent: [P12](../phases/p12-domain-workspace-expansion.md);
related: [P8-T34](p8-t34.md) (Yandex Disk pilot and Settings OAuth),
[P12-T12](p12-t12.md) (file-workspace policy/admission contracts).
Owner request and dialogue: local owner chat, 2026-11-20.

## Owner request

A regular user must be able to connect a personal Yandex Disk or Mail.ru Cloud
folder the way VK works today: one button, the provider's own login, no technical
input such as an OAuth token or a hand-typed folder path. The owner asked which
comparable fast path exists and requested this card; the plan below is what an
executor implements.

## Current behaviour (source `0baf8198`)

- VK: one «Войти через VK ID» button (`/app/vk/oauth` → `build_authorize_url`),
  because the VK application is registered in the deployment.
- Почта Mail.ru / Яндекс Почта: application password plus a provider
  `source_url` link labelled «Инструкция: как получить пароль приложения».
- Яндекс.Диск: the accepted [Settings OAuth increment](../audit/p8/p8-t34.md#settings-oauth-increment-audit--2026-11-20)
  offers «Подключить через Яндекс» **only when the deployment supplies
  `YANDEX_DISK_CLIENT_ID`/`YANDEX_DISK_CLIENT_SECRET`**, and still requires the
  user to type the folder path `/Документы` by hand. The manual-token fallback is
  unusable for a normal user and has no instruction link.
- Облако Mail.ru (`mailru_cloud`): descriptor only; no form, no transport.

## Scope and stages

Stage 1 — folder picker after Yandex consent (removes the typed path).

- The OAuth completion currently verifies the folder and writes the connection in
  one step (`app/services/file_workspace/yandex_oauth.py`). Split it: after a
  successful code exchange, hold the access token in a short-lived, single-purpose
  server-side record bound to tenant, actor, browser session and state, and render
  a folder picker instead of saving.
- The picker lists one bounded page with the existing `list_folder` +
  `ReadOnlyFolderPolicy` (root from the pending request only), allows parent
  navigation, and offers «Использовать эту папку». That action performs the same
  verification the current flow does and only then calls
  `create_yandex_connection(..., folder_verified=True)`.
- Reuse the existing CSRF/session binding and private response headers
  (`_yandex_browse_csrf`, `_private_file_response`). Pending tokens expire with the
  OAuth state TTL and are dropped on cancel, error and process restart (in-memory
  is acceptable only with the existing single-process limitation documented in
  [Configuration](../platform/CONFIGURATION.md)).
- Never save the disk root `/` from the picker; selecting a folder is the pilot
  boundary. No token is written before the user confirms.
- Keep the manual-token path working unchanged.

Stage 2 — the cheap clarity fixes for both cloud and mail forms.

- Add a `source_url` and an instruction link for the Yandex Disk manual-token form
  (the mail forms already render one) and replace the stale
  `YANDEX_DISK` descriptor text (`«пока не реализовано»`, `auth_protocol`
  «планируется») with the delivered state.
- Give the «папка не открылась» outcome an actionable message: the folder must
  exist, be spelled exactly, and be readable by the authorised account.

Stage 3 — Mail.ru Cloud over WebDAV (**owner-gated**, needs an explicit activation).

- New provider transport: fixed WebDAV authority, DNS-pinned verified TLS, bounded
  PROPFIND with depth 1, no writes, no redirects, no proxies, no compression,
  plus the same personal-owner, workspace, `source.view`, revocation and
  read-only-policy checks the Yandex reader applies.
- Form: account address and application password, with a provider instruction
  link, encrypted storage in the existing secret table and an explicit
  verification step that stores `unverified` until the check succeeds.
- Provider endpoint and app-password procedure must come from official Mail.ru
  documentation before implementation; do not infer hostnames from examples.

Out of scope: file downloads, native original opening, any write/delete or
mutation, per-folder restriction editing (P12-T15), exact-byte version authority,
public links, deployments, and registering or issuing provider application
credentials.

## Owner decisions still open

- **Registering a shared Yandex OAuth application in the deployment** (client ID,
  secret, callback) is what makes the one-button flow available to every user.
  That is an infrastructure/credentials decision, not part of this card; until it
  happens, Stage 1 improves the flow only for deployments that configured it.
- Stage 3 activation: Mail.ru Cloud is a new provider transport and needs the
  owner's go-ahead before implementation.

## Gates and acceptance

- Provider calls, storage/retention, failure and revocation behaviour and the
  current ACL must be specified and reviewed before any provider request is made
  from a route.
- Enforce tenant, personal owner, `source.view` and revocation on every operation;
  validate paths component-wise; deny unknown operations and mutations regardless
  of input.
- Focused tests must cover the assembled picker (consent → list → parent
  navigation → confirm), typed-path removal, expiry/cancel/replay, cross-session
  and cross-tenant state, provider failure, and — for Stage 3 — WebDAV refusals,
  traversal/encoding, sibling roots and revocation. Mock all providers.
- Honest status: a verified folder is verification at setup time, not continuous
  health; no broad-permission claim and no invented provider revision semantics.
- Record exact commits, documents actually read, commands, counts, unrun checks
  and cleanup in the card or PR.

## Risks

- The pending-token record is a new place where a provider secret lives in memory;
  keep it out of logs, out of templates and out of error text, and cap its lifetime.
- A picker widens the request surface of an authenticated route; keep POST-only
  actions, strict form parsing, bounded pages and `no-store`/CSP responses.
- Switching workspaces between consent and confirm must fail closed, as the
  current single-step flow does.
