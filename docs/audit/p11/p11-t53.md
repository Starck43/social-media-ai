# P11-T53 — accepted: a reset restores the capability-only catalogue rows

[Archived task card and execution evidence](../../archive/tasks/p11-t53.md).

Verdict: **ACCEPTED** — 2026-11-22 for revision `d49bab02` by an independent
reviewer (`cent.ai/hy4-flash:free`; Perch stopped at an approval gate, and the
free-pi executor cannot review itself). The reviewer raised three non-blocking
follow-ups; they are applied in `9316feae`, which touches a test, one comment and
the card only — no contract, no seed behaviour.

## What was wrong

`--reset` truncated `model_types` and the re-seed could not restore the two
capability-only identities migration `0156` inserts (`onec.data`,
`onec.command`): their `table_name` is a contract name, not a physical table, and
`register_model_types` skips every resource whose table is absent. The bootstrap
still reported `reference rows seeded`, and the next `pytest` session failed in
`tests/conftest.py` — a validated schema that could not run a single suite.

## What changed

- `scripts/setup_test_db.py` reads `CAPABILITY_RESOURCES` from the migration
  module itself (`_capability_registry`), so a re-seed restores exactly what
  history inserted instead of a copied list, and `_seed_capability_resources`
  re-creates the missing `model_types` rows with the migration's own values plus
  their permissions through `create_permissions_for_model`. It runs from
  `_seed_permissions` after `register_model_types`; `_seed_role_grants` then
  re-derives the workspace grants from the catalog.
- The migration file, the migration hook and `app/core/access_catalog.py` are
  unmodified. The new code is `select`/`insert` only: no DDL, no delete, and a
  repeated seed converges.

## Checks at `9316feae`

- Schema from migrations (`p11t53_migr`, head `0162`), `--reset` then seed:
  `model_types` holds both identities, `permissions` holds exactly the four
  declared actions, `workspace_role_permission` holds 11 capability grants —
  matching `0156`'s `CAPABILITY_GRANTS` (owner 4, admin 4, manager 2, analyst 1).
  Permission names read `Can view onec.data`, so the seed created them.
- The same reset on a metadata-built schema (`p11t53_meta2`) leaves it usable.
- `DB_TEST_SCHEMA=<schema> pytest -q tests/planner/test_p22_t07_work_task_api_db.py`:
  3 passed on both schemas — the conftest reference check accepts them.
- `pytest -q tests/infra`: 79 passed, 3 failed; the same three
  `BootstrapOrderTests` doubles fail on unmodified `dev`.
- New checks: the registry equals the migration's identities and stays a subset of
  the catalog resources; a live catalog test deletes the rows the way the
  migration's downgrade does, re-seeds, and asserts both identities and
  `onec.data`'s `view`/`export` permissions return (rolled back); and a wiring test
  fails if `_seed_permissions` stops calling the restore.

## Recorded limitations

1. Permission actions come from the live catalog (`resource_for`), not from
   `0156`'s `_actions` tuple. A resource added to `0156` with a `model_name` the
   catalog does not know would get its `model_types` row but no permissions.
2. The three `BootstrapOrderTests` failures remain pre-existing debt (their
   `Engine` double has no `begin`, so `_apply_guards` is untested there).
3. The end-to-end `--reset` + conftest path is verified by hand here; the new
   tests cover its parts, not a full reset cycle.

## Disposition

branch `fix/p11-t53-reset-capability-rows` deleted after the merge.
