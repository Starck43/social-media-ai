# P11-T52 — Test-schema bootstrap cannot seed a migrated schema

Registry: [ROADMAP](../../ROADMAP.md); parent: [P11](../../docs/phases/p11-structure.md)
(accepted phase, this is a registered follow-up). No prerequisites.

## Goal

`python -m scripts.setup_test_db` must seed any schema it accepts, and must
refuse a schema it cannot seed with a message naming the prerequisite instead of
failing halfway through reference rows.

## Why this exists

Reproduced 2026-11-22 on `dev` `782b12bb`. A schema created by the migrations
(the shape of `public` and of every schema at head `0162`) is accepted by the
bootstrap preflight, then dies while seeding:

```
async def _seed_bootstrap_tenant():
    await tenants.get_or_create_owner(settings.DEFAULT_TENANT_SLUG)      # scripts/setup_test_db.py:429-434

create(... plan="business", daily_cost_limit=5.0, ...)                    # app/models/managers/tenant_manager.py:197-215
# INSERT ... plan_holder_user_id = NULL
sqlalchemy.exc.IntegrityError: NotNullViolationError: null value in column
"plan_holder_user_id" of relation "tenants" violates not-null constraint
```

Two facts make this a defect rather than a bad input:

1. `tenants.plan_holder_user_id` is `NOT NULL` in any migrated schema
   (`migrations/versions/0155_p2t17_service_plan_finalize.py:42`) but nullable in
   the model metadata, and `tenants.get_or_create_owner`
   (`app/models/managers/tenant_manager.py:197-215`) never sets it. The metadata
   path is not a faithful image of the migrated contract:
   `Base.metadata.create_all` produces a *nullable* column, so the create_all
   path seeds happily while a migrated schema cannot — the two test schemas
   differ in a way no suite checks.
2. The preflight cannot catch it. `check_existing_schema`
   (`scripts/setup_test_db.py:287-337`) compares tables, column presence and
   UNIQUE constraints only (`_missing_columns`, `:195-212`; no `is_nullable`
   read anywhere in the file), so a migrated schema passes validation and only
   fails at the seed, after the guard objects are already applied.

Consequence: no isolated P22 test schema could be seeded without a manual
`alter table <schema>.tenants alter column plan_holder_user_id drop not null`
during P22-T04/T06/T07. That manual step is invisible to the next agent and the
schema stays silently different from `public`.

## Scope

- Seed the bootstrap tenant with its plan holder, or take the holder from the
  canonical service-plan path, so `get_or_create_owner` never violates the
  migrated constraint.
- Make the preflight compare column nullability against the metadata and refuse
  a schema whose contract disagrees, naming the column and the migration that
  owns it. Refusal must stay read-only: no automatic `alter`.
- Align `app/models/tenancy/tenant.py:135-140` nullability with the migrated contract,
  so `create_all` and `upgrade head` produce the same column. Keep the downgrade
  in `0155` as the migration's own business.
- Verify on a throwaway schema both ways: created from metadata, and created by
  `alembic upgrade head`; then run one P22 DB suite on each.

## Out of scope

- Changing `public` or the shared `test_schema` beyond the normal bootstrap seed.
- Employee/backfill rules of P2-T17; this card only fixes the test bootstrap.

## Evidence (reproduction)

```
psql -c 'create schema p11t52_probe2'
DB_SCHEMA=p11t52_probe2 alembic upgrade head            # psycopg2 sync bridge; 0162 applied
DB_SCHEMA=public DB_TEST_SCHEMA=p11t52_probe2 python -m scripts.setup_test_db
  -> schema created from the models ... (preflight accepted the migrated schema)
  -> NotNullViolationError: null value in column "plan_holder_user_id"
```

The same command succeeded on a schema created by `create_all`
(`DB_TEST_SCHEMA=p11t52_probe`), where the column is nullable — the drift
described above.

## Verification at implementation

```bash
DB_TEST_SCHEMA=<scratch> python -m scripts.setup_test_db      # metadata path
DB_SCHEMA=<scratch> python -m scripts.setup_test_db           # migrated path
DB_TEST_SCHEMA=<scratch> pytest -q tests/planner/test_p22_t07_work_task_api_db.py
python -m scripts.setup_test_db --check
```

Record both schema inventories, the seeded bootstrap tenant's holder id, and the
preflight refusal message for a deliberately mismatched nullability.

## Risks and rollback

A stricter preflight can refuse schemas that used to pass, so it must print the
owning migration and stop read-only; rollback is reverting the preflight alone,
which leaves the seed fix in place. Nothing here writes `public`.
