## Scope and acceptance

Today a `Notification` is a workspace event with one shared `is_read`
(docs/NOTIFICATIONS.md, ADMIN `mark-read`). For a business assistant the inbox
must answer "who must see/act on this, did they, and is it still relevant".

Proposal to decide before implementation (owner choice required):

- Keep `notifications` as the immutable event row; add `notification_receipts`
  (`notification_id`, `tenant_user_id`, `read_at`, `dismissed_at`, `snoozed_until`)
  instead of the shared flag. Migrate `is_read=true` as workspace-level history only.
- Add `severity` (info/warning/action_required), `dedup_key` + unique per
  tenant/open window (collapse repeated job/collection errors), optional
  `expires_at`, and typed entity attribution (`related_entity_type` enum).
- Fix typing: `related_entity_*` are nullable but annotated non-null.
- Retention: purge/aggregate per P6 contract instead of ad-hoc cleanup endpoint.
- Recipient resolution reuses `NotificationPreference` and permissions; delivery
  to messengers stays the explicit path in docs/NOTIFICATIONS.md.

Accept: approved schema + Alembic migration validated on test_schema, web bell
and admin use per-user receipts, quiet hours/preferences honored, tenancy and
permission tests. Depends: P10-T26; coordinates with P6-T02 (retention).
