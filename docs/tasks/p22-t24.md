# P22-T24 — Make the canonical task path executable, or retire it

[Phase](../phases/p22-universal-tasks.md) · [Target architecture](../product/UNIVERSAL_TASKS.md) ·
[Run admission](../audit/p22/p22-t04.md)

**Dependencies.** [P22-T03](../audit/p22/p22-03.md) (plans and bindings),
[P22-T04](../audit/p22/p22-04.md) (admission, scheduler, worker),
[P22-T07](../audit/p22/p22-07.md) (unified interface).

**Blocks.** Every card that assumes a canonical task can run: [P22-T08](p22-t08.md),
[P22-T22](p22-t22.md), [P22-T23](p22-t23.md), [P22-T10](p22-t10.md).

## Problem

The canonical P22 task path cannot execute a social collection, a mail read that saves anything, or
any LLM step. It is not a gap in one operation: the plan contract and the runtime disagree about
which operations exist, and the admission gate refuses the rest.

**The plan contract declares seven operations** (`app/services/execution_plan_contracts.py:94-102`):

```
social.collect, social.cached, social.analyze, social.digest,
mail.read_headers, mail.group_by_sender, messages.store_groups
```

**The runtime implements two** (`app/services/task_run_operations.py:173`):

```python
OPERATIONS = MappingProxyType({"mail.read_headers": read_headers, "mail.group_by_sender": group_by_sender})
```

**Admission refuses anything outside the runtime map.** `validate_runtime_plan`
(`app/services/task_run_worker.py:56-62`) raises `unsupported_execution_operation` for any step not
in `task_run_operations.OPERATIONS`, and `validate_admissible_plan`
(`app/services/task_run_admission.py:124-129`) calls it on every admission. So:

- a plan with `social.collect` or `social.analyze` is **refused at admission**;
- a plan with `messages.store_groups` is **refused at admission**, which is why the mail route
  cannot save its result;
- `task_trigger_service.configure` runs the same validation, so such a plan **cannot be armed**
  either.

The repository's own tests assert this. `tests/jobs/test_p22_t04_run_admission_db.py:536-541`
publishes `mail_plan(...)` — a plan whose third step is `messages.store_groups` — and expects
`ExecutionPlanError: unsupported_execution_operation`. The mail fixture is used as the canonical
example of a plan that is *refused*.

**LLM steps are refused separately.** `validate_admissible_plan` raises `payer_unavailable` for any
step whose `Operation.llm` is true (`task_run_admission.py:127-128`). That covers `social.analyze`
and `social.digest`. So even if the runtime map were completed, an analysis step would still be
refused until a payer path exists.

**A scenario is validated but never executed.** `Step.scenario_id` is checked for existence in
`_active_scenarios` (`app/services/task_execution_plans.py:91`), and `check_graph` enforces
`bool(operation.llm) == (step.scenario_id is not None)`
(`execution_plan_contracts.py:196`). But `_perform_step` calls
`OPERATIONS[step.operation](session, context, step, inputs, resources)`
(`task_run_worker.py:159`) — the step's `scenario_id` is never passed to anything that could call a
model. There is no LLM operation in the worker at all.

**The path that does work is the legacy one.** `handle_collect` and `handle_analyze`
(`app/jobs/handlers.py:945`, `:1510`) are registered in `HANDLERS` under `collect` and `analyze`
(`:2175`, `:2178`), dispatched by `AgentTask.job_type`, and `handle_analyze` genuinely resolves a
scenario (`task.agent_scenario` or `payload["scenario_id"]`, `:1681-1684`) and runs the model
through `app/services/task_pipeline.py:573`. That is the collection and analysis the product
actually performs today.

So the codebase has two parallel stacks: a legacy `AgentTask` → `Job` → `HANDLERS` path that runs
collection and analysis, and a canonical `Task` → `TaskPlanRevision` → `TaskRun` → `task.execute`
path that validates, versions, authorizes and then refuses almost everything. `execution_plan_service.publish`
has no caller in `app/` either (recorded in [P22-T08](p22-t08.md)), so nothing can even create the
revision the canonical path needs.

## Why this matters for `Source`

`Source` looks like a lame VK/Telegram table because **the only path that executes is the one built
around it**. `Source.params` carries exactly `mode`, `token_owner` and `telegram_authorization`
(written in `app/web/sources.py:393-395`, `:485-499` and
`app/services/social/telegram_source_bindings.py:252-254`) — three keys, not a sprawl. Reshaping
`Source` while the canonical path cannot run would move the working stack and leave the broken one
broken.

## Deliverable

One decision, made explicitly and recorded, then executed.

**Option A — complete the canonical path.** Implement the missing runtime operations
(`social.collect`, `social.cached`, `social.analyze`, `social.digest`, `messages.store_groups`), add
the payer path that `validate_admissible_plan` currently refuses, pass `scenario_id` into an LLM
operation, and give `execution_plan_service.publish` a caller. Then migrate the legacy handlers'
behaviour onto it and retire `HANDLERS["collect"]` / `HANDLERS["analyze"]` behind a compatibility
window.

**Option B — retire the canonical execution path.** Keep `Task`, `TaskPlanRevision` and `TaskRun`
as the identity, versioning and evidence layer, and route execution back through the legacy
`AgentTask` → `Job` → `HANDLERS` path, which already runs collection and analysis. Delete the
duplicate `OPERATIONS` map and the admission gate that refuses what the contract allows.

**Recommendation: A, scoped.** The canonical path is where authorization, versioning, pinning and
run receipts already live, and it is what every P22 card is written against. Retiring it would
throw away the security work. But A must be sequenced: the runtime operations first, because
without them nothing else in P22 can be demonstrated end to end.

Whichever option is chosen, record it in this card and in the phase document before implementing,
and state what happens to the other path.

## Out of scope

- **Reshaping `Source`, `Platform` or `AgentTask`.** That is [P22-T22](p22-t22.md) and
  [P22-T23](p22-t23.md), and both are blocked on this card producing a runnable path.
- **New resource kinds.** `DISK_FOLDER`, `PORTAL` and `PAIRED_ROOT` still have no operation; adding
  them is separate work that depends on this decision.
- **Write actions.** `agent/toolset/actions.py` is a separate consent and idempotency contract.

## Acceptance

A canonical task with a published plan runs end to end on a real route: admit, execute every step,
store a result, and show a receipt. For a social collection that means `social.collect` produces
rows and `social.analyze` runs the selected scenario through a model with a recorded payer. For
mail it means `messages.store_groups` persists the groups instead of being refused.

The two operation maps agree, or there is only one. A test asserts that every operation the plan
contract declares has a runtime implementation, so this divergence cannot recur silently.

A plan that the contract accepts can be armed by `task_trigger_service.configure`, or the contract
stops accepting it. No operation is advertised in `OPERATIONS` that admission refuses.

If Option B is chosen instead: a canonical task's run delegates to the legacy handler, the duplicate
map is gone, and the existing collection and analysis suites pass unchanged.
