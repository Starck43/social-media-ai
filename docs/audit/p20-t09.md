Candidate: PR [#457](https://github.com/Starck43/social-media-ai/pull/457), branch

**Verdict: NOT ACCEPTED.** Five blocking findings. The task returns to

The classification core is genuinely good work — metadata-only, deterministic

## Blocking findings

### B1 — A user's classification correction is lost on every restart and never reaches a second worker

`app/services/communications/triage.py:94`

```python
_USER_TRIAGE_DECISIONS: dict[tuple[int, int, int], dict[str, Any]] = {}
```

`record_user_triage_override` writes into this module-level dict (`:667`) and
`triage_thread_record` reads it back (`:936`) to override the classification.
Nothing persists it: no table, no cache, no session storage.

Measured on the candidate branch:

```
before override: can_wait   deterministic_baseline
after override : needs_reply user_override
after restart  : can_wait   deterministic_baseline
```

This is a task requirement, not a nicety — the card says *"corrections by the
user are recorded as our decision, not as a model fact"* and the executor's own
test asserts `after.category == TRIAGE_NEEDS_REPLY`. The user corrects a thread,
and after the next deploy or even a second API worker the inbox silently
classifies it the old way. Worse, the memory is unbounded and never expired, so
the "fix" is a leak.

Also note the override key is on `user_id`, so in a shared mailbox a colleague
never sees the correction — acceptable if documented, but it is not documented.

**Fix:** persist the decision with a real row (its own DDL is authorised by
`bb702f45`'s withdrawal only for the *artifact* table — this is a different,
small table and needs its own allocation, which the auditor grants on a written
column list). If the owner prefers no new table for P3, the honest fallback is to
drop the feature from this task rather than ship a correction that evaporates.
Under no circumstances keep an unbounded process-global dict.

### B2 — The chat «Ждут решения» panel fabricates the thread metadata it classifies

`app/web/chat_workspace.py:638-672`

```python
triage_pred = classify_thread_baseline(
    subject=ctx_title,
    unread_count=1,      # hard-coded
    message_count=1,     # hard-coded
    last_direction="inbound",  # hard-coded
)
```

Every communication context is classified as if it had exactly one unread
inbound message, whatever the truth is. The baseline's rule 5 is *"unread > 0
and inbound and non-empty subject → Нужен ответ"*, so the panel labels almost
everything «Нужен ответ»:

```
Счёт на оплату за март          -> Нужен ответ
Пришлите КП?                    -> Нужен ответ
Дедлайн завтра, нужен ответ!    -> Нужен ответ
Да                              -> Нужен ответ
Рассылка новостей отрасли       -> Подождёт
```

The resolved context the panel receives is a **`UnifiedMessage`**, not a thread
(`app/services/knowledge/workspace.py:_resolve_unified_message_context`), so its
`id` is a message id, not a thread id, and `thread_id` is a separate key the panel
never reads. Consequences:

- the card is attributed to the wrong object;
- `authoritative_ref` falls back to `communication:<message_id>` because the
  context has no `ref` key at all;
- `authoritative_url` falls back to `?thread_id=<message_id>`, a link that opens
  the wrong thread or nothing.

**Fix:** resolve the actual thread (`ctx["thread_id"]`) and call `triage_thread`,
reusing the same tenant/permission path as the Web inbox. Never pass hard-coded
counts into a classifier. If the thread cannot be resolved, emit no card — a
fabricated classification on «Ждут решения» is worse than an empty tab.

### B3 — Both new forms always submit an empty CSRF token, so every user action 403s

`app/web/templates/web/communications.html:147` and `:176`

```jinja
<input type="hidden" name="_csrf" value="{{ csrf_token | default('') }}">
```

The render context provides the token as **`csrf`** (`app/web/deps.py:285`), and
every other template in the project uses `{{ csrf }}`. `csrf_token` is undefined
here, so `default('')` renders an empty string:

```
rendered hidden value -> ''
```

Both the override form (`POST /app/communications/threads/{id}/triage`) and the
reply-draft form (`POST /app/communications/reply`) call `ensure_csrf` and reject
the empty token with 403. The handler logic is fine — it is the template that is
broken — and the executor's test mocks `ensure_csrf` away, so this was never
visible.

**Fix:** use `{{ csrf }}` in both places, and add a page-render test
(`communications_page`) that asserts the rendered HTML carries the real token.
`communications_page` is currently untested entirely — its triage block is
wrapped in `except Exception: pass`, so a broken inbox still renders "green".

### B4 — A triage failure tears down the whole «Сегодня» section and drops every thread

`app/services/workspace/today.py:875-883`

```python
try:
    triaged = triage_thread_record(...)
except InboxItemUnavailable:
    continue
```

`triage_thread_record` reads decrypted subject and contact name and builds
proposals. Any other exception — a rotated encryption key, a malformed ciphertext,
a bug in `sanitize_untrusted_text` — is not caught by this `try`, and there is no
outer guard around the loop. Measured:

```
UNCAUGHT RuntimeError: cipher: key rotated =>
  propagates out of build_awaiting_reply_section
```

The preceding provider call *is* guarded (`except Exception` → section
`unavailable`), so the section is designed to degrade, but this new loop defeats
that: one corrupt thread takes down the entire Today page for the user.

**Fix:** per-item containment — log and `continue` on any exception while
triaging one thread, keeping the existing `InboxItemUnavailable` skip. The
section must never be worse than it was before this task added fields to it.

### B5 — The new API routes are not in the generated reference and the check fails

```
$ python scripts/reference/generate.py --check
Stale reference tables: docs/generated/api-routes.md
```

Five routes were added (`/triage`, `/triage/evaluation`,
`/threads/{id}/triage`, `.../override`, `.../reply-draft`). The executor listed
"regeneration" as *deferred*; the project treats the reference as a required
artifact, not an optional one — P19-T04's audit recorded `generate.py --check`
PASS as part of its evidence. **Fix:** regenerate and commit
`docs/generated/api-routes.md`.

## Non-blocking findings

- **The suggested reply is boilerplate.** `build_thread_proposals` emits a fixed
  `"Спасибо за сообщение по теме «…». Мы изучили ваш запрос…"` for every needs-reply
  and uncertain thread. The card promises a *proposed reply draft*; a template
  string is not a proposal worth reviewing. Acceptable only if the card is
  amended to say "starter draft", not "agent-suggested reply". The reviewer
  decides; it does not block P3.
- **Rule 5 overwhelms the corpus.** `unread_count > 0 and inbound and subject` →
  `needs_reply` makes the baseline label nearly every unread thread «Нужен ответ»,
  which is what the corpus's own false-negative fixture (`fx-10`) and B2 both
  probe. Consider requiring a question/action marker before `needs_reply`, with
  plain unread threads going to `uncertain`.
- **`connection_status="active"` is hard-coded** in `ThreadTriageResult`
  (`triage.py:1009`) regardless of the actual connection row.
- **The web triage block swallows exceptions** (`except Exception: pass` twice in
  `communications_page`) — combined with B3 this hides real breakage.

3. B3 `{{ csrf }}` in both forms plus a page-render test.

5. B5 regenerated `docs/generated/api-routes.md`.

Focused re-checks expected: the executor's own 10 + 22 tests, plus a new
