# P12-T19 — Cloud disk connections: provider folder picker and Mail.ru Cloud WebDAV

Registry: [ROADMAP](../../ROADMAP.md); parent: [P12](../phases/p12-domain-workspace-expansion.md);
related: [P8-T34](p8-t34.md) (Yandex Disk pilot and Settings OAuth),
[P12-T12](p12-t12.md) (file-workspace policy/admission contracts).
Owner request and dialogue: local owner chat, 2026-11-20.

## Owner request

A regular user must be able to connect a personal Yandex Disk or Mail.ru Cloud
folder the way VK works today: one button, the provider's own login, no technical
input such as an OAuth token or a hand-typed folder path. The owner asked which
comparable fast path exists and requested this card; the plan below is what an
executor implements.

## Current behaviour (source `0baf8198`)

- VK: one «Войти через VK ID» button (`/app/vk/oauth` → `build_authorize_url`),
  because the VK application is registered in the deployment.
- Почта Mail.ru / Яндекс Почта: application password plus a provider
  `source_url` link labelled «Инструкция: как получить пароль приложения».
- Яндекс.Диск: the accepted [Settings OAuth increment](../audit/p8/p8-t34.md#settings-oauth-increment-audit--2026-11-20)
  offers «Подключить через Яндекс» **only when the deployment supplies
  `YANDEX_DISK_CLIENT_ID`/`YANDEX_DISK_CLIENT_SECRET`**, and still requires the
  user to type the folder path `/Документы` by hand. The manual-token fallback is
  unusable for a normal user and has no instruction link.
- Облако Mail.ru (`mailru_cloud`): descriptor only; no form, no transport.

## Scope and stages

Stage 1 — folder picker after Yandex consent (removes the typed path).

- The OAuth completion currently verifies the folder and writes the connection in
  one step (`app/services/file_workspace/yandex_oauth.py`). Split it: after a
  successful code exchange, hold the access token in a short-lived, single-purpose
  server-side record bound to tenant, actor, browser session and state, and render
  a folder picker instead of saving.
- The picker lists one bounded page with the existing `list_folder` +
  `ReadOnlyFolderPolicy` (root from the pending request only), allows parent
  navigation, and offers «Использовать эту папку». That action performs the same
  verification the current flow does and only then calls
  `create_yandex_connection(..., folder_verified=True)`.
- Reuse the existing CSRF/session binding and private response headers
  (`_yandex_browse_csrf`, `_private_file_response`). Pending tokens expire with the
  OAuth state TTL and are dropped on cancel, error and process restart (in-memory
  is acceptable only with the existing single-process limitation documented in
  [Configuration](../platform/CONFIGURATION.md)).
- Never save the disk root `/` from the picker; selecting a folder is the pilot
  boundary. No token is written before the user confirms.
- Keep the manual-token path working unchanged.

Stage 2 — the cheap clarity fixes for both cloud and mail forms.

- Add a `source_url` and an instruction link for the Yandex Disk manual-token form
  (the mail forms already render one) and replace the stale
  `YANDEX_DISK` descriptor text (`«пока не реализовано»`, `auth_protocol`
  «планируется») with the delivered state.
- Give the «папка не открылась» outcome an actionable message: the folder must
  exist, be spelled exactly, and be readable by the authorised account.

Stage 3 — Mail.ru Cloud over WebDAV (**owner-activated 2026-11-20**).

- Mail.ru issues no public OAuth client for third-party cloud apps (rclone uses a
  reverse-engineered first-party client; that is not a path we may take). The
  supported way is WebDAV at `https://webdav.cloud.mail.ru` with an app password
  ([WebDAV help](https://help.mail.ru/cloud/desktop/webdav/),
  [app passwords](https://help.mail.ru/mail/faq/password/external/)). Plan for the
  two-field form and one verification click below; anything claiming a one-button
  Mail.ru connection would be inventing provider capability.
- New provider transport: fixed WebDAV authority, DNS-pinned verified TLS, bounded
  PROPFIND with depth 1, no writes, no redirects, no proxies, no compression,
  plus the same personal-owner, workspace, `source.view`, revocation and
  read-only-policy checks the Yandex reader applies.
- Form: account address pre-filled from the signed-in user when available plus the
  app password, one provider instruction link
  (`https://id.mail.ru/security` → «Пароли приложений»), encrypted storage in the
  existing secret table and one «Проверить и подключить» action that stores
  `verified` only after a successful bounded listing.
- The Settings hint recommends `Полный доступ к Облаку (WebDAV)` first.
  Full mail, cloud and calendar access is an optional fallback if a newly
  issued WebDAV password is still refused and the user accepts the extra scope.
  The [WebDAV client instructions](https://github.com/dvoegor/mailru-cloud#readme)
  document the cloud-only scope. Live proof is still pending.
- A listing exceeding the 256 KiB response limit explains how to choose a
  smaller folder or split the folder contents in Mail.ru Cloud.
- Keep the WebDAV root as the connection root and let the same picker select a
  folder, so both providers share one selection experience.

Out of scope: file downloads, native original opening, any write/delete or
mutation, per-folder restriction editing (P12-T15), exact-byte version authority,
public links, deployments, and registering or issuing provider application
credentials.

## Where the OAuth application credentials live

- The Yandex application is deployment-wide by nature: Yandex registers the
  redirect URI per application, so one installation/domain uses one client ID and
  secret for **all** users. This is our application's identity, never a user
  setting; users never see or enter it.
- Per-user material stays where it already is: the access token is encrypted in
  `workspace_connection_secrets` per connection, the root lives in the connection
  config, and grants are per connection. Nothing per-user belongs in
  `app/core/config.py`.
- Today the increment reads `settings.YANDEX_DISK_CLIENT_ID/SECRET` (`SecretStr`,
  excluded from repr). That is acceptable for one deployment, but the reviewed
  pattern for operator-supplied application secrets already exists in
  [P14-T05](../../app/integrations/oauth/credentials.py): the deployment knows only
  the path of an operator secret file. Default choice: keep the settings path for
  this increment, and migrate the secret to that seam when a second
  app-credential provider needs it; record the migration in the card then.
- Mail.ru needs no application credentials at all: its path is the user's own app
  password. Registering provider applications, rotating secrets and adding a
  second domain are owner/infrastructure actions outside this card.

## Target experience (acceptance-shaped)

- Yandex: one click «Подключить через Яндекс» → provider login/consent (no app
  form fields at all) → one click on the folder → done. Zero typing, zero
  technical vocabulary.
- Mail.ru: one click «Подключить Облако Mail.ru» → email pre-filled, paste the app
  password (one link explains where it comes from) → one click «Проверить и
  подключить» → pick a folder the same way as Yandex.
- Both forms keep the provider instruction link next to the secret field, exactly
  as the mail connectors already do.

## Implementation does not wait for provider credentials

Nothing in this card needs a real account, a registered application or a provider
secret. The whole increment must be finished, tested and reviewed with providers
mocked, exactly as the accepted P8-T34 increment was:

- Yandex: set `YANDEX_DISK_CLIENT_ID`/`YANDEX_DISK_CLIENT_SECRET` to synthetic
  values with `monkeypatch` and `PUBLIC_BASE_URL` to `http://localhost:8000`;
  replace only `open_yandex_tls` with a fake stream. That is how the existing
  Settings OAuth test already runs.
- Mail.ru: a fake WebDAV stream; no account, no app password, no mailbox.
- Do not ask the owner for credentials and do not block on the missing
  `YANDEX_DISK_*` values: their absence is a supported state (the OAuth form is
  hidden and the manual-token path is shown) and must keep working.

The owner then performs the real steps in this order and nothing earlier:
1. register the Yandex application using
   [the registration checklist](../platform/CONFIGURATION.md#registering-the-yandex-application)
   and set `PUBLIC_BASE_URL`, `YANDEX_DISK_CLIENT_ID`, `YANDEX_DISK_CLIENT_SECRET`;
2. connect a real Yandex Disk folder through the button;
3. create a Mail.ru app password («Полный доступ к Облаку (WebDAV)») and
   connect the real Облако Mail.ru.

Both live proofs are owner-run and stay unrun in the agent's evidence; recording
them as unrun is required, never faking them.

## Risks

- The pending-token record is a new place where a provider secret lives in memory;
  keep it out of logs, out of templates and out of error text, and cap its lifetime.
- A picker widens the request surface of an authenticated route; keep POST-only
  actions, strict form parsing, bounded pages and `no-store`/CSP responses.
- Switching workspaces between consent and confirm must fail closed, as the
  current single-step flow does.

## Audit — 2026-11-20 (independent review of `3f6b2419`)

Verdict: **not accepted yet**; three small corrections below, no design change.
Row stays IN_PROGRESS. Not merged, branch retained.

Reviewed: the whole diff `origin/dev...3f6b2419` (19 files), the claimed
evidence, and independent checks.

Findings:

1. **Mail.ru password scope hint asks for the broadest credential** —
   `app/web/templates/web/_mailru_cloud_connections.html` tells the user to
   choose «Полный доступ к почте, облаку и календарю» and says a cloud-only
   password may not work. That claim came from an unverified user report; the
   published instructions (Cloudiet setup guide, `dvoegor/mailru-cloud` README,
   2025) name «Полный доступ к Облаку (WebDAV)» as the working choice for WebDAV
   clients. Fix: instruct the WebDAV/cloud password first (least privilege), keep
   full access only as a fallback sentence, and correct the same statement in this
   card and in `docs/platform/CONFIGURATION.md`.
2. **App password is not trimmed** — `mailru_webdav.credentials` strips the
   account only. A paste with a trailing space or newline is rejected and the user
   sees «Проверьте адрес и пароль приложения Mail.ru.» with no clue. Strip
   surrounding whitespace from the password, keep rejecting internal whitespace,
   add a regression case.
3. **Large Mail.ru folders cannot be opened at all** — WebDAV has no server-side
   paging, so one `Depth: 1` response carries every child, while the exchange is
   capped at 256 KiB (roughly a thousand entries). A folder above that bound fails
   with the generic «Не удалось обработать ответ Облака Mail.ru». Fix either the
   bound (bounded but larger, e.g. 1 MiB for metadata) or add a specific message
   telling the user to choose a folder with fewer objects; do not leave it silent.

Confirmed during review: pending credentials are bound to
`yandex-browse:<session>:<actor>:<tenant>`, so a workspace switch invalidates the
handle; confirm is single-use and re-checks owner/`source.view` before the
provider call; the disk root cannot be confirmed for Yandex; the connection and
its encrypted secret are written in one transaction; disable clears the secret;
listing requires `is_active`, `verified` for Mail.ru, the matching
platform/provider/auth method and catalog version; hrefs are decoded once,
re-encoded and refused when ambiguous, external or traversal-shaped; DTD/entity
payloads are refused; only `PROPFIND` `Depth: 1` reaches `webdav.cloud.mail.ru`
through the pinned TLS path with no redirects or proxies; 401/403/429 are mapped
to distinct messages; provider secrets never reach the HTML (`no-store`, CSP,
`no-referrer`).
