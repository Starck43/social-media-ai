## Plan

1. Model `contacts`: tenant, display name (encrypted), plus the rotation marker column
   (`pii_updated_at`, see [PII_PROTECTION](../PII_PROTECTION.md)) bumped on every write, preferred channel, last active channel/time, birthday/anniversary (encrypted date or month-day + year flag), notes, `merged_into_id`, timestamps.
2. 3. Model `contact_consents`: channel, purpose (`transactional`, `greeting`, `marketing`), basis, granted/withdrawn at, source evidence; default none.
4. `ContactManager` with tenant-scoped CRUD, identity attach/detach, lookup by normalized identifier, and a merge journal table used later by [P15-T03](p15-t03.md).
5. `/api/v1/contacts` read/list/detail (no merge yet) and a minimal `/app/contacts` list behind the existing nav group (coordinate nav edits as a separate small commit).
6. Retention/offboarding: register tables with workspace offboarding and privacy export/delete flows (P6 contracts).

## Open doubts

- **Resolved 2026-11-04 — `INDEX_KINDS` vs. the rotation registry kind.** The branch
  registered every encrypted column with kind `"text"` and extended `INDEX_KINDS`
  with `opaque_id`, so the accepted P13-T02 test
  `test_registry_entries_are_explicit_and_index_free` failed
  (`assert 'text' in frozenset({'email','phone','username','opaque_id'})`).
  **Owner decision: the third element is the value kind** of a column that also
  has a blind index, or `None` for an encrypted column without one; it is not a
  column type. The nine contact columns are therefore registered with `None`, the
  accepted test now reads `kind is None or kind in pii.INDEX_KINDS`, and
  [PII_PROTECTION](../PII_PROTECTION.md) states the meaning explicitly. `opaque_id`
  stays a legitimate new kind because it has a normalizer and tests. Reversal is a
  registry-tuple edit plus one assertion; no data migration is involved. Owner
  confirmation is recorded by PR #365 and reaffirmed in the current task dialogue.

### Defect and fix

`ContactPrivacy.delete_contact(contact_id, *, session=None)` always forwarded
`session=session` to `ContactManager.delete_by_id`, which is itself
`@with_db_session`-wrapped. With `session=None` the outer branch of the inner
wrapper called the wrapped method a second time with `session=`, producing
`TypeError: delete_by_id() got multiple values for keyword argument 'session'`.
The fix forwards the kwarg only when a real caller-owned session exists and
otherwise omits it, so the manager's own wrapper keeps transaction ownership
(open/commit for `None`, join-without-commit for a supplied session). Global
`with_db_session` is unchanged, and no new unit test was added: the two existing
DB integration tests already observe this path.
