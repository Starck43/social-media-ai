## Why the acceptance was withdrawn

`tests/tooling/test_p11_t24_schema_guards.py::test_function_bodies_match_the_final_migration_bodies`
does not give the same answer twice.

- `_executes()` walks the module AST with `ast.walk`, which is breadth-first.
- `migration_function_bodies()` keeps the **last** body it sees per function.
- Revision `0103_allow_platform_task_initiator.py` installs two bodies of
  `check_personal_llm_dispatch_account` from one helper: the `upgrade` call
  passes `allow_platform_operator=True`, the `downgrade` call passes `False`.
- The traversal therefore decides which one is "final", and it is not stable.

Reproduced by the auditor on `0850009a`:

- removing `tests/tooling/__pycache__` before the run → **1 failed, 10 passed**;
- running again with the cache warm → **11 passed**;
- `python -m scripts.ci.run_offline` on the same tree alternates the same way;
- hosted CI on `0850009a` failed with
  `check_personal_llm_dispatch_account (last written by 0103_allow_platform_task_initiator.py)`.

Attempts that did not fix it: sorting the call sites by position, sorting the
expanded statements, restricting `_Scope` to module-level assignments, and
raising on two different bodies in one revision (that last one rejects a
legitimate upgrade/downgrade pair). Each was reverted; the tree is clean.

## Required before a new audit

1. Decide the final body by revision semantics — the body an `upgrade` path
   installs is the one a migrated database has — not by traversal order.
2. Fail loudly when the body cannot be decided; never pick silently.
3. Prove determinism: cold and warm bytecode cache give the same result, and
   `scripts.ci.run_offline` is green before and after the other manifest entries.
4. Re-run the billing suite on a rebuilt schema and record the numbers.
