# P8-T52 — VK wall collection loses photo media URLs and legacy permalinks

Registry: [ROADMAP](../../ROADMAP.md); parent: [P8](../phases/p8-first-value-ui.md).
Registered while answering [Q-2](../audit/q/q-2.md), whose live check proved
the provider returns what we fail to store.

## Problem

For VK source 2939 (`annastrizhovadesign`, tenant 1) the stored rows carry
`attachments: [{"type": "image", "url": null}, …]` and, on older rows, no
permalink, while the same posts at the provider carry `photo.sizes[]` for every
photo. Measured 2026-11-18:

- 1 087 attachment snapshots for the source, only 5 with a URL (all 2019 data);
  860 `image` and 182 `video` placeholders.
- Live `wall.get` over the audited window: 61/61 photos had `sizes[]`,
  0 reposts, 33 video attachments — the same 33 video placeholders we store.
- A local reproduction of `VKClient._normalize_response` with a synthetic
  `wall.get` item does emit the largest photo URL, so the loss happens on the
  collection path that produced these rows (older normalizer or a path that
  never passes the provider attachment bodies), not in the staging validator.

Video previews are placeholdered **by design** and are not part of this defect.

## Scope and acceptance

- Identify which collection path stages VK wall rows without photo URLs (source
  collection for `USER`/group walls; include the search adapter and the chat task
  foundation), and make that path persist the largest `photo.sizes[]` URL and the
  `https://vk.com/wall{owner}_{post_id}` permalink for new rows.
- Keep the existing staging guarantees: no downloads, provider bodies or
  credentials stored; `{"type": "video", "url": null}` stays as designed;
  `normalize_attachments` remains the only writer of the snapshot shape.
- Acceptance needs one bounded live read-only check on the owner's own source
  (same credential route as Q-2), proving a freshly collected post stores a
  non-null photo URL and its permalink, plus mocked tests for the mapping.
  No backfill of historical rows unless the owner asks for it separately.
- Do not change retention, category status or provider permissions here.

## Boundaries

Collection/staging code and its tests only. No migration unless a stored field
must change (none is planned), no live provider writes, no public-schema mutation
beyond synthetic test-schema records, no secret value in code, card or commit.

## Rollback

Revert the mapping change; rows collected afterwards return to URL-less
placeholders, and the previous staging behaviour is restored without data loss.
