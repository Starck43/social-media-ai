# Q-20 — Test-schema guard coverage: `outbox_reply_evidence` PII marker

**Status: IN_PROGRESS · opencode-auditor · claimed 2026-11-11 on `dev` `9ef8b1ce`.**

Found while bringing the `public` schema from `0145` to the head `0151` (owner
instruction, 2026-11-11). The migration apply itself was clean; the divergence it
exposed is in the **test** schema.

## Observed

`public` and `p20t12_audit` carry the trigger
`outbox_reply_evidence.contact_pii_marker`; `test_schema` does not:

```text
public       outbox_messages.contact_pii_marker, outbox_reply_evidence.contact_pii_marker, outbox_targets.contact_pii_marker
p20t12_audit outbox_messages.contact_pii_marker, outbox_reply_evidence.contact_pii_marker, outbox_targets.contact_pii_marker
test_schema  outbox_messages.contact_pii_marker,                                       outbox_targets.contact_pii_marker
```

`outbox_reply_evidence` stores inbound/outbound reply text, so the PII marker is a
privacy guard, not decoration: without it, writes to that table do not advance the
contact PII marker that the retention/erasure paths read.

## Cause

The table was added by `migrations/versions/0149_outbox_reply_evidence.py`, which
creates the trigger with explicit DDL. The metadata path used to rebuild
`test_schema` cannot create migration-only objects, so it replays them from
`scripts/schema_guards.py#GUARD_TRIGGERS` — and that list never gained
`outbox_reply_evidence`. Every rebuild therefore reproduces the omission.

The guard already has a detector:
`tests/tooling/test_p11_t24_schema_guards.py::test_frozen_baseline_and_post_baseline_migrations_match_guard_module`
fails on exactly this pair (`migration-only=[("contact_pii_marker", "outbox_reply_evidence")]`).
It was red on `dev` `9ef8b1ce`.

## Fix

1. Add `outbox_reply_evidence` to the PII-marker table tuple in
   `scripts/schema_guards.py`, next to the other outbox tables.
2. Apply the missing trigger to the live `test_schema` through the module's own
   `apply_schema_guards` (idempotent drop/recreate; test-schema setup is
   pre-authorized), then verify `public`/`test_schema` trigger inventories match.
3. Leave `0149` untouched: a fresh migration run already creates the trigger, and
   rewriting applied DDL is forbidden.

## Acceptance

1. `pytest tests/tooling/test_p11_t24_schema_guards.py` → 15 passed.
2. `test_schema` trigger inventory equals `public` for every `outbox%` table.
3. `/app` schema inventory diff on `test_schema` shows only the one added trigger —
   no tables, types, functions or other triggers changed.

## Not in scope

Rebuilding `test_schema` from scratch. The guard list is the source of truth for
future rebuilds; this task repairs the current schema and the list together.
