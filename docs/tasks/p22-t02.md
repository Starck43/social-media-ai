# P22-T02 — Connector capabilities, installations and account grants

[Phase P22](../phases/p22-universal-tasks.md) · [Design](../product/UNIVERSAL_TASKS.md) · [Queue](../../ROADMAP.md#p22)

**Dependencies.** Can be claimed immediately.

**Implementation ownership.** app/integrations/catalog/, app/services/social/, workspace connection, authorization and local connector resolvers.

## Deliverable

Publish a typed resolver for capability, implementation, installation, principal/grant, resource selection and direction. Map VK, Telegram bot versus user session, Yandex Mail versus Disk, Mail.ru Mail versus Cloud, Bitrix24 and a paired root. Maintain an explicit support matrix from implemented adapters. Keep one owner for each config field. Document which fields are code defaults, operator settings, deployment secret names, personal credentials or workspace consent. Preserve existing validated endpoint policy and key rotation paths.

## Acceptance

One deployment app can serve two independently authorized accounts. Revoking an account or selected root blocks its work without disabling another account. No secret can appear in a descriptor, UI response, job payload or diagnostics. Ambiguous connections require explicit selection. Adding a registry description alone exposes no executable action.

## Verification at implementation

Exercise disabled and read-only capabilities, expired grants, two accounts of one provider and operator configuration changes using doubles. Preserve existing provider keys and handlers as compatibility adapters.
