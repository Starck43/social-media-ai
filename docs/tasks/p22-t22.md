## Problem

`AgentTask` was written when a task meant one thing: collect social posts on a cron. It is still
the live scheduling row — 491 references across `app/`, and `brief_schedule.py` still creates one
directly — but the product now means "a reminder to myself", "a team obligation", "filter my
mailboxes" and "collect and analyse social posts" under one identity. The row did not follow.

Three concrete symptoms:

1. **The creation form is a flat wall.** `POST /app/tasks` (`app/web/task_create_routes.py:43`)
   accepts more than sixty `Form(...)` parameters in one signature: `tracked_users`,
   `keywords_match`, `brands`, `competitors`, `hashtags`, `influencer_names`, `topic_list`,
   `digest_period`, `digest_group_by`, `digest_time_breakdown`, `retention_success_hours`,
   `trigger_keywords`, `trigger_threshold`, `trigger_spike_multiplier`, `collection_people`,
   `collection_communities`, `collection_discovery_queries`, `collection_candidates_confirm`, and
   so on. Every one of them is asked of every caller regardless of what the task actually is.
2. **The type list is a job list, not a task list.** `JobType` (`app/types/enums/job_types.py`)
   offers `collect`, `digest`, `prune`, `analyze`, `learn`, `reflect` — internal job kinds. The web
   layer already hides `collect` and maps it onto `analyze`
   (`_normalize_web_job_type`, `app/web/task_forms.py:63`), which is a rename papering over a model
   that no longer matches the product. A reminder or a mailbox filter has no honest choice here.
3. **The payload is an untyped bag.** `AgentTask.payload` is `JSON` with no schema
   (`app/models/scheduling/agent_task.py:78`). Selection, digest windows, retention, targets and
   collection intent all live in it side by side, so nothing can validate a task, and the editor
   must render every field for every type to avoid losing data.

The prototype already answers the shape question: title first, then optional branches — «Срок и
важность», «Исполнитель», «Источники и сценарий» → source picker → scenario → «Когда запускать?».
The branch a person sees depends on what they picked, not on a job-type dropdown.

## Deliverable

Define typed, versioned parameters for the optional automation branches. Reuse collection intent
and validate parameters against selected capabilities and steps. Personal notes, team assignments
and automated runs are journeys through the same task, and timing, people and automation can be
combined. Keep JobType internal. Show parameters progressively based on selected sources,
capabilities and steps. Preserve compatible draft fields as the selection changes.

Validate invalid parameters before publication with a bounded error. Keep reading existing
unversioned legacy payloads without dropping data. Preserve existing LegacyTaskId aliases and
compatibility writers. The canonical Task remains the same when automation is attached. A
title-only or team task creates no plan, AgentTask, schedule or job. Canonical automation publishes
a plan revision on that ID and configures a canonical trigger only when scheduling is chosen.
The new editor does not create a parallel legacy scheduler row.

Inventory duplicated AgentTask fields and propose a reversible compatibility transition if
needed. Schema removal or legacy retirement requires explicit owner approval and follows T12
parity and rollback.

## Model boundaries — what Platform, Source and AgentTask are for

The question this card has to answer before any table changes: which entity owns what, now
that a source may be a mailbox or a cloud folder and not only a VK wall. The code already
answers most of it, and the answer is not "make one universal table".

| Entity | What it is | What it must not become |
| --- | --- | --- |
| `Platform` (`app/models/collection/platform.py`) | A social collection platform: `vk`, `telegram`. Holds `base_url` and API params. | A registry of every connector. Mail, disk and portals are not platforms; forcing them here would give them a fake `base_url` and a fake `external_id`. |
| `Source` (`app/models/collection/source.py`) | One collectable social object: a community, a wall, a chat. `platform_id` + `external_id` + `params`. | The universal resource. Its `external_id` is a platform handle, and `owner_task_id` already overloads it as a task-scoped query lane. |
| `WorkspaceConnection` (`app/models/integrations/connection.py`) | The universal connected account: `provider_id`, `auth_method`, `account_key`, encrypted secret, `state`. This is what the connections settings page manages. | A place to store per-source search fields. |
| `AgentTask` (`app/models/scheduling/agent_task.py`) | The scheduling row: cron, `job_type`, `payload`, trigger/action config, and its source set. | The place where a provider's search fields live. |
| `TaskPlanRevision` + `Binding` (`app/services/execution_plan_contracts.py`) | The versioned, validated plan: ordered steps, typed bindings, trigger. | A second copy of the task. |

**`ResourceKind` is already the universal seam.** `app/integrations/catalog/task_capabilities.py`
declares `MAIL_FOLDER`, `DISK_FOLDER`, `PORTAL`, `PAIRED_ROOT` and `SOCIAL_SOURCE`, and
`CAPABILITIES` maps each provider operation to one of them. That is the abstraction the question
asks for, and it exists.

**But only two kinds can currently enter a plan.** `Binding.selection()` refuses any capability
whose kind is not `SOCIAL_SOURCE` or `MAIL_FOLDER`
(`app/services/execution_plan_contracts.py:45`), and `OPERATIONS` defines steps only for
`social.collect`, `social.cached`, `social.analyze`, `social.digest`, `mail.read_headers`,
`mail.group_by_sender` and `messages.store_groups`. `DISK_FOLDER`, `PORTAL` and `PAIRED_ROOT`
are declared in the catalog and have no operation that can consume them. A task cannot schedule
a disk read today, and no table change in `AgentTask` would make it possible.

**Collected data already has per-kind homes, and they are not one table.**

| Kind | Where the result lands | Shape |
| --- | --- | --- |
| `SOCIAL_SOURCE` | `CollectedItem` (`app/models/collection/collected_item.py`) | One fetched post/comment, raw, with `external_id`, `content_hash`, `published_at`; a write-ahead copy removed once analysis stores it. |
| `MAIL_FOLDER` | `UnifiedMessage` / `MessageThread` (`app/models/communications/message.py`) | Message metadata upserted by tenant, connection, channel and original id. `mail.read_headers` itself returns only `[connection_id, folder, validity, uid, digest]` — a bounded reference, not the message. |
| `DISK_FOLDER`, `PORTAL`, `PAIRED_ROOT` | No collection sink exists | — |

So the honest answer to "how is data stored after collection" is: **each resource kind has its
own sink, and a new kind needs a new sink, not a new column on `AgentTask`.** A universal
`collected_items` for every provider would either lose the fields that make each kind useful or
become a JSON bag with the same problem this card is fixing one layer up.

**What must not be broken.** `docs/connectors/CONNECTOR_JOB_EXTENSION_SPEC.md` (accepted
2026-10-31) already decided this: do not add a universal connector schema, do not force a new
capability into `Source`, `Platform` or `CollectionProvider`, keep job registration explicit and
server-owned, and add one explicit factory per selected capability. This card works inside that
decision, not against it.

## Answers to the owner's four questions

### 1. Leave `Source` untouched — what exactly is platform-bound in it?

Nothing in `Source` needs to change for a non-social resource to work, because nothing
non-social should become a `Source`. Its columns split like this:

| Column | Bound to | Verdict |
| --- | --- | --- |
| `platform_id` | a `Platform` row | social only. A mailbox has a `WorkspaceConnection`, not a `Platform`. |
| `external_id` | a platform handle (`@durov`, community id) | social only. A folder path is not an external id. |
| `source_type` (`SourceType`) | `USER`, `GROUP`, `CHANNEL`, `PUBLIC`, `SEARCH`, `SUPERGROUP`, `BOT`… | social only. The enum is a social taxonomy. |
| `params` | per-platform search fields | social only. |
| `last_item_id` | push watermark for the Telegram Bot API | social only. |
| `owner_task_id` | a task-scoped query lane | social only, and already overloaded. |
| `owner_user_id` | the member whose credential collects | **generic** — mail and disk need the same rule. |
| `is_active`, `last_checked`, `name` | — | **generic**. |

So `Source` is not "a source of data". It is **a collectable social object on a `Platform`**.
That is why it looks platform-shaped: it is. The generic concept the question is reaching for
already has a different name in this codebase — `WorkspaceConnection` plus a `ResourceKind` and a
selection (`resource_id` + optional `path`).

**The rule to adopt:** `Source` stays exactly as it is, and only `SOCIAL_SOURCE` capabilities bind
to it. Mail binds to a `WorkspaceConnection` + folder path. Disk binds to a `WorkspaceConnection` +
path. A local root binds to a paired device + root. Three different resource kinds, three different
selections, one `Binding` contract. No column moves, no migration, no risk to working collection.

### 2. How does this become unification, if a source is only for platform collection?

Unification happens at the layer above, and it is already built: `Binding` carries
`(capability, resource_id, path, kind)` and `resolve_task_resource` re-checks it at execution
(`app/integrations/task_resources.py:135`). A task does not care whether its binding points at a
`Source` or a `WorkspaceConnection`; it cares that the capability's `kind` matches the selection.

What is missing is not a model but **operations**. `OPERATIONS`
(`app/services/execution_plan_contracts.py:94`) has seven entries and covers only social and mail.
`Binding.selection()` refuses any kind outside `{SOCIAL_SOURCE, MAIL_FOLDER}` (line 45). So the
unification is real in the contract and incomplete in the operation table. Adding a kind means
adding an operation, a sink and a factory — not reshaping `Source`.

### 3. What about the other connectors?

Each one is a `WorkspaceConnection` with a `provider_id` from the catalog
(`app/integrations/catalog/__init__.py`), and each needs three things before a task can use it:

1. a `Capability` in `CAPABILITIES` with a `kind` and a non-null `handler` — note that
   `resolve_task_resource` returns `UNSUPPORTED` when `handler is None`, which is exactly why
   `telegram.bot.read` cannot be bound today;
2. an `Operation` in `OPERATIONS` that consumes that kind;
3. a result sink.

**Local disk is the clearest failure, and it fails in four places, not one.** The catalog declares
`local_gateway.search` with `handler="connector_gateway"`, but:

- no code anywhere implements a `connector_gateway` handler (the string appears only in the catalog);
- `ResourceKind.PAIRED_ROOT` has no `Operation`, so a plan step cannot consume it;
- `get_gateway()` raises `ConnectorUnavailable` unless both `LOCAL_CONNECTOR_ENABLED` and
  `LOCAL_CONNECTOR_SECURITY_REVIEWED` are true, and both default to `False`
  (`app/core/config.py:64-65`);
- `docs/connectors/LOCAL_CONNECTOR_PROTOCOL.md` states plainly that it is "a proposed security
  contract, not implemented behavior", with P18-T02/T03/T05/T06 still to build it.

So local disk is not blocked by `AgentTask` or by `Source`. It is blocked by an unimplemented
connector behind two off-by-default flags. No table change in this card would make it work.

### 4. What about plain web search?

Web search already exists as a service with its own budget, refusals and evidence snapshots:
`WebResearchService.research` and `run_research_task_step`
(`app/services/web_research/service.py:594`, `:773`). It is **not** a `ResourceKind` and has no
`Operation`, so a task cannot schedule it through the plan — it is reachable from the agent
toolset and delegation path instead.

That is the honest boundary: web search has no `WorkspaceConnection` and no resource to bind,
because there is nothing to authorize beyond the query itself. If it should become a schedulable
step, it needs an `Operation` with no binding and its own budget/payer check — a design decision,
not a table.

### Consequence for this card

The card defines typed optional parameters, fields derived from selected capabilities and steps, and
an evidenced proposal for the `AgentTask` columns the plan revision already duplicates. **No change
to `Source`, `Platform`, `CollectedItem`, `UnifiedMessage`, the compatibility writer or the VK and
Telegram adapters.** Adding a resource kind (disk, portal, paired root) or a bindingless operation
(web search) is separate work that depends on the plan publisher this card does not build.
