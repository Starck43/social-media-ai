## Delivered contract

The selected reusable seam is one-off task-plan launch behind REST
`/tasks/run/plan` and agent `task_execute_once`. It builds on the canonical plan
and transaction contracts delivered by [P11-T04](p11-t04.md) and
[P11-T05](p11-t05.md), without introducing P8-T40's result composition schema.

- `app/services/task_contracts.py`: strict validated launch arguments, frozen
  command/result types, fixed error-code/message/status registry and allowlisted
  receipt/tool-error presenters. The agent schema is generated from its runtime
  validator; the handler also rejects missing/extra fields at execution. Request
  keys use bounded ASCII/full-match validation, including newline rejection.
- `app/services/task_launch.py`: typed `execute_task_launch` orchestration behind
  the source-compatible `launch_social_task` wrapper. Existing fresh membership,
  permission, source/tenant, payer, transaction and idempotency checks remain.
  A receipt exposes only task/job IDs, bounded statuses and its derived task URL.
  Unknown statuses stay unknown/unconfirmed; pruned-job receipts retain the
  existing unavailable status and durable original job ID.
- `app/services/task_plans.py`: stable finite safe error codes and a version-aware
  saved-payload reader reusing the existing parser. Legacy no-plan payloads,
  omitted version=1 and ignored extension fields remain compatible. Unsupported
  versions and invalid limits/timezones fail closed. The reader is used by
  `AgentTaskManager._validate_task_plan_binding`.
- API/agent adapters map known validation, permission, policy, busy and billing
  failures to safe responses; unclassified exceptions retain an unconfirmed
  outcome without exposing raw provider text or implying safe automatic retry.
  Known REST status contracts (400/403/409), extra-ignore envelope behavior and
  successful receipt keys are preserved. Unclassified ValueError now produces a
  fixed HTTP 500 unconfirmed outcome; legitimate validation uses typed 400 errors.

No API form/CLI parameter rewrite, new permission grant, DB migration, network
call in a transaction, broad progress presenter refactor or P8-T40 schema.
Code/docs elsewhere that use legacy exceptions keep their existing string
contract; safe one-off boundaries expose only finite error codes/messages.
