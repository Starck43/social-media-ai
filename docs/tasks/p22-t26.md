[P22-T24](p22-t24.md) (an executable canonical path).

## Problem

Priority is manual everywhere, and the two automatic signals a person actually expects do not
exist.

**A task's priority never reacts to its deadline.** `Task.priority` is `String(10)` with a CHECK on
`low|medium|high|critical` (`app/models/planner/task.py:55,78`), typed `Priority = Literal[...]`,
default `medium` (`app/services/planner/contracts.py:12,25`). A person sets it; nothing raises it.
`due_at`/`due_date` are separate columns and are never converted into pressure. So a task due
tomorrow with `priority=medium` does not appear under «Важные», which is exactly
`priority in (high, critical)` (`app/services/workspace/task_queries.py:183` in the T18 branch).
«Просроченные» and «Важные» are independent predicates, and nothing bridges them.

**A sender cannot be marked as important.** `Contact` has `display_name_encrypted`,
`notes_encrypted`, `birthday_encrypted`, `anniversary_encrypted`, `preferred_channel`,
`last_active_channel`, `last_active_at`, `merged_into_id` (`app/models/contacts/core.py:62-73`).
There is no standing, tier, VIP flag or tag table — `contacts`, `contact_identities`,
`contact_consents`, `contact_merge_journal` are the only tables. A grep for
`sender_rule|domain_rule|vip|allowlist` across `communications` returns nothing.

**Triage already reads content, but not standing.** `classify_thread_baseline`
(`app/services/communications/triage.py:370-495`) applies six ordered rules over subject, sender,
`unread_count`, `message_count`, `last_direction` and an optional transient preview. It detects
autoresponders, newsletters, outbound-last threads, explicit questions and urgency keywords. It has
no input for "this sender matters", so a client's mail ranks the same as a stranger's.

**The override mechanism already exists and is the right hook.** `ThreadTriageDecision` is keyed by
`(tenant_id, decided_by_user_id, thread_id)` with `category` and `reason_encrypted`
(`app/models/communications/message.py:211-258`), `record_user_triage_override` persists a
correction with `basis="user_override"`, `is_model_fact=False` (`triage.py:690-742`), and
`triage_thread_record` applies it before returning (`triage.py:1000-1012`). A per-thread human
decision already wins over the classifier. What is missing is a per-sender decision that applies to
future threads.

## Deliverable

Two rules, both deterministic, both explainable, neither calling a model.

1. **Sender standing.** Add an explicit, tenant-scoped standing for a contact or a sender identity —
   a small bounded enum such as `important`, `normal`, `low` — stored where a person can set it and
   read it back. Feed it into `classify_thread_baseline` as an input, not as a hidden side effect:
   an `important` sender raises the floor of the classification (a thread that would be `can_wait`
   or `uncertain` becomes `needs_reply`), and a `low` sender lowers it. Record the standing in the
   returned `reason` so the classification stays explainable, and keep `is_model_fact=False` for
   anything a human set.
2. **Deadline pressure.** Derive a pressure signal for an open task from `due_at`/`due_date` and the
   workspace-local day boundary, and use it in the «Важные» predicate without mutating the stored
   `priority`. A task is important when `priority in (high, critical)` **or** its deadline is within
   a bounded window. Do not write the derived value back into `priority`: a stored field that
   silently changes is a lie in the audit trail, and the prototype's «Важные» is a view, not a
   mutation.

Both rules must be visible: the list shows why an item is there, and the triage reason names the
standing that moved it.

## Explicitly not in scope

**Content-derived difficulty.** The owner asked whether the agent can judge how hard a request is
from its text. It cannot do so reliably, and this card does not pretend otherwise. There is no
`complexity` or `difficulty` concept anywhere in the codebase — a grep returns only the password
validator and a scenario-schema limit. Adding one would mean a model call per thread, an accuracy
claim nobody can test, and a new failure mode in a path that currently fails closed. If it is ever
wanted, it needs its own card, a labelled corpus and a measured baseline, the way P20-T09 did its
classifier (`evaluate_triage_corpus`, `triage.py:1535`).

Also out of scope: rewriting the classifier, a body cache or search index (`D3`/`D11`), and the
triage plan operation itself ([P22-T25](p22-t25.md)).

## Acceptance

A contact marked `important` produces `needs_reply` for a thread the baseline would otherwise put in
`can_wait` or `uncertain`, and the reason names the standing. Marking the same contact `low` demotes
it. A per-thread override still wins over both the standing and the classifier.

A task due within the window appears under «Важные» while its stored `priority` is unchanged, and
the card shows the deadline as the reason. A task with no deadline and `priority=medium` stays out.
Clearing the standing or moving the deadline restores the previous classification with no residual
state.

Both rules are tenant-scoped and actor-scoped: one member's standing for a contact does not change
another member's classification unless the product decides standing is workspace-wide, and that
choice is recorded.
