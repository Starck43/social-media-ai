## Verified findings and acceptance contracts

### AUD-01 — P0: Replace unauthenticated password mutation with authorized recovery

**Evidence:** [app/admin/endpoints.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/admin/endpoints.py#L50-L154); [app/admin/setup.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/admin/setup.py#L59-L68); [app/core/hashing.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/core/hashing.py)

**Observed:** The custom FastAPI GET issues a CSRF token without identity. POST accepts that token and an email, looks up any account and immediately writes a replacement password. It logs the six-character temporary password. The SQLAdmin authorization backend does not wrap this custom route. CSRF proves neither account ownership nor reset authority; the request limiter cannot supply either.

**Impact/limits:** An anonymous caller can disrupt a known account when the route and configured limiter are operational. Anyone able to read the resulting log may obtain its temporary password. This audit used only synthetic doubles, not a real account or deployed endpoint.

**Accept:** Anonymous requests without a valid account-bound recovery proof cannot change any hash; recovery uses expiring, single-use proof and generic non-enumerating replies, or a separately approved operator-only reset. Missing/expired/replayed/foreign proof leaves storage unchanged. No password/reset secret in logs or responses; authorized change remains usable. Run DB/ASGI acceptance through the project runner, never send a real recovery message from a regression.

**Provenance:** Legacy auth surface outside the bounded identity/model work of PR #22 and later SQLAdmin/settings PR #191; neither PR is evidence that recovery is safe.

**Probe:** anonymous_reset.

**Execution:** TODO; implementation owner unassigned. Depends: none. Exclusive lane: app/admin/endpoints.py (reset_password_page/reset_password only); app/core/hashing.py (temporary-password helper only); app/templates/sqladmin/user/reset_password.html; new recovery regression tests.

### AUD-02 — P1: Remove password hashes from HTTP user responses

**Evidence:** [app/api/v1/endpoints/user.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/api/v1/endpoints/user.py#L12-L59); [app/schemas/user.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/schemas/user.py#L80-L99)

**Observed:** GET users, GET users/me and PUT users/{id} use UserInDB. That schema inherits public account fields and adds hashed_password. API documentation examples omitted this field, but the declared response contract includes it.

**Impact/limits:** Password verifiers are returned to authorized API callers, including the caller of /me; the ADMIN list can return other users' hashes. No real verifier was read or collected by this audit. Hashes are not plaintext passwords but must not cross this response boundary.

**Accept:** All three HTTP responses and their OpenAPI public response schemas exclude hashed_password and any credential fields, while preserving documented account metadata and permission checks. Keep internal persistence types separate. Negative controls fail if UserInDB is reintroduced.

**Provenance:** PR #165 protected creation input only; it did not replace these response models. Docs previously showed a safe abbreviated User shape.

**Probe:** user_response_schema.

**Execution:** TODO; implementation owner unassigned. Depends: none; coordinate the same user.py/user schema write lane with AUD-03. Exclusive lane: app/api/v1/endpoints/user.py (response_model declarations only); app/schemas/user.py (public response types only); new user-response regression tests.

### AUD-03 — P1: Separate self-service profile updates from privilege updates

**Evidence:** [app/api/v1/endpoints/user.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/api/v1/endpoints/user.py#L31-L59); [app/schemas/user.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/schemas/user.py#L54-L65); [app/models/managers/user_manager.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/models/managers/user_manager.py#L62-L94); [scripts/setup/assign_roles_permissions.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/scripts/setup/assign_roles_permissions.py)

**Observed:** UserUpdate accepts is_superuser and is_active. The endpoint requires user.update and checks self-or-is_superuser, but forwards those state/privilege fields. **Accept:** Define a bounded platform privilege-change policy; ordinary profile update cannot change is_superuser, role/state or other authority fields. Fresh authorized operator changes still work; revocation and cross-target attempts fail closed. Cover actual endpoint plus manager path, not just schema dropping at registration.

**Provenance:** PR #165 is correctly integrated for public registration. Its protection does not apply to UserUpdate; do not reopen or relabel that registration package.

### AUD-04 — P1: Use shared, cookie-independent login protection

**Evidence:** [app/admin/auth.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/admin/auth.py#L26-L74); [app/admin/auth.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/admin/auth.py#L108-L133); [app/api/v1/endpoints/auth.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/api/v1/endpoints/auth.py#L18-L76); [app/web/auth.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/web/auth.py#L85-L108); [app/services/user/auth.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/services/user/auth.py#L69-L114)

**Observed:** Ordinary SQLAdmin wrong-password/unknown-user branches return False without calling track_login_attempt; it runs only after exceptions. Existing counters live in the caller's signed session cookie, so cookie replacement bypasses their history. API and /app login do not call a corresponding limiter/shared attempt store. The fake dummy hash in authenticate is not a valid bcrypt verifier.

**Impact/limits:** Configuration names MAX_LOGIN_ATTEMPTS and LOGIN_TIMEOUT_MINUTES overstate effective brute-force protection. An invalid dummy verifier also does not perform the same bcrypt work as an existing account. No live password guessing or timing measurement was performed.

**Accept:** Count normal failure paths and implement a reviewed shared account/network throttle that survives cookie clearing and works across processes. Cover username/email normalization, success, wrong/unknown/inactive user and cooldown without enabling account-lockout DoS. Use a valid fixed dummy verifier, generic replies and no credential logging. Configuration/docs state the actual scope.

**Provenance:** PR #67 hardened cookie Secure flags, and PR #174 replaced JWT verification; neither establishes rate protection or server-side session storage.

**Probe:** admin_bad_password.

**Execution:** TODO; implementation owner unassigned. Depends: none; keep admin/endpoints.py recovery ownership with AUD-01. Exclusive lane: app/services/user/auth.py (authentication/failure accounting); app/admin/auth.py (login/lockout); app/api/v1/endpoints/auth.py (login); app/web/auth.py (login_submit only); new login-protection tests.

### AUD-06 — P1: Centralize safe provider-error envelopes without dropping accounting

**Evidence:** [app/services/ai/llm_client.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/services/ai/llm_client.py#L235-L295); [app/services/ai/llm_client.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/services/ai/llm_client.py#L415-L474); [app/services/ai/llm_client.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/services/ai/llm_client.py#L545-L598)

**Observed:** OpenAI-compatible, Anthropic and custom analyze clients build HTTPStatusError messages from r.text, log exception text and copy it into response.error and parsed.analysis. OpenAI's failure envelope additionally contains the full payload, including prompt/media. Output-validation warnings interpolate validation exceptions, which may contain input values.

**Impact/limits:** A provider echo or exception can carry customer text, sensitive URLs or credentials into logs and persisted/caller-visible envelopes. This is a source-level disclosure path, not proof that a real provider returned a secret. Successful provider output remains intentional analysis data; do not redact it indiscriminately.

**Accept:** One allowlisted transport/output error mapping replaces raw exceptions/provider bodies in operational logs and failure summaries. Synthetic token/DSN/prompt/media sentinels never enter logs or diagnostic error fields. Preserve dispatch identity, failed_transport/failed_output classification, unknown token/cost evidence and already-supported journaling. Validation failure remains fail-closed; no real HTTP/paid call in tests.

**Provenance:** PR #107 redacted credential tests, PR #79 schema fallback warnings, and PR #163 non-analyzer attempt capture. Their bounded redaction/capture does not cover these analyze error branches.

**Probe:** static source inspection; no provider call.

**Execution:** TODO; implementation owner unassigned. Depends: none; accounting/admission activation is explicitly excluded. Exclusive lane: app/services/ai/llm_client.py (analyze error/validation branches only); new adapter privacy regressions.

**Evidence:** [app/services/digest/builder.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/services/digest/builder.py#L112-L179); [app/services/ai/reporting.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/services/ai/reporting.py#L98-L151); [app/services/ai/reporting.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/services/ai/reporting.py#L1046-L1136); [app/models/managers/ai_analytics_manager.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/models/managers/ai_analytics_manager.py#L346-L414); [app/services/digest/render.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/services/digest/render.py#L65-L124)

**Observed:** aggregate passes source_ids/scenario_id to the brief, but not its five top-level aggregates, whose stats/topics/sentiment are rendered too. _analytics_query uses today-days without an upper bound or DAY-only filter, while period_bounds/header start at today-(days-1). A day report therefore includes yesterday; weekly/monthly rollup rows are eligible to re-enter later sums. build_period_rollups writes all sources in the workspace, independent of digest selection.

Cover two sources/two scenarios, boundary dates, future dates and daily plus weekly/monthly rows; all displayed sections agree and no rollup double count occurs. Decide/document rollup write ownership and selection. Reuse loaded rows/bounded manager reads rather than repeatedly materializing the same large JSON set; preserve grouping/coverage and previous-window behavior.

**Provenance:** PR #3 verifies workspace and recipients, PR #63 caveats and later PR #48 reporting lookup precedence. Those boundaries do not establish selected-source/time/row-kind parity.

**Probe:** report_day_window plus source-call inspection.

### AUD-09 — P2: Make pipeline counts and activity labels truthful

**Evidence:** [app/web/dashboard.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/web/dashboard.py#L133-L151); [app/web/templates/web/dashboard.html](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/web/templates/web/dashboard.html#L79-L119); [app/models/collected_item.py](https://github.com/Starck43/social-media-ai/blob/7ba5fe4ce0879a38d96ecb92770dad055c014624/app/models/collected_item.py)

**Observed:** Running/queued counts are computed from only the three newest pending/running jobs, with no collect/analyze type filter. Every non-collect running job is labelled "Модель анализирует…", including digest/prune/etc. staged is COUNT of all retained collected rows, not an eligibility/coverage query proving that those rows await analysis.

**Impact/limits:** A running job outside the latest three can be hidden; queue totals are actually preview counts; unrelated jobs masquerade as model activity. Retained staged rows may include already-covered, retired or otherwise ineligible inputs, so "awaiting analysis" is not established by this count.

**Accept:** Distinguish total counts from bounded previews, or label the preview honestly; filter/label job types explicitly and keep statuses neutral about whether provider HTTP is actually in flight. Give staged count its literal retained-input meaning or use the existing eligibility contract for a true backlog. Cover >3 jobs, digest/prune/running/pending combinations and retained covered rows; keep queries bounded, tenant-scoped and permission-gated.

**Provenance:** Direct dev c598b70 introduced this strip; this is separate from notifications partial-refresh 78e2dce behavior and does not authorize provider calls.

**Probe:** pipeline_tasks_only; pipeline_analytics_only plus source inspection.

**Execution:** TODO; implementation owner unassigned. Depends: AUD-08 (same files; never parallel writes). Exclusive lane: app/web/dashboard.py (_pipeline projection after AUD-08); app/web/templates/web/dashboard.html (pipeline count/type labels); focused pipeline projection tests.
