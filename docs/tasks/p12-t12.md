# P12-T12 — Файловое пространство: оригиналы, компактная память агента и безопасные действия

Реестр: [ROADMAP](../../ROADMAP.md). Родитель: [P12](../phases/p12-domain-workspace-expansion.md).
Приоритет `P2` · сложность `C5`; актуальные статус и исполнитель — только в реестре.
Ветка планирования: `docs/p12-t12-file-workspace-plan`; PR — см. связанный PR этой ветки.
Будущая ветка реализации: `feat/p12-t12-file-workspace`, после назначения исполнителя.
Запрос владельца: https://app.notion.com/chat?t=40c071f39db6802e935c00a98e78df77

**Это подробный план, а не реализованная функциональность.** Публикация/обсуждение
плана не разрешает запуск реализации, подключение аккаунтов, запись во внешние
файлы, развёртывание или миграцию `public`. Работа разбита на последовательные
проверяемые срезы: не пытаться реализовать все провайдеры и форматы одним PR.

## 1. Цель и пользовательские сценарии

Дать разным пользователям понятное рабочее пространство для разрешённых файлов:
найти нужное, понять содержимое, открыть оригинал, поручить ограниченное действие,
увидеть проверяемый результат и сохранить полезные выводы без замусоривания диска.

1. «Подключи папку с документами»: выбрать аккаунт/устройство, папку, режим доступа
   и место обработки; увидеть, что именно будет прочитано и что будет сохранено.
2. «Найди договор и покажи срок»: ответ с файлом, актуальностью, страницей/абзацем
   и кнопкой **Открыть оригинал**, а не только внутренним идентификатором цитаты.
3. «Сравни эти версии»: различия с привязкой к конкретным версиям; явно показать,
   если старое содержимое уже недоступно и сравнение невозможно.
4. «Собери отчёт по выбранным файлам»: предварительный список, бюджет, ход работы,
   сохранённый результат и ссылки на основания. Повторный запрос не создаёт копии
   исходников и повторный анализ неизменившихся файлов без необходимости.
5. «Предложи правки/переименование»: сначала план и предпросмотр; изменение оригинала
   возможно лишь отдельной разрешённой операцией с проверкой версии и прав.
6. «Что агент делал с папкой, что запомнил и сколько места занимает?»: раздельные
   история обращений/действий, история версий, выводы и управление хранением.

Критерий ценности — время до найденного/открытого оригинала и выполненного поручения,
а не число проиндексированных гигабайт или размер векторной базы.

## 3. Основное решение: originals-first, не «скопировать диск в Git»

### 3.1. Что хранить и где

Оригинал остаётся у пользователя/провайдера. Логически разделить:

| Слой | Состав | Политика |
| --- | --- | --- |
| Каталог | Идентичность файла, папка/путь, размер/type, observed version, права, freshness | Метаданные, не полная копия дерева байтов. Инкрементальное обновление. |
| Производный индекс | Нужный извлечённый текст/чанки, якоря, версия парсера, поисковый индекс | Восстанавливаемый, ограниченный бюджетом. Не хранить одновременно полный extracted text и полные дубли всех chunks без обоснования. |
| Знания/выводы | Краткий вывод, факты/неуверенность, ссылки на файл+версию+якорь, автор/модель/метод | Пользователь видит, исправляет, закрепляет или удаляет. Устаревшие основания инвалидируют актуальность, а не переписывают историю. |
| Журнал | Кто/когда/что открыл или изменил, operation ID, результат, version before/after | Компактные события и ссылки, не повтор содержимого файлов/промптов при каждом обращении. Отдельная retention/privacy policy. |
| Кэш байтов | Лишь недавно понадобившиеся исходники/превью | По умолчанию без постоянного зеркала: TTL/LRU, квота и явная очистка. |
| Результаты/снимки | Созданный отчёт, одобренный патч, явно закреплённая версия | Долговечность и размер видимы; не удаляются как обычный кэш. Пользователь выбирает место сохранения. |

Для cloud-пилота каталог/ledger остаются в PostgreSQL; закрытая служебная область
blob storage хранит только действительно нужные payloads. Для локального режима
каталог, извлечение, выводы и кэш по умолчанию остаются на выбранном устройстве;
локальное хранилище/поиск — отдельная реализация того же контракта, не копия
полного ledger в облако. Не переносить local_only-derived data в серверный PG/FTS.
Метаданные (включая имена, пути, хеши и поисковые запросы) тоже могут быть секретными.

Служебная папка агента — управляемая приватная область с понятным размером,
владельцем и версией формата. В пользовательской подключённой папке **ничего не
создавать автоматически**. Если нужна переносимая `.assistant/`, отдельное согласие:
не секреты, исключение из индексации/синхронизации, запрет рекурсивного поглощения
своих кэшей/отчётов, versioned manifest только для экспорта/восстановления.
Не делать PG + постоянно переписываемые JSON/Markdown-файлы двумя источниками истины.

### 3.2. Хеши, версии и дедупликация

- **File identity ≠ content hash.** Одинаковые байты у двух файлов не объединяют
  их пути, владельцев, ACL, версии или назначение. Identity — tenant, connection,
  разрешённый root и provider stable ID; path — меняемый атрибут. Если стабильного
  ID нет, переименование считается delete+create либо подтверждённой эвристикой,
  а не гарантированным сохранением идентичности.
- **ETag/version token ≠ SHA256.** Дешёвый stat/list/change cursor используется
  для freshness; хеш сырых байтов вычисляется потоково при необходимом чтении.
  Не скачивать весь диск только ради хеширования. Для провайдера без надёжного
  version token — bounded revalidation; mtime+size не доказательство неизменности.
- Хранить отдельно raw-byte hash, extracted-content hash и parser version.
  Один и тот же extraction переиспользовать только при совместимых версиях,
  правах и границе обработки. Ключ анализа включает версии входов, метод/модель,
  параметры и права, а не один SHA256.
- Контентно-адресуемое хранение (CAS) имеет смысл для реально сохранённых blobs:
  уникальность в пределах tenant + protection/key domain + representation/version
  + hash. Никакой глобальной межтенантной дедупликации, existence oracle или
  разделения local_only с cloud. При необходимости использовать внутренний
  keyed digest; raw hashes не публиковать без основания.
- Начать с дедупликации целых payloads и сжатия текста после измерения.
  Дельты — только для подходящего текста и только если дешевле compressed snapshot;
  bounded цепочка + периодический checkpoint + проверка reconstruction hash.
  Для PDF/DOCX/ZIP/фото двоичные дельты не включать по умолчанию: часто мало экономии,
  больше CPU/риска. Chunk-level CDC и embeddings — не обязательные компоненты MVP.
- **Хеш не восстанавливает файл.** Журнал версий без сохранённых байтов или
  доступной provider revision не является бэкапом. UI различает «версия известна»,
  «содержимое доступно», «восстановление доступно». Provider history может истечь.
- Не менять уже применённую0122 и её immutable snapshots. Для imported evidence
  переиспользовать content refs/derived index в новых моделях; если нужна адаптация
  DocumentRevision — additive migration/совместимый dual-read, не скрытая замена
  истории текстовых ревизий. Нативная revision провайдера и approval revision
  приложения — разные сущности, с явной связью.

## 4. Контракты данных и инфраструктура

Предварительные сущности; финальные имена/миграции уточнить в срезе1 после проверки
существующих manager/permission contracts. Не создавать generic giant JSON store.

1. `FileMount`: tenant, connection owner, device/root selector, фактические read/write
   grants, boundary, exclusions, quota/policy, cursor, last successful scan/error.
   Расшаривание личного подключения другим участникам — отдельный явный grant.
2. `FileObject`: mount+provider ID, parent, отображаемое имя/путь, type/size,
   current revision, deleted/unavailable marker; tenant-safe composite links.
3. `FileRevision`: observed native version, hash when known, observed_at,
   optional content ref, availability и provenance. Metadata-only observation
   не объявлять полным snapshot. Path change не требует новой копии байтов.
4. `DerivedArtifact`: input revision refs, representation/parser version,
   storage ref, size, retention, boundary, source ACL lineage; один canonical
   extracted payload, bounded chunks/anchors и поисковые проекции.
5. `FileInsight`: вывод/неуверенность, evidence refs, способ получения, scope
   personal/workspace с явным sharing, stale/verified/pinned state. Отделить
   пользовательские исправления от машинных выводов; сохранять основания.
6. `FileOperation` + связанные events: actor, task/job/request ID, typed action,
   selected objects/revisions, approval, idempotency key, outcome и receipt;
   журнал обращений может иметь более короткий срок/другой visibility.
7. `BlobRef/RetentionPin` — лишь для реально сохраняемых данных; учитывать
   ссылки insight/report/approval/hold. Физический blob сам по себе не выдаёт ACL.

Реиспользовать Job/AgentTask, locks/transactional admission, текущие budgets,
CSRF, secret vault и RBAC; не вводить Celery/Redis, отдельную vector DB или Git
server. Не писать файловые events в существующий `action_audit_events` с обходом
его CHECK constraints: либо reviewed extension allowlist, либо специализированный
ledger со сквозными correlation IDs. Логи не становятся источником разрешений.

Для managed cloud service — SQL metadata/FTS + приватная blob-area с атомарной
записью, fsync/rename или storage equivalent, integrity check, recovery незавершённых
записей. Нет public buckets/предсказуемых download URLs. Secrets не в manifest/URL.
Согласованность DB/blob после crash и повторного запуска проверяется отдельно.

## 5. Пользовательский путь в web

Сохранить текущую дизайн-систему и прямые маршруты. Не делать вторую независимую
копию «Базы знаний» и «Документов» или пункт меню для каждого провайдера.

### 5.1. Подключение и первое полезное действие

Settings → Connections остаётся единым местом подключения:
выбрать провайдера/устройство → авторизоваться безопасным способом → выбрать папку
→ увидеть read-only по умолчанию и границу обработки → preview объёма/поддержки
→ **Подключить выбранную папку** → progress с паузой/отменой → первый поиск.
Показывать отдельно «доступ подтверждён», «файлы перечислены», «часть проанализирована»,
«индекс обновлён». Save/auth не превращать в «всё синхронизировано».

Перед initial scan — исключения, лимиты, куда идут данные и цена анализа.
Сначала metadata-only; содержимое — по запросу или по отдельному выбору ограниченного
индекса. Источник без адаптера честно недоступен; отсутствие parser не скрывает файл:
его можно найти по имени/метаданным и открыть, но не обещать анализ содержимого.

### 5.2. Рабочая область и карточка файла

На существующих `/app/knowledge` и `/app/documents` предложить общий file catalog
и detail route (конкретные URL зафиксировать в срезе1):

- Быстрый поиск + список/дерево выбранной папки, breadcrumbs, фильтры по источнику,
  типу, дате, состоянию и избранному; server-side paging, keyboard navigation,
  mobile layout. Нельзя загружать всё содержимое всех файлов ради одного списка.
- Основная строка: имя, тип, понятный источник/папка, изменён/проверен, доступность.
  Основные действия: **Открыть оригинал**, **Предпросмотр**, **Спросить агента**.
  Хеш/ACL/внутренние ID — внутри «Технические сведения», не главный интерфейс.
- Detail: сводка и цитаты, **Оригинал / Выводы агента / История / Доступ и хранение**.
  Показать, где лежит оригинал, какая версия анализировалась и насколько свеж ответ.
- «Свидетельство» заменить понятным «Источник ответа» (сохранив P12-T06 DOM contract).
  «Локальная/корпоративная/облачная обработка» объяснять человеческим языком.
  Выбор в UI не меняет классификацию и не создаёт локальный execution route.
- Состояния: пустая папка; ничего не найдено; нет доступных записей; indexing;
  partially indexed; unsupported; encrypted/password-protected; source offline;
  reauth; revoked; moved/deleted; stale; quota exceeded; original unavailable.
  Не сообщать о существовании чужого файла через разные ответы/счётчики.
- Существующие snippets/revisions без FileObject не исчезают. Показывать legacy
  provenance и честно «Оригинал не привязан»; не превращать произвольный source_ref
  в доверенную ссылку и не пытаться автоматически угадать аккаунт/путь.

### 5.3. Безопасное открытие оригинала

Единый server-authorized resolver принимает opaque file ID, а не URL/путь клиента;
повторно проверяет tenant, actor, owner/share, root, текущий источник и версию.

- Cloud: provider-native authenticated web link без создания публичной share-link.
  URL только из reviewed provider resolver; allowlisted scheme/host, запрет token
  в query, open redirect, SSRF и произвольного `source_ref` как destination.
  Для нового окна noopener/noreferrer; краткоживущие ссылки не хранить постоянно.
- Если нет безопасной native ссылки — ограниченная авторизованная загрузка/proxy
  с повторной проверкой на download, безопасным filename/content-disposition,
  size/range/time budgets и запретом активного HTML/SVG в основном origin.
- Local: браузер сервера не может открыть произвольный путь на компьютере человека.
  Использовать явно paired device + одноразовый authenticated open request,
  повторную проверку canonical root/локального пользователя и подтверждение
  запуска приложения по политике. Не выдавать `file://`, absolute paths или
  произвольные custom-protocol команды из недоверенного содержимого.
- Устройство offline → понятное сообщение с восстановлением связи, а не фиктивная
  кнопка успеха. Открыть текущий оригинал и открыть сохранённую версию — разные
  действия; если provider не умеет revision deep-link, прямо показать ограничение.

## 6. Безопасность, команды и история

Cloud-провайдер и локальный агент реализуют один узкий capability contract:
list/stat/read/open-original; отдельно create-output, propose-patch и apply-approved.
Rename/move/delete/bulk-write не становятся разрешёнными из наличия read scope.

- Приватность персональная по умолчанию: tenant isolation недостаточно для двух
  участников одного workspace. На каждом list/search/preview/open/analysis/write
  проверять личного владельца подключения, явный share, текущие права файла/root.
  Фильтрация до retrieval/top-k/модельного запроса и на фоновых задачах; revocation
  закрывает кэш, snippets, insights, сессии, ссылки и очереди, не только новую sync.
- local_only распространяется на извлечённый текст, OCR, превью, hashes/paths,
  embeddings, выводы, telemetry и сами запросы по ним. Pairing/root permission
  не равны согласию на cloud. Пока end-to-end local route не проверен — сохранить
  текущий fail-closed, не разблокировать P12-T11 badge-based маршрутизацией.
- Локальный агент — outbound paired/revocable, ограниченная allowlist операций,
  canonical paths, traversal/symlink/hardlink escape и TOCTOU tests, device binding,
  отсутствие unrestricted shell/общего filesystem API. Файл не выполняется как код.
- Провайдеры: scopes отдельно read/write, encrypted owner-bound secrets, refresh,
  rate/Retry-After, partial paging, bounded bytes/time, credential revocation;
  endpoints/redirects/download hosts только по reviewed SSRF/network policy.
- Содержимое файла — недоверенные данные, не системные инструкции. Нельзя выдавать
  из файла права/скрывать подтверждение/передавать секреты/вызывать shell/менять root.
- Анализ: фиксировать inputs+versions, выбранный вывод/стоимость, parser limits,
  confidence и citation anchors; не сохранять цепочки рассуждений модели.
- Изменение: preview/diff → explicit approve → recheck permission+expected revision
  → conditional write → verify actual result → receipt. Approval связан с actor,
  tenant, bytes/patch/target/version и TTL; изменение плана/файла требует нового.
  Для бинарного Office MVP не обещает безопасный in-place edit: предложить патч/
  отдельный результат либо явный unsupported. Новая копия результата — намеренное
  действие пользователя, не автоматическое дублирование каждого исходника.
- Если у адаптера нет безопасного conditional replace — overwrite недоступен;
  новый output в явно выбранной папке возможен с collision policy. Provider timeout
  после записи → unknown/reconcile, не blind retry и не отчёт «готово» до проверки.
  Cancel после commit не обещает undo; undo — отдельная проверенная операция.
- История обращений ≠ история правок ≠ история диалога ≠ backup. Показывать кто,
  что, когда и результат; per-user journal по умолчанию не раскрывает другому
  участнику запросы/пути. Не логировать body, secrets и полные prompts автоматически.

## 7. Экономия места и жизненный цикл

1. Никакого фонового зеркала всех оригиналов и экспорта всех выводов рядом с ними.
   Metadata scan отдельно от read/extract; unchanged version не скачивать повторно.
   Повторный open/search оставляет компактный event, не новый snapshot.
2. Extraction cache по input hash + parser/representation + protection domain;
   small text → SQL FTS с фильтрами, bounded derived storage. Сначала измерить
   качество keyword/metadata retrieval; embeddings только при доказанной пользе.
3. UI «Хранение»: отдельно байты оригиналов у провайдера, локальный/серверный кэш,
   derived index, закреплённые результаты/версии, журнал. Показывать actual used,
   reclaimable, pins/hold и projected cost до массового анализа.
4. Настраиваемые явные budget/TTL для кэша, извлечений, previews, history и results;
   выбрать и задокументировать числовые defaults до реализации среза3. Без
   бесконечного default retention, без автоматического удаления pinned outputs.
5. «Очистить кэш» не удаляет оригиналы, выводы и нужные historical bytes.
   «Забыть вывод», «удалить индекс», «отключить папку», «удалить оригинал» —
   разные команды с разным эффектом и ясным подтверждением. Удаление originals
   в первом пилоте отключено. «Сохранить версию» честно увеличивает used storage.
6. Транзакционный GC: expiry + reachability/pins + leases/in-flight jobs;
   сначала dry-run, затем delayed delete, protection от races/retries/crash.
   Refcount не единственная гарантия. При delta chain нельзя удалить base,
   нужный закреплённой версии; compaction проверяет итоговый hash.
7. Revocation immediately denies reads; physical purge follows published SLA,
   including previews/index/insights and backup expiry. Holds оформляются явно;
   не обещать мгновенное физическое стирание из backup и не вечное хранение «аудита».
8. Export/restore: versioned manifest, permission/retention metadata и только
   явно выбранные сохранённые payloads; не secrets или скрытая копия диска.
   Проверка integrity/совместимости после restore. Зашифрованные backups индекса
   отделить от пользовательского ожидания backup оригиналов.

## 8. Пошаговый план реализации и границы срезов

P12-T12 — родительская задача; перед исполнением выделить срезы в отдельные
последовательные задачи/PR с unused IDs, не объявлять весь C5 одной готовностью.
Срезы ниже — порядок, не уже созданные дочерние карточки.

### Срез 1 — Зафиксировать пилот и контракты, без сетевых записей

- Согласовать один спросом подтверждённый провайдер/набор операций. Предложение:
  **Яндекс.Диск read-only, одна выбранная папка** для первого cloud-пилота; это
  рекомендация, не выбор владельца за него. Mail.ru/local — следующие адаптеры.
- Сверить официальные актуальные API/scopes/stable IDs/версии/native open/limits,
  условную запись и историю; записать таблицу implemented/planned/unsupported.
- Согласовать threat model, файл-identity/revision/extraction/insight/operation,
  route/data-evidence compatibility, permission sharing и retention defaults.
- Отдельно выбрать local-only deployment path: paired-agent storage/query protocol,
  реальное место исполнения model/parser и запрет cloud egress. Если нет доступной
  локальной модели, browsing/open могут работать локально, анализ честно недоступен.
- Exit: reviewed contracts + measurable budgets + список дочерних задач.
  [P8-T34](p8-t34.md) остаётся DEFERRED; не запускать non-social pilot без явного
  решения владельца о выборе и расписании/переносе его scope. План не меняет эту
  договорённость автоматически и не создаёт второй конкурирующий пилот.

### Срез 2 — Каталог и реальное открытие оригиналов (read-only)

- Additive schema/managers с tenant+owner/share/root guards, metadata-only adapter,
  folder picker, bounded initial paging, watermark/incremental scan.
- New/rename/delete observations, offline/reauth/partial handling. Отсутствие файла
  в одной неполной странице не равно удалению; tombstone только после надёжного
  provider event или законченного reconciliation. Resume не теряет/дублирует items.
- SQL paging/search, file detail, safe original resolver, empty/error states.
- Exit: обычный пользователь подключает выбранную папку, находит файл и открывает
  **оригинал**; в сервисе нет permanent mirror; честные unsupported capabilities.

### Срез 3 — Ограниченный анализ, компактный индекс и выводы

- Safe on-demand read/extraction для явно перечисленных форматов, sandboxes/limits,
  page/cell anchors, freshness и hashing во время чтения. Не ослаблять chat parser
  автоматически: его ограничения — отдельный контракт.
- Reusable derived cache/CAS, bounded FTS queries, insights+provenance и invalidation,
  storage accounting/TTL/GC dry-run, cache-cleaning UI.
- Existing evidence/chat projections получают file/revision lineage. Legacy0122
  rows живут дальше с честным отсутствием привязанного оригинала.
- Exit: повтор анализа неизменного файла переиспользует разрешённый результат;
  изменённый файл делает старые выводы stale; cache cleanup сохраняет originals.

### Срез 4 — Типизированные поручения, вывод результата и контролируемая запись

- Agent tools для selected-file search/read/analyze/propose/create-output; queued
  progress/cancel/budget и понятные receipts в чате и file detail.
- По умолчанию write-off. Для выбранного поддерживаемого формата/адаптера включить
  apply только после preview/approval, conditional version check и retry/reconcile.
- Append-only operation journal, compact access events, history UI и закрепление
  необходимых версий. Rollback оригинала только если доказана доступность bytes.
- Exit: read-only поручение и разрешённое создание отчёта имеют реальные результаты;
  conflict/timeout/revocation не превращаются в silent overwrite/duplicate output.

### Срез 5 — Локальный диск без cloud-утечки и расширение адаптеров

- Pairing/device lifecycle, selected roots, local ledger/search/extraction, safe
  original-open и policy-checked commands. Фоновая связь outbound, revoke device.
- Network-denial instrumentation доказывает, что local_only payloads и metadata
  не попадают в cloud logs/DB/model/telemetry. Проверить local index/cache deletion.
- Второй cloud adapter и новые форматы только после первого end-to-end пилота,
  каждый с отдельной capability/evidence матрицей. Не называть первую версию
  поддержкой «любых файлов»: любые имена можно каталогизировать в рамках политики,
  но анализ/редактирование — только реально реализованные типы/операции.
- Exit: файл на устройстве находится/открывается локально; недоступная модель
  не запускает cloud fallback; устройство offline и revoked честно обработаны.

### Срез 6 — Проверка полезности и закрытие родительской задачи

- Инструментированный storage/performance corpus и короткие пользовательские
  сценарии, documented supported matrix и помощь без терминов SHA/ACL/CAS.
- Миграционный rollback/restore, data lifecycle, observability без чувствительных
  данных; по каждому срезу сохранены точные SHA/команды/выводы и ограничения.
- Публичные claims перечисляют принятые срезы. Родитель закрывается только после
  согласованного end-to-end cloud и local scope либо явного уменьшения владельцем,
  а не потому, что добавлены таблицы или статическая UI-кнопка.
