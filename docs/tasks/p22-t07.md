## Deliverable

One canonical task contract, reachable three ways, so a manager, an operator and an agent act on the same identity with the same
rules: list/get, create/edit, plan preview, complete, confirmed delete, run-now with its receipt, available actions and pending
decisions. Legacy social-task and planner namespaces keep resolving through their own compatibility adapters without
reinterpreting payloads.

**Namespace decision.** The existing `/api/v1/tasks` is the social-monitoring (VK) task surface and stays untouched. The
canonical contract is a new `/api/v2/tasks` namespace; the CLI gets a `worktasks` group; agent tools get a `work_task_*` prefix.
This keeps three unrelated meanings of "task" apart and makes a wrong call fail closed instead of executing the wrong job.

## Operations

| Operation | API | CLI | Tool |
| --- | --- | --- | --- |
| list with filters and cursor | `GET /api/v2/tasks` | `worktasks list` | `work_task_list` |
| get one | `GET /api/v2/tasks/{id}` | `worktasks show <id>` | `work_task_get` |
| create | `POST /api/v2/tasks` | `worktasks create --title …` | `work_task_create` |
| edit with expected version | `PATCH /api/v2/tasks/{id}` | `worktasks edit <id> --json …` | `work_task_edit` |
| plan preview, no effects | `POST /api/v2/tasks/{id}/plan/preview` | `worktasks preview <id>` | `work_task_preview` |
| complete | `POST /api/v2/tasks/{id}/complete` | `worktasks complete <id>` | `work_task_complete` |
| delete preview | `POST /api/v2/tasks/{id}/delete/preview` | `worktasks delete <id> --preview` | `work_task_delete_preview` |
| confirmed delete | `POST /api/v2/tasks/{id}/delete` | `worktasks delete <id> --confirm <token>` | `work_task_delete` |
| run now, current published revision | `POST /api/v2/tasks/{id}/runs` + `Idempotency-Key` | `worktasks run <id>` | `work_task_run` |
| runs and receipts | `GET /api/v2/tasks/{id}/runs` | `worktasks runs <id>` | `work_task_runs` |
| available actions + decisions | `GET /api/v2/tasks/{id}/actions` | `worktasks actions <id>` | `work_task_actions` |
| decision preview | `POST /api/v2/tasks/{id}/decisions/preview` | `worktasks decide <id> --preview …` | `work_task_decision_preview` |
| decide | `POST /api/v2/tasks/{id}/decisions` | `worktasks decide <id> --confirm …` | `work_task_decide` |
| legacy URL → canonical task | `GET /api/v2/tasks/legacy/{namespace}/{id}` | `worktasks resolve <namespace> <id>` | `work_task_resolve_legacy` |

Run-now carries `Idempotency-Key`: admission binds the actor, the key and the (task, revision) fingerprint, so a replay returns
the first receipt with `replayed: true` and a different revision under the same key is a conflict. Edits, completion and
decisions carry the expected `version` instead; the remaining mutations accept the header for interface symmetry but have no
ledger-backed replay yet — that arrives with the T12 command ledger. Reads are tenant-scoped from the authenticated actor only:
no caller-supplied tenant or workspace overrides except the existing superuser surface, which keeps its own guard.

## Error codes

Statuses follow the business-router convention (`app/api/v1/conventions.py`), and every body is the shared `BusinessError`
envelope (`code`, `message`, `request_id`) with `X-Request-ID`: `403` rights refusal (no tenant scope, hidden field, boundary),
`404` absent or invisible task — one answer, no existence oracle, `409` stale version or a conflict (replayed key with a
different revision, busy run), `422` rejected plan or malformed page, `500` internal. Service refusal text never reaches the
body; a stale edit is told to refetch, not which field differed.

## Acceptance

One actor creates a plain note, adds a plan, previews it, runs the task and inspects the receipt through API, CLI and agent tool
against the same task identity; the preview leaves no `TaskRun` row. Rights, visibility, pending-decision rules and confirmation
match the services behind them: a hidden field cannot be injected, a stale version is refused, a replayed idempotency key returns
the first outcome instead of a second run. Legacy planner and social result requests still resolve, and a legacy URL yields its
canonical target. API, CLI and tool expose the same operation set — a parity test fails when one drifts.

## Risks and rollback

The new namespace is additive: no existing route changes behaviour, so rollback is deleting the router mount, the CLI group and
the tool registrations. The real risk is drift between the three surfaces, which the parity test exists to catch, and silently
reinterpreting a legacy payload — the adapters therefore resolve identity through `task_bindings` (T06) and translate nothing
else.
