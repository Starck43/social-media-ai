## Findings (non-blocking)

1. `valid_destination` silently caps `|chat_id|` at 2^52-1 (at most 13 digits
   after the `-100` prefix); the contract text says "canonical numeric
   channel IDs" without stating the cap. Channel bindings with longer IDs
   cannot be released through this capability. The owner must verify the
   rollout target channels fall inside the cap; document it in
   `docs/ACTION_ACTIVATION.md` or widen the limit deliberately.
2. `telegram_message._send` compares `claim_token_hash` with `!=` while
   `_finish` uses `secrets.compare_digest`. The token is server-generated and
   not caller-supplied, so this is consistency, not a vulnerability.

## Limitations

Certifies only this default-off code path under mocked Telegram I/O. It does
not certify bot posting rights in a real channel, live availability, or
production readiness. Live rollout requires the owner to pick the exact
bot/channel pair, verify posting rights and explicitly authorize a smoke
send; an environment flag or test approval is not permission to post.
UNKNOWN outcomes require explicit human reconciliation with Telegram.
