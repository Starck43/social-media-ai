# P20-T15 — Rebuild «Сегодня» as a work desk: day summary, work blocks and instruments

Registry: [ROADMAP](../../ROADMAP.md); parent: [P20](../phases/p20-proactive-assistant.md).

## Problem

[P20-T14](../archive/tasks/p20-t14.md) delivered a presentation layer only: shell chrome, mono
typography, radii and density. The three web mockups the owner supplied in `原型/`
(local, gitignored design folder; restored on 2026-11-19 after an accidental
deletion) describe a different **information architecture** for «Сегодня»: a
two-tier header with a live status strip, a day summary card, decision/plan/answer
blocks and a right-hand instrument column. None of that exists in the code today — a
`grep` for `Свежесть`, `Покрытие источников` and `Бюджет моделей` in
`app/web/templates` returns nothing — so the work-desk layout is currently
cosmetic.

This card owns the missing IA. The mockups are not tracked in git, so the
directions below plus the specification are the durable record; the files in
`原型/` are local reference material only.

## Goal

Turn «Сегодня» (`app/web/templates/web/dashboard.html` + the shell in `base.html`)
into the work-desk layout: everything above the fold answers "what needs me now",
and every value comes from an owning service, never from a literal.

## The three mockup directions (plain names)

The prototypes arrived as «Направление 1 · Брифинг», «Направление 2 · Пульт» and
«Направление 3 · Компаньон» — words that say nothing to a user. In the UI, the docs
and this card they are named by what the user gets:

| Old name | Plain name | What the user sees |
| --- | --- | --- |
| Брифинг | **«Сводка»** | one column: what happened, what needs me, what is planned |
| Пульт | **«Рабочий стол»** | the same facts, plus a live status strip and an instrument panel |
| Компаньон | **«Диалог»** | the same facts, arranged around the conversation with the assistant |

The old names survive only in git history; new UI copy uses the plain names.

`原型/` holds three HTML prototypes built on one and the same set of demo facts:
`01-сводка/social-media-ai-сводка.html`, `02-рабочий-стол/social-media-ai-рабочий-стол.html`,
`03-диалог/social-media-ai-диалог.html`.

Shared by all three: header with workspace and operator context, «Ждут решения»,
«По плану на сегодня», «Ждут ответа», «Рабочий контекст» with typed references
(Задача / Переписка / Контакт / Документ / Кейс), a chat surface with prompt chips
(«Когда будет дайджест?»), «Входящие», «Бюджет моделей» and a mobile bar.

| Direction | Structure | Only this direction has | Role in this card |
| --- | --- | --- | --- |
| 01 «Сводка» | single-column day summary: greeting «Доброе утро, Анна», «Ждут решения» as two verbatim proposals, «По плану на сегодня», «Ждут ответа», «Требует внимания», «Последние результаты», «Вкратце»; subnav «Мониторинг»; no icon rail | the «Вкратце» summary plus the «Требует внимания» and «Последние результаты» blocks | source of the summary requirements |
| 02 «Рабочий стол» | two-tier header with status strip (Пространство / Оператор / Модель / Ждут решения / Очередь / Бюджет 82% / Свежесть 08:45), day summary card headed «Два решения, три задачи, один источник в сбое» with a large queue number, three work blocks, right instrument column (Покрытие источников / Свежесть данных / Очередь / Бюджет моделей), icon rail with mono group labels (Ра / Кл / Зн / Мо / Си) | status strip, instrument column, icon rail | **canonical**: the specification below |
| 03 «Диалог» | chat-first: the same blocks, but «Чат с агентом» is the centre, decision rows collapse to one-line chips («Запустить «Отзывы на сезонное меню»», «Ответить Ольге Ким»), «Рабочий контекст» and «Входящие» sit beside it, least instrument chrome | the chat-centred reading order and chip-style decision rows | source of the compact decision rows |

The three differ in emphasis, not in facts: the same approvals, plan rows, inbox
items and instruments appear in each, so none of them needs a data source the
current services do not already own. This card implements the «Рабочий стол» structure
with the compact «Ждут решения» rows from «Диалог» and the «Вкратце» / «Требует
внимания» / «Последние результаты» summaries from «Сводка». Delivering a second
direction, or switching the canonical one, is an owner call rather than an
executor default.

## Specification — canonical «Рабочий стол» IA

1. **Status strip** under the navigation, one row of compact mono fields, each
   hidden when its owner has no value:

   | Field | Source of truth |
   | --- | --- |
   | Пространство | current tenant name from the session scope |
   | Оператор | signed-in user display name |
   | Модель | tenant LLM mode (personal vs platform) from the LLM settings service |
   | Ждут решения | pending approvals count (existing `approval_inbox.count_pending`) |
   | Очередь | runnable + running jobs for the tenant (jobs service) |
   | Бюджет | month-to-date model spend vs limit (`LLMBudgetDay` / `PersonalLLMBudgetDay` managers) |
   | Свежесть | timestamp of the newest collected item across active sources |

2. **Day summary card** at the top of the main column: weekday/date/time kicker, a
   one-sentence headline generated from the counted facts (e.g. "N решений,
   M задач, K источников в сбое"), a short paragraph of the counted facts, a large
   queue number, and two actions that already exist: open chat, triage inbox.
   The headline is composed in Python from the numbers, not free-form generated
   text; when a fact is unknown the sentence drops that clause.
3. **Three work blocks**, each with a count chip and a thin rule:
   - «Ждут решения» — pending approvals with the existing approve/reject actions
     and links into chat/inbox (reuse `approval_inbox`; no second queue).
   - «По плану на сегодня» — today's tasks from the existing Today projection,
     with a per-row status token (overdue / success / scheduled) already provided
     by that projection.
   - «Ждут ответа» — inbox items awaiting a reply, from the existing inbox
     service.
4. **Right instrument column**: «Покрытие источников» (per-source last-collected
   freshness and failure state), «Свежесть данных», «Очередь» (jobs with state and
   time), «Бюджет моделей» (bar + forecast note). Thin bars, no charts library.

## Full mockup application — instructions for implementers

This is the part an implementing agent needs. Every element of the three mockups
maps to one existing seam; nothing new is invented.

### Seams

- **View**: `app/web/dashboard.py::dashboard` is the only assembler of «Сегодня»
  context (today's keys: `today`, `recent_results`, `recent_tasks`, `pipeline`,
  `offer`, `next_step`, `can_open_chat`). New aggregation goes to a new module
  `app/web/home_facts.py` with `build_home_home(...) -> dict`, called once
  from that view; helpers stay pure so they can be unit-tested with fakes.
- **Shell slots**: `app/web/templates/web/base.html` already provides
  `{% block page_actions %}`, the page heading and
  `{% block right_panel %}` (rendered into the `#context-panel` dialog; currently
  unfilled on the dashboard). Add `{% block status_strip %}{% endblock %}`
  between `.shell-page` opening and `_flashes.html`, and fill `right_panel` from
  the dashboard instead of adding a second column mechanism.
- **Nav**: `app/web/templates/web/_shell_nav.html` — the icon rail is a CSS
  presentation of the same items, navigation data must not change.
- **Styles**: shell chrome, strip, rail and mobile bar in
  `app/static/css/shell.css`; home blocks and instruments in
  `app/static/css/dashboard.css`. The inline `<style>` in `dashboard.html` keeps
  only what it already owns (line clamping, density), new rules go to the CSS
  files.
- **Partials** (existing `_name.html` convention, all new):
  `_home_status_strip.html`, `_home_briefing.html`, `_home_decisions.html`,
  `_home_plan_today.html`, `_home_waiting_replies.html`,
  `_home_summaries.html`, `_home_instruments.html`.

### Element-by-element work

| Mockup element | Where | Rule | Done when |
| --- | --- | --- | --- |
| Two-tier header with status strip | `base.html` block + `_home_status_strip.html`, filled by the dashboard | one row of compact mono fields; a field with no value is omitted, never zero-filled | strip shows only counted facts, each with `data-home-field="<name>"` |
| Пространство / Оператор | existing `tenant` / `user` from the shell context | text only | renders the active workspace and signed-in user |
| Модель | LLM settings service (personal vs platform mode) | reads the tenant mode already resolved for `/app/chat` | one of the two modes, hidden when unresolved |
| Ждут решения | `app/services/commands/approval_inbox.py::count_pending` | reuse `request.state.pending_approvals_count` when present, no second count | equals the sidebar badge |
| Очередь | jobs service counts (runnable + running for the tenant) | bounded queries, no polling loop | number matches `/app/jobs` |
| Бюджет | `LLMBudgetDay` (`app/models/llm/llm_budget.py`) / `PersonalLLMBudgetDay` (`app/models/billing/ledger.py`) | spend vs limit of the current month; hidden when no limit is set | shows `NN%` or the absent state |
| Свежесть | newest `last_collected` across active sources | single max query | renders `HH:MM`, hidden with no sources |
| Day summary card | `_home_briefing.html` + `build_home_home` | kicker weekday/date/time, headline composed in Python from counts, short fact paragraph, large queue number, two actions (chat, inbox) that already exist | headline changes when a count changes; no literal numbers in the template |
| Ждут решения block | `_home_decisions.html` | compact one-line rows (from «Диалог») with the existing approve/reject actions and links into chat/inbox | one row per pending approval, no new queue |
| По плану на сегодня | `_home_plan_today.html` from the `today` snapshot | reuse the Today projection rows and their status tokens | block hidden when the projection is empty |
| Ждут ответа | `_home_waiting_replies.html` from the inbox service | rows link to the owning item | hidden when the inbox has nothing waiting |
| Вкратце / Требует внимания / Последние результаты | `_home_summaries.html` (from «Сводка») | «Вкратце» is composed from the same facts as the summary headline; «Требует внимания» lists failing sources and overdue rows; «Последние результаты» reuses `recent_results` | each sub-block hides independently |
| Instrument column | `right_panel` block + `_home_instruments.html` | thin bars only, no chart library; the mockups' «Покрытие источников», «Свежесть данных», «Очередь», «Бюджет моделей» | opens in the existing context panel and inline at ≥1200px |
| Icon rail with mono group labels | `_shell_nav.html` + `shell.css` (Ра / Кл / Зн / Мо / Си) | labels come from the existing section names, not hard-coded abbreviations in markup | rail at ≥1200px, drawer unchanged below |
| Mobile bar | `base.html` footer of `.shell-page` + `shell.css` | 4–5 existing destinations, 44 px targets, hidden from ≥640px | keyboard and screen-reader order matches visual order |
| Рабочий контекст (Задача / Переписка / Контакт / Документ / Кейс) | existing context panel + `js/context_panel.js` | a mapping of evidence rows already produced by the page, not a new store | panel shows the same rows with their type labels |

### Ordered increments

Each increment is independently reviewable and mergeable; the order is the
dependency order, not a preference.

1. **Console read-model** (`app/web/home_facts.py`) — approvals, queue, budget,
freshness, coverage, briefing facts; called from `dashboard.py`; unit tests with
fake managers only, no template change. *Done when* the view passes `home_facts`
into the template and nothing visible changes yet.
2. **Shell**: `status_strip` block, strip partial, icon rail, mobile bar
(`base.html`, `_shell_nav.html`, `shell.css`). *Done when* the strip renders only
with real values, rail/drawer keep keyboard order, no other page regresses.
3. **Home blocks**: day summary card plus the three work blocks
(`dashboard.html`, `_home_briefing.html`, `_home_decisions.html`,
`_home_plan_today.html`, `_home_waiting_replies.html`). *Done when* each
block hides when its owner returns nothing.
4. **Summaries and instruments**: `_home_summaries.html`,
`_home_instruments.html`, `right_panel` fill, `dashboard.css`. *Done when* the
context panel opens from the heading button and inline at ≥1200px.
5. **Responsive and accessibility pass**: 1440 / 768 / 390 px measurements,
focus order, `aria-label` on every count, no horizontal scroll. *Done when*
screenshots exist for all three widths and remaining gaps are named.

### Parallel work rules

- Increment 1 lands first; 3 and 4 consume its dict and must not add queries.
- Increment 2 touches only `base.html`, `_shell_nav.html`, `shell.css`; 3–4 touch
only the dashboard templates and `dashboard.css`, so two agents can work in
parallel without touching the same file.
- Nobody edits `dashboard.html` inline styles beyond removing the rules moved to
`dashboard.css`, and nobody adds a fourth CSS file.

### Working with the mockups

The three files in `原型/` open directly in a browser (no build step) and are the
side-by-side reference at 1440 px. Their content is demo data (Анна, Ольга Ким,
«Отзывы на сезонное меню»): copy the structure, never the literals — every
name and number on «Сегодня» must come from the owning service. When a mockup
element has no data behind it, the element is dropped and the gap is named in the
PR rather than filled with a placeholder.

## Scope

`app/web/templates/web/dashboard.html`, `app/web/templates/web/base.html` (strip
slot only), one dashboard read-model/aggregation module, one CSS file using the
existing variables (`--color-*`, `--ui-accent*`, `--cn-*`). Tests under
`tests/web/` and `tests/unit_web/`.

Also in scope, from the other two directions: compact one-line decision rows
(«Диалог») and the «Вкратце» / «Требует внимания» / «Последние результаты»
summaries («Сводка»), all derivable from the same reads.

Out of scope: per-page redesigns beyond «Сегодня», a second delivered direction
(«Сводка» or «Диалог» as an alternative home), new providers, new tables,
background jobs, provider spend, mobile-specific rework beyond keeping the
current responsive behaviour.

## Boundaries and default decisions

- Presentation-only values must be honest: a block with no data is hidden (no
  zero-filled placeholders, no invented counters, no demo numbers). This card's
  default is the owner-approved «Рабочий стол» direction; the other two mockups are
  emphasis variants of the same facts and need no extra data work.
- Reuse the owning services (approval inbox, jobs, budget managers, source
  registry, Today projection). No second ledger, queue, notification sender or
  cache table; derive counts at read time with bounded queries.
- Every colour stays on existing variables; no new palette values.
- No migration, no public schema change, no provider call, no deployment.
- The strip and columns must keep the current keyboard/ARIA behaviour; counts
  carry accessible labels.

## Acceptance and checks

1. `python -m scripts.ci.checks` and `python -m scripts.ci.run_offline` exit 0 on
   the branch head of every increment.
2. `pytest tests/web tests/unit_web` green on the branch head, including new
   tests that assert one block per source of truth and that a block disappears
   when its owner returns nothing (no fabricated counters).
3. A direct Jinja compile pass over `app/web/templates/web/*.html`.
4. Browser check of «Сегодня» at 1440, 768 and 390 px widths on a local runtime;
   screenshots attached to the PR, with any remaining gap to the mockups named
   explicitly rather than claimed as matching.

## Rollback

or schema changes remain.
