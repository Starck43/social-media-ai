## Scope

`OneCQueryAnswerService.answer` accepts `history_id`: a continuation rebuilds the actor- and tenant-scoped stored plan (`history.load_plan` → `plan_from_json`), refuses a row that belongs to another connection, re-validates the plan through `build_odata_query_target` against the connection's allowlist and `metadata_sha256` pin, attaches the client's `page_token` to that plan and never calls the planner. `POST /api/v1/integrations/1c/query` accepts `history_id` next to `page_token` and makes `question` optional (`question_required` when neither is given). The continuation reuses the stored history row instead of writing a duplicate. No migration, no schema change, nothing in `public`.

## Boundary review

The planner stays proposal-only and the stored plan is not trusted either: it is re-validated against the live `$metadata`, the administrator allowlist and the connection's metadata pin before execution, and the token stays fingerprint-bound, so a token of another plan is still `invalid_page_token`. Independently probed against the **real** repository (the task's own tests use in-memory fakes) on the shared `test_schema` with synthetic rows, cleaned afterwards — all three refusals happen before any provider call:

- another actor of the same workspace → `history_not_found`, nothing executed;
- another tenant → `history_not_found`, nothing executed;
- a stored row of another connection → `history_not_found`, nothing executed.

The connection itself is still authorized per call (`_authorize(require_source_view=True)`, `verified`/`odata_standard`, approved host, `metadata_sha256` pin), the transport stays read-only and budget-bounded, and the actor scope of `load_plan` was already proven in the accepted T03 database suite.

## Findings

**F1 of the T03 audit — closed.** The continuation no longer re-plans, so a second page is reachable regardless of how the model would describe the same question; the token binds to the stored plan's own fingerprint.

**N1 (low, ordering) — the catalog is fetched before the stored plan is loaded.** `answer()` calls `fetch_metadata_catalog` before the `history_id` branch, so a continuation with a foreign `history_id` still spends one provider request and one budget token before being refused. No boundary is crossed (the actor is authorized for that connection and its metadata anyway), but the order is worth inverting when the catalog cache of [P17-T08](p17-t08.md) lands — tracked as [P17-T09](../tasks/p17-t09.md).

**N2 (low, contract) — `history_id` and `question` together are ambiguous.** The stored plan wins and the supplied question is silently ignored. Recommend refusing the combination or documenting the precedence in the API reference.

**N3 (info) — the reused history row keeps the first page's metrics.** `row_count` and `duration_ms` describe page 1; the continuation does not overwrite them. No duplicate row is written.

Carried forward and still open from the T03 audit: F2 (positional DTD guard — now reachable), F3 (`mark_exported` dead code), F4 (float guard on the JSON path), F5 (API omits `chart`/`truncated`) in P17-T07 — since closed on 2026-11-12 by the [P17-T07 audit](p17-t07.md); F6 (catalog cache) and F7 (unused history statuses) in [P17-T08 audit](p17-t08.md).
