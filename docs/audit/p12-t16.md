# P12-T16 audit — Personal source ownership, auth preflight and actionable authorisation notices

**Verdict: ACCEPTED and merged.**
Candidate: `cebd033e` merged into `dev` as `1b470838` (PR [#312](https://github.com/Starck43/social-media-ai/pull/312)).
Acceptance date: 2026-11-02. Owner dialogue: local session, 2026-11-02.

The task replaced the "collect with the workspace owner's token" default with
per-member ownership, and turned an unauthorised source from a silent failure into
a narrow-but-real collection with an in-place fix.

## Delivered

- `sources.owner_user_id` (nullable, FK `users.id` `ON DELETE SET NULL`, indexed);
  no backfill in the migration, so an ownerless source stays ownerless rather than
  being handed to an arbitrary person.
- `resolve_source_owner`: explicit `params.token_owner` (validated as an active
  member) → recorded owner → `None`. No workspace-owner fallback, membership
  re-validated on every run.
- `SOURCE_AUTH_REQUIRED` notification enum member, added explicitly in the
  migration because Alembic does not autogenerate enum values.
- An unauthorised `mode=auto` VK source collects on L1 and reports
  `narrowed_access`; the run modal groups it into `narrowed_platforms` and offers
  the authorisation link inline.

## Migration on `public`

`0123` was applied after a backup
(`social_manager_public_pre_0123_20261102T175620Z.dump`, SHA-256 `9c9f436e7a0f…40e274`).
Revision `0122 → 0123`; column, FK (`confdeltype='n'`), index and enum label all
present; 17 pre-existing sources intact. All 17 were then set to `owner_user_id = 2`
(`starck`) by explicit owner instruction — the workspace holds only two members and
ownership of the individual sources could not be inferred.

The task was blocked at first because the page queried `owner_user_id` before the
migration had been applied to `public`; the apply above resolved it.
