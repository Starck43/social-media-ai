**Acceptance fix `781010bf`.** A task created without a description stores `NULL`,
while `TaskOut.description` is a string field inherited from `TaskCreate`, so
`_projection()` raised `ValidationError` on every `create`/`get`/`list`; five of
six DB scenarios failed on exactly that. `_projection()` now returns `""`, an
empty description is stored as `NULL` rather than a ciphertext of nothing, and
`description_encrypted` is nullable in the model and in `0140`. The scenario that
originally asserted all three encrypted columns carry ciphertext now asserts the
empty description is `NULL`; the code was not bent to the test.

## P15-T09

Executor is Codex; the owner approved the matrix in PR #417. The auditor answered
the scoped question on PR #421 (comment 6660060082): **PASS on both counts**.

- Presets: owner `VIEW UPDATE CONFIGURE`, admin the same, manager `VIEW UPDATE`, analyst `VIEW`, viewer `VIEW`. Resource declares `VIEW UPDATE CONFIGURE` with no `CREATE`/`DELETE`.
- `UPDATE` does not grant `APPROVE`: `approve` is not among the resource's actions, so `has_permission`, the codename lookup and `member_decision` all fail closed.
- `pytest tests/security/test_access_policy.py -q` on `test_schema` → 80 passed. The branch also turns the pre-existing `dev` red `test_migration_catalog_and_presets_match_runtime_without_database` green by declaring the frozen post-0096 resources explicitly.

**Recorded design gap, not this task's scope.** `ActionType` has no `APPROVE`
value, and the existing decision endpoint (`app/web/actions.py`) gates approval
on `VIEW + UPDATE` of the agent-action resource. When the outbox gains storage
and the D14 approval flow (P15-T05), approval must be gated on `CONFIGURE`
explicitly rather than inherited from `UPDATE`.
