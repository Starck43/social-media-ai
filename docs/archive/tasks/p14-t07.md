# P14-T07 — Bitrix24 as a global application with tenant portal settings

Owner decision 2026-11-04, superseding the deployment-credential half of
[D2](../../audit/q-18-owner-decisions.md): the Bitrix24 OAuth client secret must not
travel in environment configuration. The accepted [P14-T01 record](../../audit/p13-t04-p14-t04-business-crm.md)
resolved `client_id` / `client_secret` from `settings` through
`OAuthMethod.client_config_keys`, which only works when the whole deployment hosts
one application.

## Contract

1. Bitrix24 is registered as a **global application**, once, outside this product.
   Portal owners install it and the portal then issues its own tokens to us.
2. The application credentials (`client_id`, `client_secret`) live **outside both
   environment configuration and the source tree**: in a secret store the operator
   controls, or in an operator-supplied file whose path is the only thing a
   deployment knows. The product never commits, logs, or renders the secret.
3. Per-portal settings — the portal domain, the install state and everything after
   authorization — stay **tenant-scoped in the database**, under the P13-T02
   encryption contract, not in deployment settings.
4. Absent or unreadable credentials fail closed with a distinct, actionable error
   (`bitrix_credentials_unavailable`), never a silent fallback to environment
   variables.
5. Nothing about the secret reaches the browser: no form field, no template
   variable, no API response field.

## Out of scope

- Changing how portal access tokens and refresh tokens are stored — that contract
  is already accepted under P13-T08 and stays.
- The Bitrix24 channel integration (`P15-T01`).

## Doubt and rollback

A secret store is an infrastructure choice and is left to the operator; the code
must work with an operator-supplied secret reference either way. Rollback: keeping
`client_config_keys` resolvable from deployment settings stays supported until the
operator's store is in place, so the change can be reverted without a migration.
