## Why not accepted

Four independent defects make the delivered storage layer unusable, and each one is
visible on the first real database contact. The PR's own deferred list contains exactly
the scenarios that would have found them; the 24 green tests use a fake store.

| ID | Severity | Summary |
|---|---|---|
| F-1 | blocking | Migration cannot emit DDL: `CheckConstraint`/`UniqueConstraint` receive `schema=`, `alembic upgrade --sql` exits 1 (`TypeError … got 'schema'`). The repo test bootstrap then refuses to run with these models. |
| F-2 | blocking | Reclaim statement uses `UPDATE … LIMIT`, invalid in PostgreSQL (`syntax error at or near "LIMIT"`); it is the first statement of every acquire. |
| F-3 | blocking | Bucket seed binds one parameter to `capacity_units bigint` and `available_units numeric` → `inconsistent types deduced for parameter $5`. |
| F-4 | blocking | The identity check runs after the attempt's own `ON CONFLICT DO NOTHING` insert, so every fresh dispatch raises `RateStoreUnavailable("dispatch identity already in flight")`; `acquire` can never succeed. |
| F-5 | medium | Without `credential_ref` (allowed for any non-platform funding class) the `upstream` pool buckets are not built at all: provider RPM/TPM becomes a per-scope fairness cap instead of the shared pool quota. |
| F-6 | medium | No database evidence for `PostgresRateStore`: no upgrade/downgrade cycle, no two-session ceiling, no Retry-After floor run, no reclaim run. The acceptance bullets that depend on them are unverified. |
| F-7 | minor | 408 (`Request Timeout`) and 529 classify as permanent, so a real timeout never raises the floor. |
| F-8 | minor | `RateAcquirer.acquire` converts `CancelledError` from its own bounded sleep into `RateDenied`; an invalid dispatch id is reported as `RateDenied(0.0)` without a reason code. |

## What should be kept

Bucket/lease model, `COALESCE(model_family, '')` identity, version-free credential pool
identity, `blocked_until` as a floor with `available_units = 0` at block time, the written
lock order, fail-closed store handling in `RateAcquirer`, and the dormant seam wiring that
populates only `rate` while strict mode keeps denying on the other foundations.

## Resume conditions

1. F-1 fixed and an upgrade → downgrade → upgrade cycle green on an isolated schema.
2. F-2, F-3, F-4 fixed, each covered by a real-schema test (capacity denial, two-session
   concurrency ceiling, Retry-After floor, expired-lease reclaim).
3. F-5 decided and the choice recorded (fail closed without a credential ref, or a derived
   pool identity).
4. F-7/F-8 handled or explicitly deferred with a reason.
5. Row stays `IN_PROGRESS`, PR stays draft; re-request audit against this list.
