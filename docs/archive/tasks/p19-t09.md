# P19-T09 — `retrieval.py` ACL/boundary predicate contradicts its own contract

## Problem

`app/services/knowledge/retrieval.py` gates snippets by data boundary in two places, and both
predicates keep the **more sensitive** item and drop the safer one — the opposite of the docstring
and of every other boundary filter in the package.

```python
# filter_snippets_by_acl  (line 94)
if snippet_level is None or snippet_level < max_level:
    continue
```

`BOUNDARY_LEVELS` is `local_only=1, company=2, cloud=3`. With the documented call
`allowed_boundary="cloud"` (level 3), every snippet below level 3 — i.e. `local_only` and
`company` — is skipped, and only `cloud` snippets survive. The docstring two lines above says:

> Snippets exceeding allowed_boundary are strictly excluded (e.g. 'local_only' cannot leak
> to 'cloud' queries).

Read literally the docstring describes `snippet_level <= max_level` (an inclusive ceiling, the
reading `DocumentSearchService` implements). `assemble_llm_citations_context` (line 146) repeats the
same `>=` shape.

Why this matters beyond wording: a `local_only` workspace calling with the documented default
receives nothing, while a `cloud` caller receives cloud items — the filter is not a ceiling, it is an
equality-plus-floor. If a future caller passes `allowed_boundary="local_only"` expecting "local data
only", it gets *all three* boundaries.

The package the P19-T07 tests pinned the code as written; the asserted behaviour now
encodes the current predicate, so a fix must update those tests deliberately, not by accident.

## Resolution (2026-11-11, executor)

**Option B, taken as the safe default; A rejected on evidence.** The card's premise for A — that
`DocumentSearchService` implements an inclusive ceiling — is false. The ORM destination table
`app/models/managers/knowledge_manager.py:11` is documented as *destination clearance*:

```python
# Destination clearance: local processing can read all three classes, company
# processing cannot read local-only, external/cloud processing only reads cloud.
BOUNDARIES = {"local_only": ("local_only", "company", "cloud"),
              "company": ("company", "cloud"),
              "cloud": ("cloud",)}
```

`filter_snippets_by_acl` agrees with it exactly, so the shipped predicate is the shared convention
and only the wording was wrong. A would have inverted the security direction: every default
`allowed_boundary="cloud"` caller — including `assemble_llm_citations_context`, whose blocks go into a
cloud LLM prompt — would start to receive `company` and `local_only` evidence, and nothing in the
package enforces the separate transport boundary that A's docstring merely promises. That is the
`local_only` cloud-transit constraint in [BUSINESS_MODULES](../../product/BUSINESS_MODULES.md), so it is not an
executor's call.

The fix therefore keeps the behaviour and removes the contradiction: one shared predicate
(`_meets_required_clearance`) used by both gates, both docstrings restating `allowed_boundary` as the
clearance the destination requires, `assemble_llm_citations_context` normalised the same way as the
filter (it now lowercases/strips, so `"LOCAL_ONLY"` no longer silently excludes everything), and tests
that pin retrieval to the ORM destination table.

Rollback: revert the one commit; it changes no behaviour, no schema and no data.

### Superseded options (kept for the record)

- **A (recommended):** treat `allowed_boundary` as an inclusive ceiling — `snippet_level <= max_level`
  in both functions, matching the docstring and `DocumentSearchService`. `cloud` callers then get all
  boundaries they are allowed to see; `local_only` callers get only local data. Requires updating the
  P19-T07 tests that pin the current result.
- **B:** keep the predicate and fix the docstring to say "only snippets at or above the requested
  boundary are returned". No behaviour change, no test churn, but callers keep the surprising
  semantics.

Reverse either way by reverting the one-hunk change plus its test edits.
