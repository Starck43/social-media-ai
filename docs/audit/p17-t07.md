## Scope

Four hardening follow-ups, no change to the delivered query contract or its authorization:

- **F2** (`ed5aeba9`, separate small commit touching the accepted P17-T02 file, as the card required): `_refuse_unsafe_xml` in `app/services/onec/metadata.py` runs a real expat pass with `StartDoctypeDeclHandler`, `EntityDeclHandler`, `UnparsedEntityDeclHandler`, `ExternalEntityRefHandler` and a stylesheet-PI handler, so a DTD or `<?xml-stylesheet?>` is refused at whatever offset it appears; the positional first-8192-character scan is gone. A top-level `<!ENTITY` is refused by a full-text pre-check because expat reports that shape as malformed before any handler fires.
- **F3** (`15a81ead`): `export(history_id=…)` calls `history.mark_exported` and returns the same row id; no duplicate history row is written. Exporting a fresh question keeps the record-a-new-row path.

- **F5** (`8fef1310`): `QueryOutput` of `POST /api/v1/integrations/1c/query` carries `chart: [{label, value}]` and `truncated`, matching the chat tool; the empty-answer path returns `chart=[]`, `truncated=False`.

## Boundary review

- **F2 fails closed in both directions.** A payload that trips a handler → `unsafe_xml_forbidden`; a payload expat calls malformed falls through to the structural `ET.fromstring`, which rejects it as `invalid_metadata_xml`. Since ElementTree parses with expat too, there is no well-formedness gap through which a DTD could slip past the guard into a catalog. Fixed codes only, no payload echo. The full-text `<!ENTITY` pre-check can false-positive on a benign comment containing that literal — fail-closed direction, acceptable for 1C `$metadata`.
- **F3 marks only after every validation passed:** connection-mismatch refusal (`stored_plan_connection_mismatch`, proven by the new test with an empty `marked` list), plan re-validation against live metadata and allowlist, successful rendering — and `mark_exported` itself re-checks tenant/actor row ownership and `require_source_view` authorization at execution.
- **F4** leaves the Mapping path's typed float refusal (T03) intact and closes the JSON-text gap with tests on both a filter value and `top`.
- **F5** types match `OneCResultTable` (`chart: tuple[tuple[str, str], ...]`, `truncated: bool`). The chat tool ORs its own display row limit into `truncated`; that is chat-pagination specific and does not apply to the API, which returns the full row set — informational, no action.
- Planner stays proposal-only, typed allowlist validation and the read-only budgeted transport untouched, no authorization behaviour changed. `parse_plan_draft`'s explicit `except OneCNaturalLanguageError: raise` is defensive (the class is not a subclass of the caught tuple) — harmless.
