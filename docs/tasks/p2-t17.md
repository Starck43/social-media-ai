# P2-T17 — User-level tariffs, module entitlements and shared token allowances

Registry: [ROADMAP](../../ROADMAP.md#p2); parent: [P2](../phases/p2-usage-spend.md).

## Goal and predecessors

Implement one service tariff per user, shared across that user's owned workspaces.
Tariff definitions configure enabled product modules, the maximum number of owned
workspaces and finite or explicitly unlimited LLM token allowances. Platform model
availability is configured by [P21-T13](p21-t13.md); allowance reservation and
settlement belong to [P21-T15](p21-t15.md) / [P21-T16](p21-t16.md).

Consume the accepted [entitlement foundation](../platform/ENTITLEMENTS.md) and
[subscription configuration](../platform/SUBSCRIPTIONS.md), not another capability
engine or checkout provider. This task owns the plan-holder/policy contract that
P21-T12 can specify before wiring it. Tariff storage can be delivered with LLM
execution disabled; it does not depend on completed P21 runtime work. Checkout,
real prices, automatic renewals and production activation are separate assignments.
[P2-T08](p2-t08.md) corporate billing remains deferred.

## Owner decision — 2026-11-13

Source: OpenCode session `ses_e2fa3690affea2bSCgS5dlSVmg`, owner assignment and
explicit answer **models of the workspace owner** to the invitation question.

- The subscription subject is the user, not the workspace or a membership role.
  All owned workspaces share that user's tariff and allowance pool; creating or
  switching workspaces never multiplies or resets an allowance.
- Enabled modules include configurable ERP, CRM, documents, social analysis and
  other registered domains. These are packaging targets, not assertions that every
  module is implemented. Product module grants and model operation capabilities
  are different concepts.
- A workspace is bound to a governing owner/plan holder. Invited members execute
  within that owner's enabled functionality using the owner's configured platform
  or personal models, intersected with their own workspace/object permissions.
  Their own tariff/catalog neither expands nor replaces the host's rights.
- Any invited role, including a broad administrator role, grants no authority to
  change the host's tariff, catalog/providers/keys, models or model defaults.
  Owner LLM configuration and billing are account-level operations, not workspace
  RBAC. Invitees can manage their own account/catalog in their own context.
- Membership alone does not authorize charging or decrypting the owner's BYOK.
  Explicit owner consent binds delegated model use to the workspace/task scope;
  execution resolves the key internally and never returns it to the invitee.

## Proposed persistence contract

Publish a final field/consumer/constraint mapping before writing migrations. These
are target relations, not current schema; do not impose a fixed table count.

| Responsibility | Target storage and invariants |
| --- | --- |
| Configurable tariff definitions | Versioned plan policy keyed by validated plan code. Initially reuse the existing plan set; one policy owns module/resource/allowance packaging. Paid offer amount/currency remain a separate immutable checkout snapshot. |
| User entitlement | `user_service_plans`: unique `user_id` FK, plan/policy version, active state and aware expiry. Roles never select its subject; no per-workspace subscription copies. Preserve old policy versions referenced by history. |
| Workspace sponsorship | `tenants.plan_holder_user_id`: verified user FK with restrictive deletion. Resolve ambiguous/multiple legacy owners explicitly; do not infer the holder from the current actor or an arbitrary owner-role member. Ownership transfer is a separate owner-approved lifecycle. |
| Module grants | Reuse the composed namespaced capability registry and decision engine. Configure supported module keys/grants in the authoritative policy; unknown or unavailable capabilities fail closed. Do not hardcode a second ERP/CRM list in LLM tables. |
| Owned-workspace limit | Policy `max_owned_workspaces`: nonnegative integer or explicit unlimited. Count creations/ownership, not invited memberships. Atomic enforcement locks the plan-holder scope, not an individual workspace. Deployment ceilings remain independent. |
| LLM token allowance definition | Versioned policy: unit/counting rule, period definition and `token_limit` as nonnegative BIGINT or NULL meaning explicitly unlimited. Zero denies token use; missing policy/row is not unlimited. It is not USD or provider TPM. |
| Allowance balance | Owner/period/pool unique balance with nonnegative BIGINT `reserved_tokens` and `used_tokens`, policy version and unresolved-use evidence. Workspace and actor are attribution only, not separate balances. P21-T15 owns atomic reservation by dispatch identity; P21-T16 owns settlement/reconciliation. |

Do not use `tenants.daily_cost_limit`, `entitlement_usage` or monetary
`llm_budget_days` as a token ledger. Existing capability usage counts admissions,
not LLM tokens. Workspace USD ceilings can remain a stricter independent guard;
they do not define subscriber token entitlement. Personal USD accounting retains
its accepted payer/consent ledger. No duplicate ledger for the same economic event.

## Holder and policy interface — stage 1 deliverable for P21-T12

### Subject and sponsorship

The subscription subject is the user. A workspace does not own a tariff; it is
**sponsored** by exactly one holder user.

| Workspace ownership is derived, not stored: `TenantUser.role_id` → `workspace_roles.codename = 'owner'` | `app/models/tenancy/tenant_user.py:54-72`, `app/models/tenancy/workspace_role.py:31-34` |

Consequences accepted for this task: a new `tenants.plan_holder_user_id`
(user FK, restrictive deletion, nullable only until backfill completes) becomes
the single sponsorship authority; the derived owner role stays as a workspace
permission fact and stops being a billing authority. The backfill must resolve
multiple owner memberships explicitly — never by first/highest role, never by the
current actor — and must record the resolution, because the fixture proves such
rows exist.

### Resolution order (server-side, fail closed)

Every consumer resolves the holder in this order and stops at the first missing
or conflicting fact. No step is influenced by request payload, query string or a
client-supplied model/user/tenant id.

1. Authenticated actor (platform session) and its workspace membership.
2. Workspace sponsorship → `plan_holder_user_id` (verified user, not the actor).
3. The holder's active user plan: plan code, policy version, expiry.
4. Module grants for the required capability key, from that plan's policy,
   through the accepted capability catalog (`app/services/tenancy/plan_catalog.py`,
   contract in `docs/platform/ENTITLEMENTS.md:25-39`). Unknown key or unknown
   plan denies.
5. Token allowance policy for the holder (definition below); consumption and
   reservation are P21-T15's job, this task only supplies the policy.
6. Funding class and credential custody (personal/BYOK ownership, managed ref) —
   P21-T11 and P21-T13 supply the fields; this task supplies the holder identity
   they are bound to.
7. Delegated-use consent version for host-sponsored invitee calls — **not yet
   persisted**; recorded as gap G7 below.

An invited member therefore executes inside the holder's enabled functionality
and the holder's configured models, intersected with the member's own
workspace/object permissions. The member's own plan, if any, never widens the
host's rights.

### Holder-level management is account-scoped

Tariff, module packaging, catalog, providers, keys, model defaults and
allowance settings are account-level operations of the holder user. No
workspace role grants them — including the broad `admin` role, which today
carries the same grants as `owner` (`app/core/access_catalog.py:178`).
Enforcement is therefore by account ownership, not by role comparison. The
concrete gates this task owns:

- `POST /plan` in `app/web/settings.py:948-1005` is a workspace route whose
  superuser check at line 918 is dead code (`if user is None or not False:`), so
  the continuation verified it currently rejects every plan write. It must become
  holder-account scoped (or move to the account surface).
- Admin packaging surfaces (`app/admin/view_modules/users.py:279-375`) keep the
  platform-grant behaviour for superuser-curated packaging, which is a platform
  control and not a workspace permission.
- The personal catalog remains owner-scoped through
  `app/core/personal_catalog_context.py:9-19`; using a configured model is not
  CRUD and never grants management.

### Module grants

One authoritative definition lives in the plan policy of this task; the
capability registry and decision engine stay as accepted in
`docs/platform/ENTITLEMENTS.md`. `tenants.plan_limits()` and
`PLAN_LIMITS["model_types"]` remain compatibility inputs until their consumers
migrate. Model/capability availability per plan (`plan_model_grants`) is
P21-T13's relation and consumes the plan code and policy version defined here.
No second module list is introduced in LLM tables.

### Token allowance policy (definition only)

The policy is versioned per plan code and holds the unit/counting rule, the
period definition and `token_limit` as a nonnegative BIGINT, where NULL means
explicitly unlimited, `0` denies token use, and a missing policy or row is
**not** unlimited — it denies allowance-governed dispatch. Tokens are the
holder's shared allowance across owned workspaces and host-sponsored invitee
activity; workspace and actor are attribution, not separate pools. The balance
rows, atomic reservation and settlement belong to P21-T15/P21-T16 and are not
defined here.

Counting rule, period boundary, package sizes and overage are owner decisions
still open below; until they are answered, only the storage and interface work
proceeds and no allowance-governed dispatch is activated.

### Engineering gaps found while publishing this interface

These are executor findings, not owner questions.

- G1 — no sponsorship column, and existing workspaces may have several owner
  memberships: the backfill needs an explicit resolution rule and its own
  evidence; it cannot be derived from "the first owner".
- G2 — the plan-write superuser gate is dead code (`app/web/settings.py:971`).
  Continuation source verification: `user is None or not False` is always true,
  so the current route denies every write; it does not grant member writes.
- G3 — `owner` and `admin` share one grant set (`app/core/access_catalog.py:178`),
  so holder-level denial must be account-scoped rather than role-scoped.
- G4 — a restrictive holder FK collides with `UserManager.delete_user`
  (`app/models/managers/user_manager.py:178-203`), which has no pre-check; the
  delete path would surface as an integrity error. Transfer before delete is a
  separate owner-approved lifecycle.
- G5 — workspace creation is not transactional
  (`app/web/auth.py:47-67`: tenant insert, then owner membership), so the
  owned-workspace count must lock the holder row and count owner memberships in
  one transaction; the existing limits service
  (`app/services/tenancy/limits.py:78-198`) has no workspace-count concept.
- G6 — the personal LLM ledger is dormant by configuration
  (`PERSONAL_BILLING_ENABLED`, `app/core/config.py:333`); this task's storage
  ships independently of it.
- G7 — payer is currently resolved in three independent places (catalog owner,
  `personal_llm_dispatches.payer_user_id`, tenant-scoped admission
  (`app/services/ai/catalog_execution.py:5-31`,
  `app/models/managers/personal_billing_manager.py:451-506`,
  `app/services/ai/budget_admission.py:128-130`), and `consent_version` is not
  carried into dispatch evidence. P21-T12 unifies this; this task adds no fourth
  resolution and no second ledger. Existing task payer consent is self-consent
  only (`app/models/billing/billing.py:76`), so host-sponsored delegated use has
  no consent record yet.
- G8 — migration traps found in the source inventory: the daily-cost resolver
  falls back to the workspace column even for an "unlimited" holder
  (`app/services/tenancy/resolver.py:98`); the attachment service defaults to
  `pro` whenever a workspace read fails
  (`app/services/chat_attachments.py:1723`); planning-time admission and
  execution-time admission read the plan separately
  (`app/models/managers/agent_task_manager.py:1209-1218` and
  `app/jobs/handlers.py:1060,1115,1654`), so a queued job could survive a
  holder plan change unless both resolve the same holder.
- G9 — `plan_expires_at` is never written in `app/` (read at
  `app/services/tenancy/entitlements.py:46,79`, displayed in
  `app/admin/view_modules/users.py:298`), so expiry today has no producer. The
  holder plan's expiry needs one, or expiry stays inert and must be stated as
  such.
- G10 — `PLAN_LIMITS` has no token and no workspace-count key, and
  `analytics_depth` is declared but never read; the limits service exposes
  `check_daily_cost` and `check_model_type` that no caller uses
  (`app/services/tenancy/limits.py:190-202`). The new policy keys must be
  additive and must not silently activate dormant helpers.
- G11 — the migration history was folded into `migrations/versions/baseline_0118.sql`
  (`0117` is a legacy script under `scripts/migrations/legacy_definitions/`), so
  a new holder column must be written against the live head
  (`p17t01_workspace_outbound_hosts`) with the number assigned at merge.

## Open packaging questions before allowance activation

The owner has decided the subject, shared scope, configurable modules and
finite/unlimited option, but not numerical packages or counting semantics:

1. Which period resets the allowance: UTC day, calendar month or subscription
   period? What happens on renewal or mid-period plan change? Neither upgrade nor
   downgrade silently erases usage or possible charges.
2. Which input/output/cache/tool/media units consume tokens, and does BYOK consume
   the included platform allowance? Non-token modalities need an explicit rule;
   do not convert media/USD into tokens or allow an accidental bypass.
3. What finite limits/module packages are offered, and is exhaustion a denial or
   separately consented overage? No automatic charge or trial entitlement.

Record owner answers here before activating the corresponding policy. Continue
storage/contract work without guessing commercial terms; missing answers deny new
allowance-governed dispatch, not legacy work outside an approved migration.

## Acceptance and boundaries

- One owner tariff governs all owned spaces. Membership/role promotion neither
  changes sponsorship nor grants subscription/model management.
- Configurable module grants, owned-space limits and token policies have one
  authoritative definition; usage preserves owner/period/workspace/actor history.
- Public surfaces show the host's effective rights in an invited workspace, not
  the invitee's tariff; safe model metadata contains no secret/ref internals.
- Required focused mocks, PostgreSQL race tests, retained-data Alembic cycle,
  mapped legacy rows, actual documents read and exact checked SHA are recorded.
- Additive rollout stays off until P21 admission/settlement/credential controls and
  owner packaging decisions pass. No production migration, payment request or
  corporate billing activation is authorized by this card.
- Rollback freezes new target-path work, preserves usage/reservations and restores
  compatible reads only after proving no lost entitlement or liability evidence.
