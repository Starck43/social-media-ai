# P2-T17 — User-level tariffs, module entitlements and shared token allowances

Registry: [ROADMAP](../../ROADMAP.md#p2); parent: [P2](../phases/p2-usage-spend.md).

## Goal and predecessors

Implement one service tariff per user, shared across that user's owned workspaces.
Tariff definitions configure enabled product modules, the maximum number of owned
workspaces and finite or explicitly unlimited LLM token allowances. Platform model
availability is configured by [P21-T13](p21-t13.md); allowance reservation and
settlement belong to [P21-T15](p21-t15.md) / [P21-T16](p21-t16.md).

Consume the accepted [entitlement foundation](../platform/ENTITLEMENTS.md) and
[subscription configuration](../platform/SUBSCRIPTIONS.md), not another capability
engine or checkout provider. This task owns the plan-holder/policy contract that
P21-T12 can specify before wiring it. Tariff storage can be delivered with LLM
execution disabled; it does not depend on completed P21 runtime work. Checkout,
real prices, automatic renewals and production activation are separate assignments.
[P2-T08](p2-t08.md) corporate billing remains deferred.

## Owner decision — 2026-11-13

Source: OpenCode session `ses_e2fa3690affea2bSCgS5dlSVmg`, owner assignment and
explicit answer **models of the workspace owner** to the invitation question.

- The subscription subject is the user, not the workspace or a membership role.
  All owned workspaces share that user's tariff and allowance pool; creating or
  switching workspaces never multiplies or resets an allowance.
- Enabled modules include configurable ERP, CRM, documents, social analysis and
  other registered domains. These are packaging targets, not assertions that every
  module is implemented. Product module grants and model operation capabilities
  are different concepts.
- A workspace is bound to a governing owner/plan holder. Invited members execute
  within that owner's enabled functionality using the owner's configured platform
  or personal models, intersected with their own workspace/object permissions.
  Their own tariff/catalog neither expands nor replaces the host's rights.
- Any invited role, including a broad administrator role, grants no authority to
  change the host's tariff, catalog/providers/keys, models or model defaults.
  Owner LLM configuration and billing are account-level operations, not workspace
  RBAC. Invitees can manage their own account/catalog in their own context.
- Membership alone does not authorize charging or decrypting the owner's BYOK.
  Explicit owner consent binds delegated model use to the workspace/task scope;
  execution resolves the key internally and never returns it to the invitee.

## Proposed persistence contract

Publish a final field/consumer/constraint mapping before writing migrations. These
are target relations, not current schema; do not impose a fixed table count.

| Responsibility | Target storage and invariants |
| --- | --- |
| Configurable tariff definitions | Versioned plan policy keyed by validated plan code. Initially reuse the existing plan set; one policy owns module/resource/allowance packaging. Paid offer amount/currency remain a separate immutable checkout snapshot. |
| User entitlement | `user_service_plans`: unique `user_id` FK, plan/policy version, active state and aware expiry. Roles never select its subject; no per-workspace subscription copies. Preserve old policy versions referenced by history. |
| Workspace sponsorship | `tenants.plan_holder_user_id`: verified user FK with restrictive deletion. Resolve ambiguous/multiple legacy owners explicitly; do not infer the holder from the current actor or an arbitrary owner-role member. Ownership transfer is a separate owner-approved lifecycle. |
| Module grants | Reuse the composed namespaced capability registry and decision engine. Configure supported module keys/grants in the authoritative policy; unknown or unavailable capabilities fail closed. Do not hardcode a second ERP/CRM list in LLM tables. |
| Owned-workspace limit | Policy `max_owned_workspaces`: nonnegative integer or explicit unlimited. Count creations/ownership, not invited memberships. Atomic enforcement locks the plan-holder scope, not an individual workspace. Deployment ceilings remain independent. |
| LLM token allowance definition | Versioned policy: unit/counting rule, period definition and `token_limit` as nonnegative BIGINT or NULL meaning explicitly unlimited. Zero denies token use; missing policy/row is not unlimited. It is not USD or provider TPM. |
| Allowance balance | Owner/period/pool unique balance with nonnegative BIGINT `reserved_tokens` and `used_tokens`, policy version and unresolved-use evidence. Workspace and actor are attribution only, not separate balances. P21-T15 owns atomic reservation by dispatch identity; P21-T16 owns settlement/reconciliation. |

Do not use `tenants.daily_cost_limit`, `entitlement_usage` or monetary
`llm_budget_days` as a token ledger. Existing capability usage counts admissions,
not LLM tokens. Workspace USD ceilings can remain a stricter independent guard;
they do not define subscriber token entitlement. Personal USD accounting retains
its accepted payer/consent ledger. No duplicate ledger for the same economic event.

## Open packaging questions before allowance activation

The owner has decided the subject, shared scope, configurable modules and
finite/unlimited option, but not numerical packages or counting semantics:

1. Which period resets the allowance: UTC day, calendar month or subscription
   period? What happens on renewal or mid-period plan change? Neither upgrade nor
   downgrade silently erases usage or possible charges.
2. Which input/output/cache/tool/media units consume tokens, and does BYOK consume
   the included platform allowance? Non-token modalities need an explicit rule;
   do not convert media/USD into tokens or allow an accidental bypass.
3. What finite limits/module packages are offered, and is exhaustion a denial or
   separately consented overage? No automatic charge or trial entitlement.

Record owner answers here before activating the corresponding policy. Continue
storage/contract work without guessing commercial terms; missing answers deny new
allowance-governed dispatch, not legacy work outside an approved migration.

## Acceptance and boundaries

- One owner tariff governs all owned spaces. Membership/role promotion neither
  changes sponsorship nor grants subscription/model management.
- Configurable module grants, owned-space limits and token policies have one
  authoritative definition; usage preserves owner/period/workspace/actor history.
- Public surfaces show the host's effective rights in an invited workspace, not
  the invitee's tariff; safe model metadata contains no secret/ref internals.
- Required focused mocks, PostgreSQL race tests, retained-data Alembic cycle,
  mapped legacy rows, actual documents read and exact checked SHA are recorded.
- Additive rollout stays off until P21 admission/settlement/credential controls and
  owner packaging decisions pass. No production migration, payment request or
  corporate billing activation is authorized by this card.
- Rollback freezes new target-path work, preserves usage/reservations and restores
  compatible reads only after proving no lost entitlement or liability evidence.
