## Goal and existing boundaries

Protect personal connection secrets, make the credential used for each source
explicit and auditable, and give operators a clear separation between deployment,
platform and personal configuration. Avoid breaking existing users or silently
changing the identity used by a source.

- **Deployment:** one application's identities, service and bot credentials,
  encryption key and infrastructure settings, provided by deployment configuration
  (`.env` or equivalent secrets manager). Never commit or display secret values.
- **Shared catalog:** non-secret platform API endpoints, version, OAuth URLs and
  callback in one shared `Platform.params`, managed by authorized operators. Code
  bootstrap values and legacy environment inputs are initialization/migration
  inputs, not competing runtime overlays; see [Q-16](../audit/q-16.md).
- **Personal and workspace connections:** VK/Telegram personal credentials use
  `user_credentials`; mail connections use `workspace_connections` plus encrypted
  `workspace_connection_secrets`, scoped to both tenant and owner. This is not
  currently one universal table. Any unification requires its own reviewed design
  and data-preserving migration; do not silently merge scopes. See
  [P12-T08](../audit/p12-t08.md) and [connector configuration](../CONNECTOR_CONFIGURATION.md).

At source snapshot `279e23bae487f8e1be75da4168993266c146331a`,
[`vk_oauth.py`](../../app/services/social/vk_oauth.py) encrypts the VK access token
but stores its refresh token in `user_credentials.meta` as plain text on create
and refresh. This is a source-code finding, not a claim about the values or rows
in any deployment. The same file's pending PKCE verifier uses encrypted storage.
The existing rotation and renewal behavior must not be weakened by the fix.

## Ordered implementation slices

### 1. Protect refresh tokens — first priority

- Design a single encrypted canonical refresh-token representation with the
  existing key-management conventions; do not expose tokens in `meta`, admin,
  logs, exceptions, diagnostics, exports or API responses. Metadata may carry
  a non-secret availability/state indicator, not the token itself.
- Inventory every read, write, refresh, status and revoke path before changing
  it. Preserve owner scoping, expiry, provider rotation semantics and OAuth/PKCE
  state. Prevent concurrent refresh callers from replaying a rotated token:
  specify and test the actual locking/compare-and-set and failure semantics.
- Add a reviewed Alembic data migration or an explicitly authorized equivalent
  migration procedure with safe handling of null, malformed and pre-existing
  values. No secret values in migration output; do not leave plaintext as a
  parallel runtime source of truth. Define idempotence, transaction boundaries,
  backup retention and a forward-recovery plan before changing stored secrets.
  Inspect the real Alembic head; do not reserve a revision number here.
- Validate upgrade and recovery on an exclusively owned synthetic test schema;
  verify synthetic records and full schema inventory cleanup. Public/production
  apply requires separate owner authorization after validation and backup.
  Encryption-key replacement requires a separately tested re-encryption and
  recovery plan; losing the current key is not a routine rotation.
- Assess whether legacy database backups, exports or access require restriction
  and whether affected VK sessions need revocation/re-authorization; do not claim
  an actual exposure or revoke credentials without owner approval.

### 2. Explicit source identity and least privilege

**Coordination gate:** [P12-T16](p12-t16.md) owns `sources.owner_user_id`,
creator assignment, removal of implicit workspace-owner selection, L1-only
reporting, auth preflight and personal authorization notifications. Do not
implement a competing resolver, ownership migration, preflight or notification.
Review its delivered contract and integrate focused security tests after its
exact revision is available; until then, this slice is inventory/design only.
P12-T14 retains refresh-token confidentiality, residual credential-selection
security, Telegram-session deprecation and cross-surface configuration safety.
The source-identity requirements below constrain integration, not ownership of
P12-T16's implementation. Coordinate exact paths before editing shared modules.

- Inventory legacy source collectors, newer selected-task policy, API, CLI, admin,
  UI and background jobs. Preserve existing authorized behavior until an explicit
  migration policy is approved. Do not set a user ID for all sources by guesswork.
- Make the actual mode and non-secret owner/credential identity visible per source
  and run: service vs personal, active/expired/denied, and reason for refusal.
  Recheck current actor, workspace membership, credential ownership, consent and
  applicable method permissions at execution, not just in a preview.
- Personal identity must not silently fall back to a different user's credential or
  a deployment-wide session. If auto/fallback is retained for compatibility, it
  must be an explicitly selected, transparent policy with documented allowed
  transitions and no cross-owner substitution; a denied/revoked selection fails
  closed. Consent/sharing semantics need a reviewed contract before implementation.
- Provide an inventory and dry-run migration for existing `auto` sources: identify
  unknown or ambiguous ownership without exposing tokens; let an authorized owner
  approve mappings per source, report unresolved cases, and provide rollback.
  No unapproved bulk edits to live data.
- Deprecate deployment-wide `TELEGRAM_SESSION` fallback in stages, after inventory
  and a supported personal-session path. Treat session strings as full credentials;
  no copy to logs, prompts or browser-visible output. Distinguish MTProto collection
  from shared bot delivery. Preserve existing installations until migration is ready.

### 3. VK policy, OAuth configuration and honest UI

- Distinguish service key configured, locally allowed methods/scopes and actual
  provider-verified capability. Surface unknown grants as unknown/denied rather
  than "working"; do not infer rights from token presence, UI labels or mocks.
- Keep [Q-5](q-5.md) open: method, app profile, credential mode, scopes and network
  require evidence. No live VK requests, token use or category activation are
  authorized by this planning task. Music retains its separate permission gate.
- Use `Platform.params` as the sole runtime source of OAuth URLs/callback; validate
  appropriate HTTPS/host policy for the deployment and exact registered callback.
  Legacy migration inputs are not presented as live configuration. Avoid claiming
  any environment's current callback without a separately authorized inspection.
- The current OAuth exchange does not send `VK_CLIENT_ACCESS_KEY`; correct the
  misleading UI error and docs, then deprecate/remove unused configuration only
  after checking all consumers and compatibility. Verify provider requirements
  before claiming PKCE replaces a client secret for every application profile.
- Keep provider/catalog readiness honest: P12-T08 implements mail configuration
  and IMAP checks, not general mail sync; disk and other planned descriptors are
  not working integrations merely because they appear in the catalog.

### 4. Owner bootstrap and operational guidance

- Review `TELEGRAM_OWNER_IDS` / `MAX_OWNER_ID` bootstrap, platform-owner checks,
  and persisted `tenant_users` ownership separately. Provide an authorized,
  non-secret inventory and explicit revocation procedure; removing an env ID
  must not be described as deleting existing membership.
- Document smallest necessary owner allowlists, admin access, key backup/rotation,
  callback configuration and incident response. Distinguish operator alerts from
  workspace digest destinations. Do not change existing memberships or keys
  automatically and do not print their values into task evidence.

## Acceptance and verification

Each implementation slice records exact source SHA, commands, outcomes, changed
paths, rollback and independent review. Overall completion requires:

1. Synthetic legacy and newly created VK credentials contain no plaintext refresh
   token in database fields or user-facing surfaces; successful renewal persists
   encrypted rotated tokens, handles missing/wrong keys safely, and does not lose
   sessions on a failed migration. Negative/concurrency tests cover double refresh,
   partial failure and token revocation. No secret appears in logs or test artifacts.
2. Mocked multi-user/multi-workspace tests prove explicit owner, consent, membership
   and revocation checks, including forged IDs, queued runs, fallback decisions,
   expiry and disconnect; users cannot acquire another person's credentials.
3. UI/API/CLI/admin and job diagnostics agree on service/personal selection and
   bounded, non-secret status; service grants and separate Q-5/music gates stay
   fail-closed. Existing supported collection/delivery and OAuth paths have focused
   regression tests; no mock result is described as live provider verification.
4. Migration upgrade/recovery and all data preservation are tested on the authorized
   synthetic schema, with before/after full inventory and cleanup; public rollout
   remains separate. Configuration/security docs describe actual sources of truth,
   operational steps and limitations without exposing values.
5. Focused checks and static/security checks pass. Paid services and external writes
   are mocked; no broad suite without explicit owner request. UI claims require
   appropriate route/DOM tests, not merely unit tests. Unrun checks remain unrun.

**Shared, serialized — first writer announces, the other rebases:**

  representation; T16 added `ordered_tokens` (personal token preferred over the
  service token). T14 re-reads this file after the T16 merge and keeps the

  `renewable`/`reauth` derivation) and `app/services/social/vk_connections.py`.
- `app/web/connections.py` and the connection templates.

**Contracts T14 must treat as already decided once T16 lands:**

1. There is **no** fallback from a source to the workspace owner's personal
   credential. A source with no `owner_user_id` and no explicit
   `params.token_owner` collects through the deployment credential only, and the
   run says so. T14's "if auto/fallback is retained for compatibility" clause
   therefore does not apply to source selection: the fallback is removed, and
   the inventory/dry-run migration it plans must map "who should become
   `owner_user_id`", not "whose token was being borrowed".
2. `notification_type` is a native PostgreSQL enum stored as member names, and
   Alembic does not autogenerate new members. Any new value needs an explicit
   `ALTER TYPE ... ADD VALUE`. T16 adds `SOURCE_AUTH_REQUIRED`; the deployed head
   moves past `0122`, so T14 reads the real head at implementation time instead
   of assuming a revision number.
3. `renewable` is not an error: it renews itself and must never be presented as
   something a person has to fix. T14's status work keeps that distinction.
