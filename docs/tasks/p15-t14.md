## Problem

Two in-flight tasks need the outbox to carry more than a text body: P15-T08 needs reply headers and
P19-T05 needs document attachments. `app/services/communications/outbox.py` currently models one
body per item, and the ingest contract explicitly stores no attachments
(`app/models/communications/message.py`). If each task extends the outbox independently, the second
merge overwrites the first — the same shape as the `0143` / `0145` chain collision.

## Plan

1. Extend the outbox contract with an optional, ordered attachment list bound to **stored evidence**,
   not to caller bytes: content reference, size, MIME type and a hash the approval already sealed.
   No attachment is read from a request body at dispatch time.
   - **Two hashes, not one** (adjudicated 2026-11-09, answering P19-T05's question): the approved
     document is sealed by `(revision_id, revision_body_hash)` — the SHA-256 of the document body
     that P19-T01/P19-T04 approval covers — and every attachment additionally carries
     `attachment_bytes_hash`, the SHA-256 of the exact delivered file. A re-rendered or re-edited
     revision fails on the body hash; a renderer that produces different bytes for the same body
     fails on the attachment hash. Neither may be substituted for the other, and the approval never
     stores an attachment hash as if it were a revision hash.
2. Delivery rules: a provider that cannot attach (Telegram, MAX) is refused at scheduling time, not at
   dispatch; partial delivery is not allowed — either the item goes with all attachments or it is not
   sent; retries are idempotent per `(item, destination, attachment hash)`.
3. Approval binding: the same hash the document approval sealed (P19-T04/T05) goes into the outbox
   item, so a re-render between approval and dispatch invalidates the item instead of sending different
   bytes.
4. Inbound direction stays out of scope: ingested attachments are not stored (unchanged contract).
5. Reuse `outbox_store.py` and the P14-T09 trusted-outbound guard; no new sender, no second queue.

  attachment hash, each with its own recorded refusal.
- A channel without attachment support is refused when the item is scheduled, with a recorded message.
- Restart mid-dispatch does not send the item twice or send a partial attachment set.

## Storage contract (owner decision D9a, 2026-11-10)

Attachment bytes are **transient**. An approved revision is rendered, hashed,
rechecked and delivered; the file lives in a filesystem spool from render until
dispatch plus the TTL, then is deleted. They are never written to PostgreSQL —
thousands of tenants would bloat the database with bytes needed for minutes — and
the platform never becomes the tenant's archive: that role belongs to their own
cloud or local store (S3 connector per D9, Yandex Disk for existing users).

- Owned code: `app/services/attachments/` (`spool.py`, `policy.py`).
- Settings, not schema: `ATTACHMENT_MAX_FILE_BYTES` (5 MiB), `ATTACHMENT_MAX_TOTAL_BYTES`
  (10 MiB), `ATTACHMENT_SPOOL_TTL_SECONDS` (900), `ATTACHMENT_STORAGE_DIR`.
  Documented in [CONFIGURATION](../../CONFIGURATION.md).
- Outbox stores a reference — `(tenant, item, position, sha256, size, mime)` — never
  a location. A later S3 source is a new reader, not a contract change.
- Restart: the spooled file and its digest outlive a crash, so the retry reads and
  rechecks `attachment_bytes_hash` rather than re-rendering. The existing
  acceptance sentence about restarts still holds; the spool is the mechanism that
  makes it true.
- The spool is host-local. Delivery runs on the process that wrote the file, which
  the single `python -m app.runtime` satisfies; a shared volume is the escape hatch.

### Auditor stitch: approved revision to spooled attachment (2026-11-10)

`app/services/communications/attachment_delivery.py` is now the single seam where
an approved revision becomes a deliverable attachment. Both halves meet here, and
it is the only place that does all four steps:

1. Read the approval and the current revision **under locks**.
2. Recheck `(revision_id, revision_hash)` against the approved pair and recheck
   the stored body hash against the body itself, even though the database
   enforces it — the service does not trust a constraint it has not re-read.
3. Render and spool through `spool_revision`, reusing P19-T05's exporter.
4. Return `StitchedAttachment(reference, document_id, revision_id, revision_hash)`
   — exactly the `AttachmentRef` the outbox persists.

Every refusal is a stable code (`approval_unavailable`, `approval_not_granted`,
`revision_changed`, `revision_hash_mismatch`, `document_unavailable`,
`invalid_*`) and nothing is written for a refused revision. There is no re-render
and no fallback.

The branch merges `feat/p19-t05-export-recovered` (`99f03a48`) because the
renderer and the outbox are two halves of one contract; the merge was
conflict-free, which is the evidence that the two halves stayed independent.

**One improvement came from the merge:** the newer spool refuses to overwrite an
occupied position (`attachment_position_occupied`), so a slot cannot be silently
re-rendered over. The dispatch test now tampers with the file directly, which is
the only way left to simulate a re-render, and still gets a refusal.
