# Q-5

Parent: none (standalone question).

[Active queue](../../../ROADMAP.md#questions).

Which registered VK application profile and credential mode should deployment
use for the global search methods (`newsfeed.search`, `groups.search`,
`users.search`)? The open decision is whether the current web app profile can
serve those methods or a different profile is required. The API is the required
integration surface; internal vk.ru search endpoints are not evidence of API
capability. Record method, app profile, credential mode/scopes and the network
where evidence was obtained.

## Answer — 2026-11-17

Use the existing Web application profile (`54798450`) with a personal VK ID user
token obtained through the app's OAuth flow and freshly authorized after the VK
grant. `newsfeed.search`, `groups.search` and `users.search` all answered `ok` in
a bounded live run; no Standalone profile change and no extra `scope` value was
needed. The token carried only `vkid.personal_info`. Evidence, limits and the
reproduction command are in the live probe section below.

## VK support response — owner-provided, date not recorded

VK support replied that only the [VK ID scopes documented for the
service](https://id.vk.ru/about/business/go/docs/ru/vkid/latest/vk-id/connection/work-with-user-info/scopes)
can be enabled in application settings. Requests for additional access
must provide the application ID from the business portal, the requested access,
a detailed usage scenario, and website and community links. This is a request
for details, not confirmation that any search method or application profile is
approved. The owner said the project is still local; no deployed site or
community URL has been recorded here. Do not present a repository URL as a live
site or invent a community link.

Q-5 therefore remains OPEN at that point. Before a live check, verify the app ID
and resolve method/profile/network availability. Any live request still needs
immediate, method-specific owner authorization and the bounds recorded by P8-T41.
The 2026-11-17 live probe below resolved this: the grant is bound to a fresh
authorization, not to an extra `scope` value.

## Probe aid (2026-11-11)

`scripts/check_vk_search_capabilities.py` performs the bounded check this row
asks for, once the profile is known: one read-only request with `count=1` to
`users.search`, `groups.search`, `newsfeed.search`, `video.search` and
`apps.getCatalog`, plus `market.search` when a community owner id is supplied.
It prints one bounded verdict per method
(`ok`, `auth_failed`, `access_denied`, the three rate-limit codes, `invalid_parameters`,
`profile_restriction` for VK 1051, or a bare provider code) and never prints,
logs or stores the token, which is read from `VK_ACCESS_TOKEN` by default.

It changes no category status and writes nothing. A green run is the
method/profile evidence P8-T33/T46/T47/T48 wait on; a refusal is recorded with
the exact code, not paraphrased provider text. The four categories stay
`mocked` until that result is recorded here and in the registry.

## Live probe — 2026-11-17

Owner-authorized, read-only, one request per method. The owner re-authorized the
VK ID connection minutes before the run after VK granted the application
extended access. The stored personal token (web user 2) reported
`scope=vkid.personal_info` and VK ID `3619562`.

| Field | Value |
| --- | --- |
| Application | `54798450`, Web profile, unchanged |
| Credential mode | personal VK ID user token (OAuth PKCE), not the service key |
| Token scope | `vkid.personal_info`; no extra `scope` was requested |
| Network / host | owner's machine, `https://api.vk.com/method` |
| API version | `5.199` |
| Bounds | one GET per method, `count=1`, no retry, no write |

| Method | Verdict | Items |
| --- | --- | --- |
| `users.search` | ok | 1 |
| `groups.search` | ok | 1 |
| `newsfeed.search` | ok | 1 |
| `video.search` | provider error 15 (access denied for this token/app) | 0 |
| `apps.getCatalog` | ok | 0 |

Interpretation:

- The three Q-5 methods work with the current Web application profile. A
  Standalone migration is not required for them.
- `scope` is not the gate: the token carried only `vkid.personal_info` while all
  three methods answered. The VK grant is bound at authorization, so a token
  issued before the grant keeps the old result; existing connections need
  re-authorization, not a new `scope` value.
- `video.search` returned code 15, not `1051`: the profile restriction is gone
  for the probed methods, but the video method still lacks access for this
  token/app. That gate belongs to P8-T46, not to this question.
- `market.search` was not probed: the granted category list did not include
  `market`, and no community owner id was supplied.

Limits: one token, one network, one run, no independent audit yet. The service
key was not re-probed; the historical `1051` for it is neither confirmed nor
refuted. The product search path uses a personal user token for
`groups.search`/`users.search` regardless.

Reproduce: point `VK_ACCESS_TOKEN` at a token from a fresh personal
authorization and run `python scripts/check_vk_search_capabilities.py`. The
script now covers the three Q-5 methods, prints bounded verdicts and never
prints the token.
