# Q-12

[Active queue](../../ROADMAP.md#questions).

decide whether and when to add self-service, account-bound one-use password
recovery by email.

**Status: DEFERRED** (owner decision 2026-10-26). The pilot keeps operator-issued
recovery; email confirmation and, on top of it, self-service recovery are
scheduled for the pre-production phase. The question stays open as a scheduled
item, not as unassigned work — see "Trigger" below.

## Decision (owner, 2026-10-26)

- **Now (pilot):** recovery stays the operator-issued reset from
  [ADMIN password routes](../ADMIN.md#password-routes-outside-sqladmin). No
  self-service flow, no anonymous password mutation, no mail provider.
- **Near production:** implement **email confirmation** first, and only then
  self-service recovery on top of confirmed addresses.
- The ordering is not cosmetic. An unconfirmed `User.email` is only a claim: a
  public "send a reset link to this address" flow run against unverified
  addresses lets one person register someone else's mailbox and then use
  recovery against it. Confirmation must land **before** recovery is reachable,
  not in the same change.

## Trigger

Start the work when either happens:

1. the product opens beyond the closed pilot (public signup), or
2. a real transactional mail provider is chosen and funded.

Until then the question is deferred by decision, not blocked by a defect.

## What already holds (verified in source, 2026-10-26)

| Prerequisite | State |
| --- | --- |
| `User.email` present and unique | `app/models/identity/user.py` — `String(100)`, `foreign key`-free, `unique=True`, `nullable=False` |
| Email format validated at signup | **no** — `/app/register` only checks uniqueness |
| Email ownership proven | **no field anywhere** (`email_verified`/`email_confirmed` absent from model and schema) |
| Mail delivery | **none** — no SMTP, no transactional provider, no dependency, no config key |
| Messenger delivery | Telegram works (`app/services/notifications/messenger.py`); VK is referenced without a working sender |
| Operator reset | `/admin/user/change-password/{user_id}` — active platform operator/admin, CSRF, password validation, owner remains self-only |
| Anonymous reset route | removed by P10-T01; no handler looks an account up by a submitted email |

So three prerequisites are partly present (the column, its uniqueness and
operator visibility through SQLAdmin) and two are entirely missing: address
confirmation and any outbound mail channel.

## Follow-up shape (to be filed as real tasks at the trigger)

- **Email confirmation task** — `email_verified` column + migration, confirmation
  token storage with expiry and single use, provider adapter behind a settings
  switch (mocked in tests), neutral responses, resend throttle. Owns
  `app/models/identity/user.py`, an Alembic revision, `app/core/config.py` and
  the signup/profile routes.
- **Self-service recovery task** — depends on the one above. One-use expiring
  token hashed at rest, identical response and timing for known/unknown
  addresses, no password in logs, rate limiting through the shared login budget,
  mocked-provider tests. It must reuse the existing operator reset for anyone
  whose address is still unconfirmed rather than silently skipping them.

Neither task is created yet: a card without an owner and a funded provider would
be registry noise.
