## What the task claimed and what was true

Card recommended option A — "make `allowed_boundary` an inclusive ceiling, because
`DocumentSearchService` already reads it that way". That premise is false.
`app/models/managers/knowledge_manager.py:11` documents `BOUNDARIES` as **destination
clearance**:

```python
# Destination clearance: local processing can read all three classes, company
# processing cannot read local-only, external/cloud processing only reads cloud.
BOUNDARIES = {"local_only": ("local_only", "company", "cloud"),
              "company": ("company", "cloud"),
              "cloud": ("cloud",)}
```

`filter_snippets_by_acl` already matched that table exactly, and two further suites pinned the
same behaviour (`tests/unit_web/test_p12_t03_knowledge_documents.py`,
`tests/web/test_p12_t11_real_knowledge.py`). Only the docstring disagreed with the code.

Option A would have inverted the security direction rather than repaired a contradiction: every
default `allowed_boundary="cloud"` caller, `assemble_llm_citations_context` included, would begin to
receive `company` and `local_only` evidence, while nothing in the package enforces the transport
boundary A's new docstring merely promised. That is the `local_only` cloud-transit rule in
[BUSINESS_MODULES](../product/BUSINESS_MODULES.md), so the executor took option B — keep the behaviour,
remove the contradiction — and recorded the deviation from the card's recommendation.

## Accepted change

- one shared predicate `_meets_required_clearance` drives both `filter_snippets_by_acl` and
  `assemble_llm_citations_context` (the card's "one predicate, documented and tested the same way")
- both docstrings state that `allowed_boundary` is the clearance the **destination** requires
- `assemble_llm_citations_context` normalises its argument like the filter; it previously failed
  closed on `"LOCAL_ONLY"` while the filter accepted it
- no behaviour, schema or data change
