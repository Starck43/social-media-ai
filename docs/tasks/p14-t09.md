# P14-T09 — Installation-wide trusted outbound hosts (shared egress authorization)

Owner decision 2026-11-04: build it now, as shared infrastructure rather than a
Bitrix24 branch. Every self-hosted connector hits the same wall, and a per-connector
copy of the guard would be a security layer per provider instead of one.

## Why this is not P14-T08

`P14-T08` is "let a workspace owner connect an on-premise Bitrix24 portal". That is
a consumer. This task is the control it consumes: one installation-level registry of
hosts the server is allowed to reach, one admin surface, one audit trail, one
refusal vocabulary — used by every outbound connector, not only Bitrix24.

## The gap, measured on `dev` `b2ea5356`

- `app/integrations/oauth/network.py` holds the only egress guard (`validate_oauth_url`,
  `post_oauth_form`): allowlist match, DNS resolution, and a hard `is_global` check
  on every resolved address.
- `BITRIX24_OAUTH_METHOD.allowed_hosts` is a static tuple; `Bitrix24Service` keeps a
  second static copy and is a module-level singleton, so a change is frozen at import.
- Nothing else consults the guard: the 1C OData client (`onec`), IMAP
  (`mail_check.py`) and any future CalDAV client would each need their own copy.

Consequence: an installation cannot reach a client-hosted portal, 1C base, mail
server or CalDAV endpoint at all, and the moment one connector grows its own
allowlist the guarantee that our server talks only to vetted destinations is gone.

## Contract

1. **One registry, installation level.** A table of trusted outbound hosts with
   `host`, `kind` (`public` | `private`), the addresses authorized for a `private`
   host, who added it and when. No `tenant_id` — this is the platform-wide technical
   row allowed by the 2026-11-04 exception, because it holds no customer data and is
   global by nature. Cite that exception in the model docstring.
2. **One enforcement point.** Every outbound connector validates through a single
   `acquire_outbound_target(host, port, …)`-style seam that: normalizes the host,
   checks the static provider allowlist (cloud suffixes and known endpoints stay
   code-owned), checks the registry for an installation-approved host, resolves DNS
   **on every attempt**, and refuses any address that is neither globally routable
   nor explicitly authorized for that host.
3. **Fail closed.** Registry unreadable, empty, or missing → only the code-owned
   cloud hosts are reachable. No connector falls back to an environment variable.
4. **Refusals are typed and user-facing.** `host_not_trusted` (registry has no
   entry), `address_not_authorized` (entry exists, a resolved address was not
   approved), `private_address_forbidden` (no entry, non-global address). Each
   names the host and the actor-facing owner: the installation administrator.
5. **Address re-validation.** DNS is resolved per attempt; an answer that differs
   from the authorized list fails closed. No pinning at boot, no trust in a cached
   IP.
6. **Auditable.** Add, remove and address change are written to `action_audit_events`
   with the actor. Admin routes are gated by `is_superuser_role`; a tenant actor
   can use a trusted host but can never add one.
7. **Provider-neutral by construction.** The seam knows nothing about OAuth, REST,
   IMAP or OData. Connectors pass a host, a port and the provider's static policy.
8. **Migrate, don't rewrite.** `validate_oauth_url` and `post_oauth_form` move onto
   the seam with their behaviour preserved; `Bitrix24Service` stops carrying a
   constructor allowlist. Existing cloud-only behaviour must be byte-for-byte the
   same when the registry is empty.

## Plan

1. Model + migration `0138`: `trusted_outbound_hosts` (`host` unique, `kind`,
   `authorized_addresses` JSON list, `note`, `created_by_actor_id`, `created_at`);
   audit codes `admin.trusted_host_add/remove` registered in all four places.
2. `app/core/outbound.py`: the seam and the three typed refusals. Pure function over
   an injected resolver and an injected registry reader, so tests need no network.
3. Registry reader cached **per request**, never per process.
4. Admin surface `/app/admin/trusted-hosts`: list with last resolved addresses, add,
   remove with confirmation, superuser-only, audited.
5. Move `validate_oauth_url` / `post_oauth_form` onto the seam; preserve the static
   cloud policy. Remove the constructor allowlist from `Bitrix24Service`, inject the
   resolver instead.
6. Attach the second consumer (whichever of P15-T01 / P17-T01 is in flight) with a
   call-site change only.

## Out of scope

- Per-tenant trust. If a tenant ever needs its own list, that is a new decision with
  a new threat model.
- The local connector gateway (P18) — it authorizes the client, not our egress.
- Changing what counts as a cloud host: those stay code-owned.
- Any relaxation of the `is_global` default: private addresses require an explicit
  approved entry, per address.

## Doubt and rollback

Whether the registry belongs in the main database or in a runtime-reloaded file. The
database is chosen for the audit requirement and the admin surface. Rollback: keep
the seam, revert the admin surface — the installation returns to cloud-only without
a data risk; the table drops in the downgrade and connections stay untouched.

## Evidence required

- Empty registry: cloud hosts work, every on-premise host is refused with a typed error.
- Add → connect works without a restart; remove → next attempt fails closed.
- `private` entry authorizes exactly its listed addresses; a changed DNS answer is
  refused with `address_not_authorized`.
- Non-superuser refused on the admin route; a tenant actor can use but not add.
- Audit row per add/remove with the actor.
- Both wired consumers go through the same seam — a test asserting neither has its
  own resolution path.
- Migration `up -> down -> up`; ORM metadata matches the live schema.

Decisions taken without the owner (rollback = revert the named piece):

- **`down_revision = "0136"`**: `0137` (P15-T02) is not on `dev` yet, so a `0137` parent would
  break `alembic upgrade` here. If `0137` lands first, only this file's `down_revision` changes to `"0137"`.
- **Audit tenant**: `action_audit_events.tenant_id` is NOT NULL, so admin changes are written
  into the administrator's active workspace ledger (row id only, never the host name). The page
  refuses writes without an active workspace. Alternative (a platform audit ledger) is a new decision.
- **`is_superuser_role`** is the existing web gate (`operator`/`admin`; the platform `superuser`
  is not an `/app` actor). The manager re-checks the same set from the DB; a test keeps them equal.
- **Address change** = remove + add (each audited); no in-place edit route.
- **Private entries** refuse loopback, link-local (incl. `169.254.169.254`), multicast,
  unspecified and reserved addresses; hosts must be DNS names (TLS needs one), never IP literals.
- **Empty-registry compatibility**: `validate_oauth_url` maps seam refusals back to its old codes
  (`untrusted_oauth_host`, `unsafe_address`, …); the typed refusal rides on `OAuthNetworkError.refusal`.
  The only visible change is Bitrix24 on-premise input: `untrusted_portal_domain` → `host_not_trusted`.
- Registry snapshot is read once per connector operation (`registry_scope`), never per process;
  outside a scope the reader is empty, so a forgotten scope stays cloud-only.
