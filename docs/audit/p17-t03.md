## Security review

No boundary defect found. The language model only proposes a plan: `parse_plan_draft` rejects unknown keys, non-identifier names, foreign operators, non-ISO dates and oversized payloads, and `build_odata_query_target` re-validates the entity set, fields, filters and sorts against the connection's own `$metadata` and the administrator allowlist, so an injected instruction inside the question cannot widen access (fixture: `entity_not_allowed`). Raw OData text is never accepted or stored; literals are typed and quotes are doubled. Execution stays read-only (`GET`), bounded (30 s, 2 MiB, ≤ 1000 rows) behind `_authorize(require_source_view=True)`, `verified`/`odata_standard`, an approved host and the `metadata_sha256` pin; the shared provider budget stays fail-closed. Export renders only already-authorized rows, fetches no external resource and neutralizes spreadsheet formula prefixes. History stores the question as Fernet ciphertext, never the returned rows, and every read is tenant- **and** actor-scoped (another actor or tenant sees an empty list and `history_not_found`).

## Findings carried forward

**F1 — a pagination continuation depends on the planner (medium; closed by [P17-T06 accepted](p17-t06.md)).** `POST /query` accepts `page_token` and returns `next_page_token`, but `answer()` re-runs the planner and binds the token to the *new* plan's fingerprint; the fingerprint covers the rendered `$select` order, filters and `$orderby`, so the continuation fails with `400 invalid_page_token` whenever the model does not return a byte-identical plan (a different field order alone is enough, and the fleet order in `chat_with_fallback` is runtime-dependent). Probe on the accepted revision: plan A (`Description`, `Цена`) → token; plan B (`Цена`, `Description`) with that token → `invalid_page_token`. Fail-closed, no leak; the accepted behavior was that a second page is not reliably reachable. Fixed on 2026-11-12: the continuation continues from the stored plan (`history_id` → `plan_from_json`, the path the export flow already uses) instead of re-planning.

**F2 — the positional DTD guard is now reachable (low, hardening, closed by the [P17-T07 audit](p17-t07.md)).** `metadata.py` still refuses `<!DOCTYPE`/`<!ENTITY` only inside the first 8192 characters: an early DTD → `unsafe_xml_forbidden`, the same DTD after a 9 000-character comment → accepted and parsed into a catalog. The P17-T02 audit conditioned the parser-level refusal on "before that wiring"; T03 is that wiring — the remote `$metadata` is now parsed on the API and chat paths. The residual impact stays contained (expat resolves no external entities and its amplification limit refuses billion-laughs). Fix: refuse DTDs at the parser level (`defusedxml`, or an expat `StartDoctypeDeclHandler`).

**F3 — `mark_exported` is dead code and an export duplicates the history row (low, closed by the [P17-T07 audit](p17-t07.md)).** `export()` records a new row with `status="exported"` instead of marking the referenced one, so exporting a stored result leaves the source row at `status="executed"` with `exported_at = NULL` and adds a second row.

**F4 — the float guard never fires on the production JSON path (low, closed by the [P17-T07 audit](p17-t07.md)).** `parse_plan_draft` uses `json.loads(..., parse_float=Decimal)`, so a JSON float arrives as `Decimal` and `_reject_float` does not fire; the `float_forbidden` test covers the Python-mapping path only. The real refusal happens later in the typed literal rendering (`invalid_filter_value` for a non-decimal field; a decimal field renders `1.5m`), so no injection or type confusion follows — but the claim "floats are rejected before anything runs" does not describe the production path.

**F5 — the API omits what the chat tool exposes (low, closed by the [P17-T07 audit](p17-t07.md)).** `format_result` computes the chart series and a `truncated` flag; the chat tool returns both, `QueryOutput` returns neither, and `row_count` reports the capped length (≤ 1000) without saying that rows were dropped.

**F6 — one question costs two provider requests (operational, [P17-T08](p17-t08.md)).** `answer()` fetches `$metadata` per question and then the data: 2 of the 10 requests the 1C policy allows per 60 s (`rate=10, burst=10, window=60`, cost 1 per request) → about 5 questions/min sustained.

**F7 — the status enum is wider than what is written (info, [P17-T08](p17-t08.md)).** The table allows `planned`/`refused`; the service only ever writes `executed`/`exported`.

## Limitations

No live 1C base and no provider LLM call (planner calls are mocked), no UI surface, no full test suite. PDF bytes are unverified on hosts without pango. The card's plan step "show the interpreted plan before execution" is delivered as an interpretation returned with the answer, not as a pre-execution preview — there is no dry-run surface; the write-command preview belongs to P17-T04. History is telemetry: the downgrade drops rows without a guard, unlike the P17-T01 host approvals.
