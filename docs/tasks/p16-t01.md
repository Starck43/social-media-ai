## Goal

Personal and team to-dos with deadlines and priorities.

## Baseline

- `agent_tasks`/`/api/v1/tasks` mean scheduled agent work — not reused (R-03).

**Boundary (D23, [Q-20](../audit/q-20-notification-surface.md)):** a one-off planned
action is a planner task; a contact birthday or anniversary stays a CRM event with
its `greeting_history` ledger, which `P14-T04` already surfaces 7/3/1 days ahead. Do
not add a contact-event model here and do not duplicate the company-statistics
reminder.

**Source authority (D24, [Q-21](../audit/q-21-source-authority.md)):** the planner owns its tasks,
its RRULE subset and its visibility because no external task system is connected. When
[P16-T03](p16-t03.md) lands, a task tied to a calendar event reads the recurrence from the
calendar instead of computing it. Never mirror a Bitrix24 task or calendar event.

**Orchestration (D25, [Q-21](../audit/q-21-source-authority.md)):** the planner is one source of tasks,
not the only one. Its external identifier and its source registrations come from the
shared registry of connected sources; it never grows its own external-id scheme, and a
second task source (a calendar, a CRM) is registered next to it, not merged into it.

**Overlap and choice (D26, [Q-21](../audit/q-21-source-authority.md)):** a task system
connected later does not take over the planner automatically — the user is shown the
overlap and keeps or changes the current choice.

## Plan

1. Model `planner_tasks`: tenant, owner, assignee, title, description, due at (timezone-aware) or due date, priority `low|medium|high|critical`, status `todo|in_progress|done|cancelled`, category, tags, contact, parent task, recurrence (RFC 5545 RRULE subset: DAILY/WEEKLY/MONTHLY, interval, until/count), completed at.
2. Recurrence engine: completing an occurrence creates the next one; editing series vs. occurrence explicit. The rule is stored **as text, never as expanded occurrences**: a monthly task must not pre-create a year of rows, and the next occurrence is computed from the rule plus the last completion. This is what makes the future hand-over to a calendar a storage-preserving change.
2a. `recurrence_source` (`planner` | a registered external source) is a column from the first migration, filled with `planner` today. It is the switch the calendar will flip, not a later rewrite of every task. A task whose source is external never has its rule computed here, and its stored rule is used only while the source is unreachable (D24 part 3).
2b. Occurrence identity is deterministic — `(task_id, occurrence_key)` where the key is derived from the rule and the occurrence date, not from `now()` — so a retry, a restart or a duplicate webhook cannot create the same occurrence twice. Bind that with a test before the calendar exists; after it does, the same property is what stops a pull from duplicating occurrences.
3. Visibility: owner/assignee/workspace managers; tenant isolation.
4. API `/api/v1/planner/tasks` CRUD, `POST …/{id}/complete`, `POST …/{id}/reschedule`; `/app/planner` list/board using the existing design system.
5. Chat tool registration for creating/listing planner tasks (typed tool, P11-T09 rules).
