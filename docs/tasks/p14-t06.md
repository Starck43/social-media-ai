# P14-T06 — Trusted on-premise portal hosts administered at runtime

Owner request 2026-11-04: a workspace owner cannot depend on the deployment owner
to edit environment configuration before every on-premise Bitrix24 portal can be
connected.

## The gap this closes

`app/integrations/bitrix24/portal.py` accepts an on-premise portal only when its
host appears in `allowed_onprem_domains`. No caller passes that argument today, so
on-premise portals cannot be connected at all. Even with a populated list, the
OAuth egress guard in `app/integrations/oauth/network.py` rejects any host that
resolves to a non-global address, so a portal in a private network fails anyway.

The list itself is correct as a security control: the portal form makes **our**
server issue outbound requests, and an unconstrained list turns it into an SSRF
pivot into the host's internal network. The defect is that the control is
unreachable, not that it exists.

## Contract

1. Trusted hosts move from a constructor argument into a **runtime store** that the
   installation owner edits through an admin surface. No deployment restart, no
   release and no environment edit is required to add or remove an entry.
2. An entry is one of:
   - an on-premise portal host (`crm.company.ru`) trusted as a public on-premise
     portal;
   - a host inside a private range, which additionally authorizes that resolved
     address for the OAuth egress guard. Authorization is per host **and** per
     resolved address; a host whose addresses change is re-checked on the next
     connection attempt and fails closed if any new address was not authorized.
3. Every change — added, removed, who made it and when — is recorded in the audit
   trail. The store is installation-level, not tenant-level: a tenant may use a
   trusted host, but no tenant can add one.
4. A workspace owner connecting a portal that is not trusted gets an explicit,
   actionable refusal (`portal_host_not_trusted`) that names the domain and states
   that the installation administrator must authorize it. Never a silent failure
   and never a generic validation error.
5. The store fails closed: unavailable, unreadable or empty means no on-premise
   host is accepted; cloud portals keep working regardless.

## Out of scope

- Cloud portals: unchanged, accepted by suffix without any entry.
- The application credentials from P14-T05: separate secret, separate task.
- Any per-tenant override. If the owner later wants one, it is a new decision.

## Doubt and rollback

Whether the trusted-host store lives in the main database or in deployment-level
configuration the runtime reads and reloads. Recommendation: a small
installation-level table, because the audit requirement and the admin surface both
need it, and because it is the only option that satisfies "no restart". If the
implementer finds a concrete reason against a table, the fallback is a reload-on-
change file, and the card must say so before code moves. Rollback for either
choice: the guard stays, so reverting the admin surface restores today's
"cloud only" behaviour without a data risk.

## Evidence required

Focused tests for: add/remove through the admin surface, audit record per change,
a tenant unable to add an entry, on-premise refusal message, private-range
address authorized only for a trusted host, a host whose DNS answer changes now
failing closed, and cloud portals unaffected. If a migration is added, it is
`0137` and needs the usual `up -> down -> up` round-trip on the isolated schema.
