## Scope and acceptance

Complete the user journeys on top of the existing source, scenario, task,
schedule and digest pages and the shared task contract. Treat the AI chat as the
primary workspace for the entire lifecycle: request, clarification, preview,
execution, progress/status, results and follow-up. It must not be a secondary
launcher that sends the user to forms for the main workflow. Keep every
management page directly accessible for setup, review and editing, and preserve
the current design.

The task composer exposes the six universal input groups: goal, data, processing,
result, timing and limits. It uses the existing typed definitions and the same
server validation/services as web forms, API, CLI, admin and agent tools. The
same definition round-trips through create, edit, preview, run and result views.
Source selection distinguishes existing selected sources, requested-scope
discovery and all permitted sources; temporary discovered targets do not become
permanent shared Sources without user action. Scenario methodology remains
separate from task scope and source selection. One-off research stays within
existing limits; schedules and external sends retain their confirmation gates.

Accept when an owner can start and finish a permitted collect/analyze task in
chat, inspect progress/results and follow up there; can independently manage
sources, scenarios, tasks, schedules and digest settings; and can reopen the
same task through the direct web pages. API, CLI, admin and agent tools preserve
the same data-window, source-scope, scenario, payer and authorization semantics.
Preview, denied permission, stale form, revoked connection, partial results and
cross-workspace cases fail closed and remain understandable. Verify the primary
entry screen in the existing shell while preserving existing routes, overview
and deep links. This is user-journey acceptance, not a visual redesign.
