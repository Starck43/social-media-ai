# P14-T08 — Trusted on-premise portal hosts administered at runtime

Owner request 2026-11-04: a workspace owner cannot depend on the deployment owner
to edit environment configuration before every on-premise Bitrix24 portal can be
connected.

Status 2026-11-04: **DEFERRED** by the owner — no on-premise customer yet, and the
security layer it needs is no longer built here.

**Superseded in part by [P14-T09](p14-t09.md).** The registry, the egress seam, the
admin surface and the audit trail moved there, because 1C, IMAP and CalDAV need the
same control and a per-connector copy would be one guard per provider instead of one.
What stays in this card is the **Bitrix24-specific form**: the `portal_domain` field
behaviour, the `portal_host_not_trusted` message for a workspace owner and the
"this portal was authorized by the installation administrator" state. Resume this
card once [P14-T09](p14-t09.md) is accepted; its sections below describe the form on
top of that seam.

## The gap this closes

`app/integrations/bitrix24/portal.py` accepts an on-premise portal only when its
host appears in `allowed_onprem_domains`. No caller passes that argument today, so
on-premise portals cannot be connected at all. Even with a populated list, the
OAuth egress guard in `app/integrations/oauth/network.py` rejects any host that
resolves to a non-global address, so a portal in a private network fails anyway.

The list itself is correct as a security control: the portal form makes **our**
server issue outbound requests, and an unconstrained list turns it into an SSRF
pivot into the host's internal network. The defect is that the control is
unreachable, not that it exists.

## Current wiring (read before changing anything)

- `BITRIX24_OAUTH_METHOD.allowed_hosts` in `app/integrations/catalog/__init__.py` is a
  **static tuple** of cloud suffixes. It is what the egress guard actually consults.
- `Bitrix24Service.__init__(allowed_onprem_domains=())` and `_allowed_hosts_for()` in
  `app/integrations/bitrix24/client.py` take the other half, and `bitrix24_service` is a
  **module-level singleton** created at import. Anything read at construction time is
  frozen for the process lifetime — which is exactly why an env edit needs a restart.
- `POST /api/v1/integrations/bitrix/connect` and the `/app/settings/oauth/bitrix24/*`
  web routes reach `start_oauth_connect`, which is the single place a portal domain
  enters the system after `normalize_portal_domain`.
- Installation-level authorization already exists as a concept: `perms.is_superuser_role`
  in `app/web/deps.py` and `tenant_filter_context`. There is no separate installation
  admin role; a superuser is the installation owner.

## Contract

1. Trusted hosts move from constructor arguments into a **runtime store** that the
   installation owner edits through an admin surface. No deployment restart, no
   release and no environment edit is required to add or remove an entry.
2. An entry is one of:
   - an on-premise portal host (`crm.company.ru`) trusted as a public on-premise portal;
   - the same host marked `private`, which additionally authorizes **each resolved
     address** for the OAuth egress guard. Authorization is per host **and** per
     resolved address: the next connection attempt re-resolves DNS and fails closed
     if any address was not authorized.
3. Every change — added, removed, who made it and when — is written to the audit
   trail. The store is installation-level: a tenant may use a trusted host, no
   tenant may add one.
4. A workspace owner connecting a portal that is not trusted gets an explicit,
   actionable refusal (`portal_host_not_trusted`) naming the domain and stating that
   the installation administrator must authorize it. Never a silent failure and
   never a generic validation error.
5. The store fails closed: unavailable, unreadable or empty means no on-premise host
   is accepted. Cloud portals keep working regardless.

## The Bitrix24 form, as the owner asked for it

Two screens, both existing surfaces extended rather than invented:

**A. Workspace owner — connect a portal.** The existing field
`Field("portal_domain", …, example="company.bitrix24.ru")` stays the only input.
Behaviour by case:

| Input | Result |
| --- | --- |
| cloud suffix | accepted as today, no trusted entry, no change |
| trusted on-premise host | accepted; the form states it was authorized by the installation administrator |
| untrusted on-premise host | `422 portal_host_not_trusted`, message names the domain and says who must authorize it |
| IP literal, `http://`, port, path, credentials, internal single-label host | unchanged rejections from `normalize_portal_domain` |

The field help text must say that on-premise domains require administrator
authorization, so the refusal is expected rather than surprising.

**B. Installation owner — authorize hosts.** New `/app/admin/trusted-hosts`:

- list: host, kind (`public`/`private`), last resolved addresses, added by/at;
- add: host and kind, validated with the same `normalize_portal_domain` plus an
  explicit "this is on-premise" flag — a cloud-suffix host needs no entry and is
  refused as redundant;
- remove: with a confirmation step; removing does not disconnect existing
  connections but the next re-authorization fails closed;
- every action gated by `is_superuser_role` and written to `action_audit_events`.

## Plan

1. `trusted_portal_hosts` model: `host` (unique), `kind` (`public`/`private`),
   `resolved_addresses` (JSON list, informational), `created_by_actor_id`,
   `created_at`. **Installation-level: no `tenant_id`** — this is the platform-wide
   technical row the 2026-11-04 exception allows, because it holds no customer data
   and is global by nature. Record that citation in the model docstring.
2. Migration `0137` or `0138` (see the collision rule) creating the table and, if
   audit codes are added, extending `ck_action_audit_events_action` from
   `audit_check_sql()`.
3. A resolver seam, `trusted_portal_hosts()` cached per request and **not** per
   process: read once per connection attempt so an admin change applies without a
   restart. Feed it into `Bitrix24Service` through an argument, not the singleton's
   constructor, so tests can inject.
4. Egress: extend the guard so a `private` entry authorizes the concrete addresses
   it lists; re-resolve on every attempt and fail closed on any mismatch.
5. Admin surface `/app/admin/trusted-hosts` and the workspace-owner refusal message.
6. Refusal precedence: `portal_host_not_trusted` is returned before any network call.

## Out of scope

- Cloud portals: unchanged, accepted by suffix without any entry.
- The application credentials from P14-T07: separate secret, separate task.
- Any per-tenant override. If the owner later wants one, it is a new decision.
- Self-hosted providers other than Bitrix24. The seam must be provider-neutral, but
  only Bitrix24 is wired in this task.

## Doubt and rollback

Whether the store lives in the database or in a file the runtime reloads. The
database is chosen: the audit requirement and the admin surface both need it, and a
reload-on-change file cannot satisfy "written to the audit trail". Rollback: the
guard stays, so reverting the admin surface restores today's "cloud only"
behaviour; the table can be dropped in the downgrade without touching connections.

## Evidence required

- admin add/remove with audit rows, and a non-superuser refused on the admin route;
- a tenant user cannot add an entry but can use a trusted one;
- untrusted on-premise refusal carries the domain and the actor-facing message;
- `private` entry authorizes exactly its listed addresses; a host whose DNS answer
  changes fails closed on the next attempt;
- cloud suffix accepted with an empty store;
- empty or missing table → cloud only, no error;
- migration `up -> down -> up` on the isolated schema.
