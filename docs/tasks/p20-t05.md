# P20-T05 — Review-gated isolated browser execution pilot

Registry: [ROADMAP](../../ROADMAP.md#p20); status, owner and dialogue live there. Parent: [P20](../phases/p20-proactive-assistant.md). Request: https://app.notion.com/chat?t=40fa7457748980d094a100a930619250

## Goal and dependencies

Assess whether one explicitly authorized source requires a browser fallback that the official API cannot provide; prefer official APIs and the existing connector/egress controls. First deliver a threat model and cost/operations decision, then only after separate owner approval implement one default-off, read-only isolated pilot. No pilot is a dependency of social triage, approvals or specialist delegation.

## Scope and safety gates

- Establish permitted source, terms, account owner, actor/tenant scope, consent, allowed hosts and action types; no bypass of access controls, private communities, unsupported API profiles, CAPTCHA or anti-bot controls. A login/challenge must pause for an authorized human where supported; otherwise fail closed. The user request does not itself authorize live access.
- Define a hardened, disposable execution boundary, not merely “Docker is safe”: least privilege, no host runtime/DB/socket/secret mounts, per-run isolated workspace and browser profile, constrained CPU/memory/time/storage/processes, clean teardown and verified deletion. Select infrastructure only after comparing alternatives and obtaining owner approval for cost/operations.
- Route egress through reviewed destination validation and network isolation, including redirects, DNS rebinding and local/private/metadata-address refusal unless separately authorized by existing policy. Enforce server-side action allowlists; fetched pages and scripts are untrusted. Disallow shell or arbitrary script access in the initial pilot.
- Credentials remain outside agent prompts, logs and screenshots; if a secure user-assisted login cannot be implemented, do not enable authenticated browsing. Treat captured data under current tenant, source, retention and local/cloud boundaries; recheck rights and revocation per run.
- Read-only fixture pilot must not click send/delete/purchase, solve CAPTCHAs automatically, perform live collection, add a dependency or deploy before the applicable owner/security review. Preserve one runtime owner and existing queue/kill switches.

## Acceptance and checks

- Document source-specific authorization and API gap, attack surface, lifecycle, credential model, costs, failure modes, rollback and security review. Prove isolation and cleanup against cross-tenant, secret-exfiltration, prompt-injection, SSRF/redirect/rebinding, resource exhaustion, revocation and denied-action fixtures; use mocked/local targets, not real accounts.
- Explicit owner decision is required before selecting paid/infrastructure components, live source checks or activation. If those prerequisites are unavailable, stop at the threat model and report the remaining evidence rather than claim a production-safe sandbox.

## Open doubts

The runtime isolation mechanism and operations cost are unselected. Default: no new infrastructure or live browser; reversible by removing the proposed pilot. A concrete cost, risk and rollback proposal requires owner review before implementation.
