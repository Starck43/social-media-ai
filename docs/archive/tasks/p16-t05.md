## Lock order and erased-identity limit

- **Owner clarification:** for a deleted and recreated contact with a new ID, a previously orphaned year should remain closed if identity can be recovered; otherwise document the limit. The orphan row stores no stable identity and `contact_id` is NULL, so it cannot be matched to an independently recreated contact. Consequently a new ID may generate the same event/year again. ## Unmerge returns the source's own event (`3cca39a8`)

- **Reported defect:** `unmerge_event_lineage` only restored a task version and a claim, so after a merge of two closed events the restored contact kept no run and got no tasks back; a `fire` then either regenerated an event or duplicated rows. The previous record did not prove this contract.
- **Schema (0145 edited in place, no new migration):** `planner_event_groups` gains `origin_contact_id` (NOT NULL), `event_type`, `year`, and `origin_run_id`, plus the unique `(tenant_id, origin_contact_id, event_type, year)` and the two key check constraints. `planner_event_claims` gains nullable `originated_contact_id`. Together they make the link unambiguous by recorded origin, contact and event key — never by year or name.
- **Merge contract:** the survivor keeps its run, its own group and its own claim. Every closed key the source brings either moves the source's run to the survivor (when the survivor closed nothing) or is recorded beside the survivor's group under `origin_contact_id=source_id` with the run that held it; the survivor then gets a claim naming the source as origin (or its own claim gains that marker).
- **Unmerge contract:** for every marked claim or recorded group it moves that group's tasks back from whoever holds them now (which may be the survivor of a later merge), deletes the recorded group, drops the marker or merge-only copy, and hands the source a run and claim that fully own the returned tasks. A run already backing the survivor's own event is never taken. Nothing is regenerated and the survivor's event is untouched.
