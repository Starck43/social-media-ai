# P15-T12 — Restore Telegram FloodWait deferral in the guarded runtime

Registry: [ROADMAP](../../ROADMAP.md#p15); status/owner/dialogue live there.  
Parent: [P15](../phases/p15-communication-hub.md) · Related: [P15-T11](p15-t11.md), [P12-T14](../audit/p12-t14.md).

## Problem

The rate-limit contract in `app/services/social/rate_limit.py` and [COLLECTION](../COLLECTION.md#platform-rate-limits) says a long Telegram FloodWait is reported as `SourceRateLimited` and recorded as `rate_limited`. The guarded personal Telegram runtime currently converts provider exceptions to `AuthorizationUnavailable`. The runtime is default-off; do not infer an active production rollout. The behavior was reproduced with synthetic provider errors, no database or network; see [T11 diagnostic](https://github.com/Starck43/social-media-ai/pull/426#issuecomment-6686513575).

## Routing diagnosis (source `66645e05`)

- `credential_exception_status()` classifies FloodWait as the string `error: rate_limited` for connection diagnostics (`tg_session.check_session`); it is not a collection outcome and is not called on the guarded collection path.
- `BaseClient._fetch_page()` maps HTTP/VK response limits to `SourceRateLimited`; personal Telegram collection branches to `collect_personal_telegram()` before obtaining that client and never calls `_fetch_page()`. The base helper is not itself a Telethon exception handler.
- The real history loop in `_telegram_history_batch()` sees a Telethon exception, but the outer generic `except Exception` converts it to `AuthorizationUnavailable`; `ContentCollector` therefore cannot catch `SourceRateLimited` for the deferred outcome. `telegram_flood_wait_seconds()` in `rate_limit.py` recognizes Telethon FloodWait but has no caller in current `app`.
- The T11 double was checked against the real history loop using synthetic errors; no live provider or DB was used. Confirm the route on fresh source before proposing a fix; distinguish reuse of the existing collection contract from changing the diagnostic or expanding a contract. [Owner clarification](https://app.notion.com/chat?t=410f361cdc99804388b100a96e9837bc).

## Scope

Investigate and restore the documented long-FloodWait deferral through the guarded runtime and collection outcome path, or explicitly resolve any contract conflict with the owner before changing it. Preserve default-off gating, authorization, fencing, redaction, bounded reads, cleanup and cursor/transaction safety. Do not introduce automatic retries, unbounded waits, live provider calls or old-session fallback. P15-T11 is test hygiene only and must not change production behavior.

## Acceptance and checks

- A fake long FloodWait reaches the collection outcome as a distinct rate-limit deferral, not an authorization or empty result; bounded retry-after information is handled safely.
- No partially read items or cursor updates are admitted on deferral; disconnect and guard cleanup remain effective. Ordinary errors stay fail-closed without leaking provider details.
- Focused tests cover the guarded runtime and collection/job outcome, plus relevant regression tests. Record exact commands, environment, SHA and counts. DB/integration and activation evidence remain separately governed; no live credentials or network sends.
- Identify and reconcile any changes to the documented contract or user-visible behavior with the owner; do not silently relax existing security checks.
