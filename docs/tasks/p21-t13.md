# P21-T13 — Unified model catalog, plan grants and generation policy

Registry: [ROADMAP](../../ROADMAP.md); parent: [P21](../phases/p21-ai-operations.md).

Prerequisites: [P21-T12](../audit/p21/p21-t12.md), [P2-T17](../audit/p2/p2-t17.md) accepted dormant tariff storage increment.

## Goal and predecessors

Make superuser-curated tariff models and personal/BYOK models equally usable
through one catalog service, without per-user copies of managed models or weaker
personal-key authorization. P21-T12 is the normative dispatch/access contract;
P21-T15/T16/T14/T11 must provide admission, settlement, operational limits and
credential controls before managed routing is activated. No commercial activation,
public apply or irreversible change is authorized by this planning card.

[P2-T17](../audit/p2/p2-t17.md) owns the single user-level tariff, module grants, owned-space
limit and token policy. Consume its plan-holder interface before granting managed
access; do not independently configure a tariff on each tenant. Catalog additions
can remain dormant while this prerequisite is implemented. This card owns model
grants/metadata, not token accounting, subscription prices or checkout.

## Owner and invitation policy

The holder's tariff applies to every owned workspace. In an invited workspace,
eligible models are the host owner's plan-granted platform models and host personal
catalog; the invitee's tariff/catalog never substitutes. Execute only through P21-T12's
permission-scoped, explicitly consented delegation. Any invited role is denied
host tariff/catalog/provider/key/model/default management server-side. Model
selection settings remain owner-controlled; using configured models is not CRUD.
Users can independently configure their own personal catalog for their own context.

## Proposed relations and constraints

1. `llm_catalogs(id, kind, owner_user_id, is_active)`: initially platform and
   personal only. CHECK platform owner is NULL and personal owner is NOT NULL;
   restrictive owner FK. A partial unique index on `kind` WHERE platform enforces
   one platform catalog; a partial unique index on owner WHERE personal enforces
   one personal catalog per user. Plain UNIQUE with a nullable owner is insufficient.
   Do not add a speculative workspace kind/column; credential sharing is separate.
2. Reuse `llm_providers`/`llm_models` and their global IDs. Both current
   `owner_user_id` columns are NOT NULL; their composite owner FK and provider
   owner/uid uniqueness cannot accommodate platform rows. Add non-null
   `catalog_id`, provider UNIQUE `(id, catalog_id)` and a model-to-provider
   `(provider_id, catalog_id)` FK. Publish the transition of owner NOT NULL,
   `uq_llm_provider_owner_uid`, `uq_llm_provider_id_owner` and
   `fk_llm_model_provider_owner`; add/backfill/check before retiring old guards.
   Catalog is the final custody authority. Retained compatibility owner columns
   must agree with personal catalog ownership and be NULL for platform rows,
   enforced by a named cross-table guard, not two writable authorities. Replace
   unconditional `__personal_scoped__` managers/decrypt paths with funding-aware
   authorization before exposing platform rows; no broad owner-OR-platform query.
3. Unique `(catalog_id, provider.uid)` and `(provider_id, model_id)` only after
   duplicate/data inventory and an explicit mapping. Keep the API model key as a
   string on its catalog row; do not rename it just to match external sample DDL.
4. `plan_model_grants(plan, capability, llm_model_id, is_active, priority, is_default)`:
   numeric `llm_model_id` FK to `llm_models.id`, never the string API `model_id`;
   unique `(plan, capability, llm_model_id)`; partial unique `(plan, capability)`
   WHERE `is_active AND is_default`. Grant only active platform rows supporting
   the capability. Defaults/ordering are capability-specific and deterministic.
   Name the DB guard for platform-only membership (a plain model FK is not enough)
   and the service recheck for active/capability support at admission. Plan policy
   is the P2-T17 authority; initially use its existing validated plan set. Future
   dynamic plan definitions must be delivered there, not duplicated here.
5. Personal eligibility uses the existing capability policy and owner/consent
   scope, not one grant per personal model. During transition curated eligibility
   is the intersection of grant, active catalog/provider/model, capabilities and
   holder tariff/module policy. Remove duplicate packaging rules only after consumer
   migration; no permissive fallback on a denied plan or invalid selection.
6. Managed providers use allowlisted deployment-secret refs, personal providers
   use the existing encrypted BYOK path. Enforce source exclusivity and server-side
   catalog custody. No platform row contains personal ciphertext and no personal
   row uses a managed secret ref; define the cross-table custody guard from P21-T11.
   Public model metadata cannot expose secret fields/ref internals.

## Column mapping and lifecycle requirements

- Replace CSV `model_type` with validated operation/input/output capability
  storage and an explicit legacy-to-new mapping. Its existing String(20) cannot
  grow safely; grant capability keys and legacy `PLAN_LIMITS.model_types` must
  migrate together. Product module entitlement keys remain in P2-T17, not here.
- Separate model context window and hard output-token ceiling from current
  `max_tokens` generation defaults. Define precedence with scenario/tenant/purpose
  settings and tariff limits; a model output ceiling is not a total allowance.
- Current input/output prices are Float with `_per_1k` names but a configurable
  token unit. Specify Decimal/Numeric precision, NULL/explicit-zero semantics and
  old/new units/field mapping; never relabel historical receipts or reinterpret a
  legacy zero as proof of free pricing. Retain explicit FREE/PRICED/UNDEFINED.
- `llm_models.is_default` is not the managed plan default. Retain only a documented
  personal-catalog purpose or retire it after consumers migrate; managed defaults
  live in grants. Default choice and ordering must remain deterministic.
- Inventory `DateTime` health/test columns without timezone and their actual
  timestamp meaning before conversion; P21-T14 decides whether measured hot health
  state moves. Do not guess the timezone of legacy values.
- Deactivation is the ordinary retirement path. Existing scenario/tenant model
  FKs use SET NULL and provider ORM relationships use delete-orphan/CASCADE;
  inventory both before revising lifecycle. Disable raw managed deletion and
  protect explicit selections from delete-to-NULL automatic defaulting. A proposed
  RESTRICT FK/ORM migration needs retained-data tests and separate apply approval;
  do not change unrelated personal deletion semantics incidentally.

## Parameter and selection policy

- Model identity owns supported API operation/input/output capabilities, context
  and hard output limits, adapter-supported parameter metadata and prices. Replace
  CSV capabilities compatibly; vision input and image generation are distinct.
- Generation defaults belong to tenant/scenario/purpose policy. Reuse current
  columns and typed code defaults; add bounded, versioned JSONB only for actual
  modality-specific consumers. Do not add a generic `agents`/profile table yet.
- Requested output is limited by model/provider ceilings, approved plan bounds
  and purpose policy. Validate temperature/top_p/response schema against the
  selected endpoint; omit unsupported parameters. Retry/timeout/tool-loop limits
  remain restrictive server execution policy, not arbitrary request JSON.
- Do not invent a universal `temperature_ceiling` as a financial budget. Per-model
  supported ranges and fixed/absent parameters differ; monetary bounds need the
  reviewed reservation contract, including input/cache/media costs.
- Preserve explicit personal selections and consent-bound workers. Changing NULL
  to a plan default is an explicit compatible migration, not an automatic rewrite
  of scheduled jobs. No managed/BYOK switch without informed selection and new
  admission with the proper payer; ordinary fallback keeps cost class and payer.

## Steps and acceptance

### Executor sequence and storage-only gate

Require the P21-T12 typed resolver and accepted P2-T17 holder/tariff storage; consume
P21-T11 credential field/version rules. Start at `app/models/llm/`, model/provider
managers, `app/services/ai/personal_catalog.py` and all selection/serializer callers.
Publish a field-by-field old/new map with types, nullability, defaults, indexes,
FK/custody guards and consumer migration order before DDL. Add/backfill personal
catalogs preserving IDs first; add managed metadata and grants second; migrate
owner-only CRUD/default reads third. Keep managed HTTP off throughout.

Catalog acceptance covers storage/metadata/authorization/migration parity with
mocked seam interfaces. It does NOT require T14–T16 completion. Runtime activation
belongs to the phase gate after T16; no circular dependence on later admission.

1. Inventory catalog queries, owner predicates, task consent, FKs, pricing units,
   duplicates and serializers. Publish an old/new field mapping and rollback.
2. Add catalog/grant structure without changing dispatch; backfill existing rows
   without losing IDs, ownership, payer consent or historical snapshots.
3. Use the P21-T12 resolver across chat, analysis, digest, tools and probes. Cache
   non-secret grant metadata only; use revision/invalidation plus a fresh admission
   check so downgrade/revoke cannot keep an unauthorized cached model usable.
4. Superuser admin can assign/order/default models per plan and capability. Owners
   see eligible managed models and their personal catalog, clearly labelled;
   invitees see only safe metadata for models available in the host context.
   No per-user model copies or repeated configuration in each public surface.
5. Test cross-owner/catalog/grant denial, downgrade/revoke while queued, forged
   model IDs, default races, capability mismatch and both forbidden fallback
   directions. Include accepted legacy consent-bound scheduled execution,
   invited-admin model/tariff CRUD denial, explicit owner delegation and a user
   whose own tariff is higher/lower than the host's. Test cross-catalog FK failure,
   NULL-owner platform uniqueness and retirement without selection loss.
6. Measure representative hundreds-concurrent mocked workload, DB pool and lock
   waits. P21-T14 owns shared quota buckets; optional health-state relocation needs
   measured contention, not an assumption that a table count determines capacity.
7. Only then consider removing `tenants.agent_model` or model generation-default
   columns. Resolve ambiguous legacy names explicitly; never pick the first match.

Required evidence: focused tests; isolated Alembic upgrade/rollback and retained-
data protection; metadata/FK/API parity; complete schema inventories and synthetic
cleanup; direct source/checked-SHA handoff. Additions, removals, consumers and
rollback rationale are reviewed individually. Public apply requires separate approval.

## Rejected shortcuts

No parallel `platform_*` or modality catalogs; no arbitrary `owner OR platform`
filter; no polymorphic model IDs; no generic vault losing FK/custody guarantees;
no universal quota table mixing policy, actual charges and throttle counters.
Shared IDs simplify reuse but do not themselves authorize secret access.
