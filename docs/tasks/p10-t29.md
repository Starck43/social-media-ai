# P10-T29 — `setup_test_db --reset` for migration-aligned schemas

Registry: [ROADMAP](../../ROADMAP.md#p10); current status/owner live there.

Parent: [P10](../phases/p10-audit-hardening.md). Found during the P8-T37
audit closeout on 2026-10-26 ([PR #245](https://github.com/Starck43/social-media-ai/pull/245)).

## Scope and acceptance

`python -m scripts.setup_test_db --reset` aborts with
`Budget reservation is immutable` when the seeded test schema carries the
migrations' guard triggers (`llm_budget_reservations_no_truncate` from 0095,
plus the other `*_no_truncate` guards from 0093–0100 on the billing
evidence tables): `_truncate_all` issues one `TRUNCATE` for every base table,
and the `BEFORE TRUNCATE` statement triggers refuse it. Schemas that were
aligned through `alembic upgrade` in a session (for example during the P8-T29
0112 migration run) carry those triggers; schemas built from
`create_all` alone do not, which is why the failure depends on the schema's
history.

Accept: with guard triggers present, `--reset` truncates, re-seeds the
reference rows and leaves every guard installed, so
`LLMBudgetManager.reserve_receipt`'s `GUARDS` check still sees all three
guards enabled on `llm_budget_reservations`. Guard-free schemas behave
exactly as before. Regression suite: `tests/infra/test_p10_t29_reset_guard_triggers.py`.

Owns: the reset path of `scripts/setup_test_db.py` and the new infra suite.

Not owned: trigger DDL and migrations, `tests/conftest.py` schema validation,
any application code.

## Context

The reset path is the script's only destructive writer; it may bypass the
guards only transaction-locally — disable them around the `TRUNCATE` and
re-enable before the transaction commits, so a failure rolls back both and
the installed guards are unchanged for the next reader.
