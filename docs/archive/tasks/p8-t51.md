# P8-T51 — Widen job_type so the bootstrap creates every default task

Archived 2026-11-18: accepted `f1efe064`, merged `4c15a235` — [audit](../../audit/p8/p8-t51.md).

Registry: [ROADMAP](../../../ROADMAP.md#p8); current status/owner/dialogue live there.
Parent: [P8](../../phases/p8-first-value-ui.md).
Related: [P8-T41](../../archive/tasks/p8-t41.md) — the seed defect was found while resuming its live journey.

## Scope and acceptance

`AgentTask.job_type` and `Job.job_type` are `varchar(20)`, but three entries in
`app/tasks/bootstrap.py::DEFAULT_TASKS` are longer: `comms.outbox.dispatch` (21),
`documents.approvals.expire` (26), `planner.reminders.dispatch` (26). Startup
`ensure_all_default_tasks()` therefore aborts on the fifth default task, leaving
only the four short-type tasks in a workspace. P8-T41 worked around this with a
bounded launcher; this task removes the workaround's cause.

Fix by widening both columns (placeholder revision `p8t51_job_type_width`,
`down_revision` set to the live `dev` head at implementation time) and updating
the two ORM models. Do not rename the job types: `app/jobs/dispatcher.py` has
lazy handler imports keyed by these exact strings, so renaming changes an
accepted dispatch contract and leaves orphan handlers.

Accept only when:

- all `DEFAULT_TASKS` job types fit the new column width in both models;
- a fresh `ensure_all_default_tasks()` creates every default task on an
  isolated schema, including the three long-type ones;
- the migration cycle (upgrade, empty downgrade, refused downgrade with data,
  single-head check) passes on an isolated schema at the graph that lands;
- focused regression tests pass and no synthetic rows remain;
- the same revisions and behavior are validated before the separately
  authorized apply to `public`.

## Ownership and dependencies

Executor: opencode. Owner authorized the fix **and the `public` apply** on
2026-11-18 in chat. No dependency on P8-T41 acceptance; the P8-T41 fixes are
already integrated on `dev`. Branch: `type/p8-t51-job-type-width`.

Schema-wide caveat: widening `varchar` to a larger `varchar` is a metadata-only
change in PostgreSQL; it does not rewrite rows and no stored value changes.
The integrator assigns the numeric revision at merge; this card records only
the placeholder and its live-head dependency.

## Implementation and evidence (2026-11-18)

Executor: opencode; branch `type/p8-t51-job-type-width` from claim revision
`628d8d47`. Placeholder revision `p8t51_job_type_width`, `down_revision`
`p12t15_policy_audit` (live head confirmed with `ScriptDirectory.get_heads()` at
implementation time). Migration file `migrations/versions/p8t51_job_type_width.py`
widens `agent_tasks.job_type` and `jobs.job_type` from `String(20)` to
`String(64)`; both ORM models were updated to match. No job type was renamed.

Isolated validation on a task-owned `p8t51_schema` (Alembic run with a plain
`postgresql://` URL so the sync engine is used, `DB_SCHEMA=p8t51_schema`):

- `upgrade head` → both columns `varchar(64)`, head `p8t51_job_type_width`.
- `ensure_all_default_tasks()` created **10** tasks, including
  `comms.outbox.dispatch` (21), `documents.approvals.expire` (26) and
  `planner.reminders.dispatch` (26); synthetic role/user/tenant/tasks were then
  deleted and verified at zero.
- `downgrade p12t15_policy_audit` with a long job type present was **refused**
  with `StringDataRightTruncation`; the transaction rolled back and the head
  stayed at the new revision.
- Empty downgrade succeeded (widths back to 20), re-upgrade succeeded (widths
  64); `alembic heads` reported one head.
- `schema_inventory.py` before/after diff exit 0 with no output. The isolated
  schema was dropped afterwards.

Public apply (owner authorized 2026-11-18): `public.alembic_version`
`p12t15_policy_audit` → `p8t51_job_type_width`; both columns are now
`varchar(64)`; nothing else changed — the public inventory diff reports only
the revision line. The migration created no default tasks and no synthetic rows
on `public`; the remaining defaults will appear on the next normal startup.

Checks: `tests/jobs/test_p8_t51_job_type_width.py` 4 passed; combined with
`tests/jobs/test_p8_t41_research_journey.py` and
`tests/jobs/test_p8_t40_checkpoint_db.py` 18 passed (one pre-existing
MovedIn20Warning). Black/isort check clean on all four changed source/test files.
No full suite was run (no owner request).

Handoff for the integrator: `public` is stamped with the placeholder
`p8t51_job_type_width`. Either keep that named revision as the final id, or, if
it is renumbered at merge, update the `public.alembic_version` row to the
assigned id in the same integration — the DDL body does not change, so no new
migration cycle is needed.
