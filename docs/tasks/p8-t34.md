## Selected scope and boundaries

The owner selected and scheduled a Yandex Disk read-only pilot in P12: one user-
selected folder, no write or delete. First develop a fail-closed folder policy
foundation and focused tests; then build the reviewed adapter, authorized connection
and safe read-only user flow in separately reviewable commits. A provider-wide
OAuth read grant is not equivalent to one-folder provider permission; disclose it
and enforce the root in the application. No provider credentials or live account
operations, external writes, deployment or public migration are authorized by this
claim. The unrelated credential-security task P12-T14 retains its own scope.

User-requested per-folder restrictions must protect against accidental mutation:
read-only is the pilot maximum; child folders may be made more restrictive, never
more permissive than their ancestors. Distinguish folder controls from later write
capabilities, which require a separate task, review and explicit enablement.

## Acceptance and gates

- Provider calls, data model, storage/retention, quotas, failure/revocation, current
  ACL and ownership must be specified and reviewed before connection activation.
- Enforce tenant and personal-owner/share checks on every operation. Validate paths
  component-wise, deny unknown operations and prevent mutation regardless of input.
- Focused tests must cover nested restrictions, traversal/encoding, sibling roots,
  unknown operations, revocation and tenant/owner separation at integrated routes.
- Keep existing 0122 data; migrations only in isolated test schema unless separately
  authorized after backup. Mock providers; do not run the full suite.
- Honest capability/status and safe original-open: no public links, arbitrary URL
  redirect, broad permissions claim or invented provider revision semantics.
- Record exact commits, relevant documents, tests and unrun integration limits.

## Initial implementation handoff (in progress)

- The first two commits add a restrictive-only folder policy and a bounded,
  metadata-only Yandex Disk page reader. They do **not** register a provider,
  connect credentials, create a UI, authorize actors, persist policy or implement
  original opening, extraction, synchronization or any write/delete operation.
  The reader requires its caller to enforce current tenant, actor, owner/share,
  connection and revocation rights; it is not an independently safe web endpoint.
- The reader validates the selected folder and immediate returned children,
  filters child listings with the policy, caps response bytes/page size and reports
  offset truncation. Offset paging is not a snapshot; it must not be used to infer
  deletion. Literal `%` in paths is deliberately unsupported until the provider

## Local-dev connection form (in progress)

  supplies a token and one root; the form explicitly discloses disk-wide OAuth
