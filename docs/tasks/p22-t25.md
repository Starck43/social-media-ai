# P22-T25 — Make triage a plan step, and let a thread become a task

[Phase](../phases/p22-universal-tasks.md) · [Correspondence journey](../product/UNIVERSAL_TASKS.md#representative-journeys) ·
[Inbox triage audit](../audit/p20/p20-t09.md)

**Dependencies.** [P22-T04](../audit/p22/p22-04.md) (admission and worker),
[P22-T10](p22-t10.md) (correspondence vertical), [P22-T15](p22-t15.md) (commitment to task),
[P22-T24](p22-t24.md) (an executable canonical path).

**Blocks.** The owner's requirement that a task sort mail by importance, and any task that
should turn a triaged thread into work.

## Problem

Inbox triage exists, is accepted, and is good work — but it is unreachable from a task, and its
output cannot become one.

**Triage is not a plan operation.** `app/services/communications/triage.py` (P20-T09, accepted at
merge `8af6c870`) classifies a thread into `needs_reply`, `fyi`, `can_wait` or `uncertain` with a
deterministic metadata-first baseline and an optional paid-model refinement. It is a service, not a
step: `OPERATIONS` in `app/services/execution_plan_contracts.py:94-102` has seven entries and none
of them is triage. A task cannot ask for "sort my mail by importance".

**`mail.group_by_sender` is not importance.** It groups by sender identity
(`app/services/task_run_operations.py:164-171`), which is the journey [P22-T10](p22-t10.md) owns. The
owner now wants importance as well; nothing in the plan runtime computes it.

**Triage reads threads the plan never creates.** This is the deeper gap. `triage_thread`,
`triage_thread_record` and `list_triaged_threads` all operate on `MessageThread` rows
(`triage.py:1108`, `:802`, `:1202`). `MessageThread` and `UnifiedMessage` are written only by
`app/services/communications/ingest.py` (`:438`, `:731`), and `ingest` is called from exactly one
production path: `app/integrations/email/imap_sync.py:577`. Meanwhile `mail.read_headers` — the
plan's only mail operation — returns `[connection_id, folder, validity, uid, digest]`
(`task_run_operations.py:155-162`) and never touches `ingest`. So a plan that reads headers
produces no threads, and triage has nothing to classify. `ingest_max_update` and
`ingest_telegram_update` (`ingest.py:862`, `:776`) exist but have **no caller in `app/`** — only
re-exports in `communications/__init__.py`.

**A triage proposal cannot become a task.** `build_thread_proposals` emits
`proposal:planner_task:{thread_id}` with `title`, `priority`, `thread_id`, `contact_id` and
`target_service="workspace.planner"` (`triage.py:519-530`, `:570`). No route in `app/web/`
consumes it: a grep for `planner_task` in `app/web/` returns nothing. The proposal is a dead end.

## Deliverable

1. **Add a triage operation to the plan.** A `mail.triage` operation in `OPERATIONS` with
   `llm=True`, `input_port="mail"`, no `resource_kind` (it consumes a prior step's output, not a
   binding). It classifies the threads or headers produced upstream and emits a bounded
   `[thread_ref, category, reason]` list. Because `check_graph` enforces
   `bool(operation.llm) == (step.scenario_id is not None)`
   (`execution_plan_contracts.py:196`), the step carries a scenario — which is exactly the owner's
   "always add a scenario so the agent can work with the data".
2. **Close the read-to-thread gap.** Either `mail.read_headers` gains a persistence step that
   upserts through `ingest`, or a new `mail.ingest_headers` operation does it. Without one of the
   two, triage has no input and the importance sort cannot be scheduled. State which, and why.
3. **Let a proposal become a canonical task.** Wire `proposal:planner_task:{thread_id}` to
   `task_service.create` with the proposed `title`, `priority`, `thread_id` and `contact_id`, behind
   explicit human approval. This is the T15 boundary: triage proposes, a person confirms, the task
   is the record, the snippet stays evidence.
4. **Keep importance two separate things.** A task's «Важные» is `priority in (high, critical)`
   (P22-T18, `task_queries.py:183`). A thread's urgency is a triage category. Do not merge them into
   one flag: a task can be important without mail, and mail can be urgent without a task. The only
   bridge is the proposal in step 3, which copies a triage category into a task priority at approval
   time.

## Out of scope

- **Rewriting `triage.py`.** The classifier, its guards, its prompt-injection handling and its
  budget gate are accepted work. This card wraps it, it does not reimplement it.
- **A body cache or search index.** `D3`/`D11` forbid it and the triage docstring says so
  explicitly (`persisted_body_cache=False`, `indexed_body=False`). A triage step must work from
  metadata and transient previews only.
- **Sender grouping.** That is [P22-T10](p22-t10.md).
- **MAX as a platform.** `ingest_max_update` exists, but MAX is absent from `PlatformType`,
  `CAPABILITIES` and the provider catalog. Making it a real platform is
  [P22-T23](p22-t23.md)'s seam plus its own card.
- **The publisher and the runtime gap.** [P22-T24](p22-t24.md) owns those. This card adds one
  operation; it cannot make the other six run.

## Acceptance

A scheduled task reads a mailbox folder and sorts the result by importance: `mail.read_headers` (or
its ingest variant) produces rows, `mail.triage` classifies them through a scenario, and the run
result shows counts per category with a human-readable reason for each. A thread classified
`needs_reply` offers «Создать задачу»; approving it creates one canonical `Task` with the proposed
priority, and the task's card links back to the thread as evidence. Repeating the run creates no
duplicate tasks.

A triage step with no scenario is refused (`invalid_scenario_binding`), and a scenario with no
triage step is not silently ignored. No message body is stored or indexed by the step.
