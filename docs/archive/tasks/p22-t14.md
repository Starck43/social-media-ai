**Decisions taken by the executor** (owner delegated them):

1. The task session keeps `channel='web'` and the deterministic chat id
   `task:<task_id>:<user_id>`; a new channel would split runtime confirmation and
   cost paths that branch on `channel='web'`.
2. The binding references the canonical task, not a plan revision; scenario
   attachment is re-read from the newest published revision on every call.
3. Reading and delegating are separate capabilities: `available` covers an
   authorized history, `delegation` covers a new turn. Closed work or an attached
   scenario keeps the first and refuses the second with `task_closed` or
   `scenario_attached`; there is no delegation picker step.
4. Drafts stay client-side per conversation; no new draft table.
5. Open work is the canonical status `todo` or `in_progress`. A revision this code
   cannot decode counts as an attached scenario: fail closed for new delegation,
   keep the existing history readable.
6. Scenario name and step are granted metadata: they are returned only with
   `agentscenario:VIEW`. Without it the history and the delegation ban stay, the
   labels are empty.
7. The picker runs one bounded query: tasks are outer-joined to this actor's
   binding, filtered to a binding or open work, ordered by "has a conversation"
   first and newest task second, and cut at `limit` rows. Existing private
   conversations therefore keep their place, and the number of eligibility checks
   never exceeds the window.
8. T14 wires the server action, the `/chat` entry and the conversation selector;
   the card-level link on every unified surface stays T08's job, and the current
   `planner.html` link is left untouched until T08 replaces the surface.
9. The task drawer hosts the same `/chat` page in `embedded=1` mode instead of
   copying the transcript, composer and streaming markup into a second partial.
   T08 only includes `web/_task_chat.html` with the action's conversation and
   renders a trigger carrying `data-task-chat-open`.

**Access.** Reuse [effective workspace AI access](../../platform/TENANCY.md#web-ownerguest-context-and-membership-disable). An active owner can enter chat. An invited member needs active membership with `ai_chat_enabled`; the assigned workspace role controls tools and task visibility. Check this on listing, opening, reading and sending. Task sessions additionally require current task access. Sending a delegation also requires open work and no explicitly attached scenario. Even a workspace owner reads only their own conversation through these routes.

**Existing storage.** In the current workspace, [web_session_id](../../../app/agent/runtime.py) looks up the main session by web channel and user ID. [agent_sessions](../../../app/models/agent/agent_session.py) stores the session and [agent_messages.session_id](../../../app/models/agent/agent_message.py) owns message membership. Preserve existing main-session IDs and histories. Add a unique, tenant-checked binding from (workspace, user, canonical task) to one dedicated session. A session belongs to at most one binding. Read an empty conversation without creating rows on selection; allocate once on first send. Keep authenticated actor identity independent of the conversation selector.

## Implementation and handoff

1. Supply the actor-scoped delegation action only for an open canonical task with no scenario attached to its current plan. A configured but unavailable scenario still counts as attached. Recheck at send time. Use the user’s message and permitted task context for this conversation.
2. Expose the global conversation at `/chat` and preserve `/app/chat` as a compatible entry to the same conversation. For the drawer, resolve one persistent private conversation per (workspace, actor, canonical task). Reuse [AgentSession](../../../app/models/agent/agent_session.py) and its message store. Make concurrent first opens converge. Server-resolve the task title, topic and permitted context for each turn. The existing page-context chip and submitted task ID alone cannot establish this binding.
3. Extract the transcript, composer, streaming and message actions from the [web chat](../../../app/web/templates/web/chat.html) for both the full page and [right drawer](../../../app/web/templates/web/_chat_dock.html). Parameterize the [chat handlers](../../../app/web/chat.py) by authorized conversation scope, including history, attachments, drafts, feedback, clear/stop and pending confirmations. Scope prompt history and recall to the conversation. Guard against late responses when switching drawers. Keep model boundary, payer and confirmation checks on send and tool execution.
4. On a direct visit to `/chat`, show «Основной чат». Extend the [right sidebar task picker](../../../app/web/templates/web/_chat_workspace.html) to select an eligible task conversation or return to «Основной чат». In place, switch the center transcript, title and composer target together. On selection clear the old transcript from view while fetching; display empty/unavailable states explicitly. Keep selection per tab. Discard late history or stream updates for the previous selection, and clear the active view when the workspace changes. A pending confirmation remains with its original session.
5. Hand T08 the server action, accessible link and task-mode drawer. Clicking «Поручить агенту» opens the current task's conversation in place, with its title, prior messages and composer. Opening or closing that drawer performs no send, model call or task launch. On narrow screens use the shell's mobile drawer and return focus to the originating card on close.

## Acceptance

- In one workspace open global chat, task A and task B. A and B are open and have no scenario. Send a distinct message in each, switch while a response streams, close, reload and reopen. Each transcript, draft, confirmation and message action targets its own conversation. Both global URLs show the same global history.
- Start at the main session, select A then B rapidly in the sidebar, return to main, and open A from its card. Each view shows the expected saved messages, and a reply goes only to the displayed session. An empty or denied selection cannot send to the last conversation. Switching workspaces opens that user's main session in the new workspace.
- Exercise an owner and an invited member with and without effective AI access. Give the invitee chat access but withhold access to A: main chat works, A is absent from the picker, and direct access is denied. After granting A, both users see their own histories. Revoking the member's AI access blocks further reads and sends even from an already open tab.
- Open a drawer, then close the task or attach a scenario from another tab. All cards hide «Поручить агенту» and a stale send is refused. Existing history stays private and readable through the session picker while workspace chat and task access remain valid. Removing the binding from an open task restores delegation and resumes the same session.
- The first user message reaches the agent with the selected task and the user’s instruction. Exercise both themes, desktop and mobile with the same message rendering on both surfaces. Use a model double to distinguish opening the drawer from submitting a turn.

## Progress 2026-11-25 (conversation selector)

The right sidebar now carries a «Разговоры» section: «Основной чат» plus every
task conversation this actor already owns and every open task without an attached
scenario, both filtered by current task access. Choosing an entry calls
`selectConversation()`, which reads the transcript from the server's JSON branch
(`/chat?conversation=…`) and swaps it in place, so the page does not reload, the
composer keeps its Alpine state, and the browser tab keeps its own selection in
the URL. Late answers are dropped by a request token, and a switch detaches from
a running turn instead of being refused: the answer stays in its own session and
the old view cannot write into the new one. Drafts are per conversation in
`sessionStorage`. Every send, `/stop` and message
delete now names the conversation, so a stale selector cannot act on another
session; an unavailable conversation disables the composer and says why.

## Progress 2026-11-25 (action and drawer handoff)
