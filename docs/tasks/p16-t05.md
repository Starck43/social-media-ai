## Lock order and erased-identity limit

- **Owner clarification:** for a deleted and recreated contact with a new ID, a previously orphaned year should remain closed if identity can be recovered; otherwise document the limit. The orphan row stores no stable identity and `contact_id` is NULL, so it cannot be matched to an independently recreated contact. Consequently a new ID may generate the same event/year again. Neither event type/year alone nor another person's survivor proves identity; preventing this requires a separately authorized retained identity or a safe explicit linking mechanism. This is a known limit, not proof of closure. Normal PostgreSQL sequences do not automatically reuse IDs, but recreation itself receives a new one.
- **Locking work:** outside-owned `app/services/contacts/reconcile.py` is isolated in `4f0c9d6b5b2d76a77c8355beaa286039e8b53ebc`: merge/unmerge lock the tenant before acquiring contact locks in ascending ID order. Owned planner changes and tests are in `b8f0b1efbf5c39fe1e5c8c27fdee338c33fec219`: daily generation locks tenant during authorization, then locks workspace contacts ascending before listing. This locks all workspace contacts for the transaction, a contention/scaling trade-off needing review; it is not a proof against every lock cycle in the application. No intersections for the reconcile path were found in open PRs #443, #444, #445 when checked.
