## Deliverable

A commitment found in a thread, a mail or a document becomes a **canonical task** (P22-T01/T08) with a due date, a
resolved contact and a source citation, and produces one reminder through the user's personal notification channel.
Approval by a human is mandatory; nothing is created or sent automatically. A commitment never gets its own table:
the task is the record, the message snippet stays evidence.

## Entry points and handoff

The [P22-T16 sidebar](../audit/p22/p22-t16.md) already pins «Задачи» and leaves `/app/followups` as a legacy page.
Start proposals from «Переписка» or the originating document. Show «Создать задачу» with the proposed deadline,
contact and citation. After approval, open the same task card used by «Задачи» and the calendar.
Use the recorded proposal origin to support the cutover filter within the canonical task list.
The legacy catalogue reads `KnowledgeSnippet(context_type='followup')` rows as evidence.

## Scope

1. **Source.** A `MessageThread` message, an email or a document snippet supplies the commitment text, the
   counterparty, the channel and a stable citation. Content stays in the source system; the task stores the
   citation, never the body.
2. **Detection.** Reuse the triage proposal path: the agent proposes a task with the extracted commitment, the
   counterparty and a proposed date. Imprecise phrasing («в начале следующей недели», «до конца месяца») marks the
   proposal `requires_confirmation` and never becomes a due date without a human choice.
3. **Commit on approval.** Approving the proposal creates exactly one canonical task with a due date, the contact
   link and the citation; re-approving the same proposal is idempotent. Rejection records the decision and creates
   nothing.
4. **States.** `pending` → `requires_confirmation` → `confirmed` → `snoozed` / `completed` / `dismissed` map onto
   task status and decision rows; use the unified task and decision labels in the UI. A `dismissed` commitment never resurrects on the next sync.
5. **Reminder.** One notification per commitment per due window through `NotificationDelivery`: quiet hours
   (21:00–08:00 by default) reschedule instead of dropping, and the escalation «повтор через 24 ч» is a second
   attempt, not a duplicated commitment. Delivery respects the user's configured channel; an unavailable channel is
   reported as an honest gap, not silently skipped.
6. **Answer to the contact.** Offer «Ответить» that opens the outbox draft for the same thread (P15-T05/T08); sending
   stays behind the existing approval binding.
7. **Calendar visibility.** The due date appears in `/app/task-hub/calendar` as a task deadline in the workspace
   timezone. An event synced from Google/Yandex calendar is never duplicated by a commitment task
   (`recurrence_source == "calendar"` rows stay source-owned).

## Reused behavior

- Keep the [triage extraction](../../app/services/communications/triage.py) and use its evidence in the task proposal.
- Keep quiet hours and imprecise-date handling from the [follow-up rules](../../app/services/communications/followups.py).
- Open source citations through the existing permission checks. A legacy snippet remains evidence until a user approves a proposal.

## Out of scope

- A second commitments table, a parallel list or a soft-duplicate store.
- Auto-creating tasks without human approval; auto-sending replies.
- Calendar write from a commitment (`calendar.event_write.v1` keeps its own approval path).
- Recurring commitments and multi-step plans; both belong to P22-T01/T03 follow-ups if they are ever needed.
- Bitrix24/1C calendars and Bitrix tasks as a source: P14 owns those adapters.

## First slice (smallest useful delivery)

Mailbox thread with one message → triage proposes a commitment → approval creates a task with a due date and the
contact → the deadline shows in the calendar → one Telegram reminder outside quiet hours → «Ответить» opens the
outbox draft. Everything else in Scope can be a follow-up card.

## Acceptance

- The «Переписка» proposal opens the created task in «Задачи». The same card opens from the calendar.
- The same source message approved twice produces one task and one reminder; a rejected proposal produces neither.
- An imprecise date cannot reach the task without an explicit human date; after confirmation the reminder fires at
  the confirmed time in the workspace zone.
- Quiet hours move the reminder instead of dropping it, and the second attempt is the escalation, not a duplicate.
- A commitment task and a synced calendar event for the same meeting are distinguishable in the calendar and never
  render twice for one occurrence.
- The task detail shows the counterparty, the citation and the channel; opening the citation requires the source
  permission and shows a refusal rather than a leak when it is missing.
- Deleting the source message or revoking the channel leaves the task with an explicit unavailable citation instead of
  breaking the page.
