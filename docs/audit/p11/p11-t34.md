# P11-T34 — reported `0145` downgrade data loss: closed, not reproducible

- **Verdict:** closed 2026-11-13 as not reproducible. No code change.
- **Task:** P11-T34 (card removed at acceptance) · Parent: [P11](../../phases/p11-structure.md)
- **Auditor:** session-local audit on `dev` `0ad6c246`, python 3.14.0, project `.venv`,
  PostgreSQL 15 on `localhost:5432/social_manager`.

## The recorded claim

Registered in the P19-T07 closeout (`136f4b30`) as: "`0145` downgrade drops tables
created by `0143`; blocks every isolated-schema bootstrap." The card asked for
reproduce-or-close before any fix.

## What the source says

`0145_planner_event_planning.py` is internally consistent. Its `upgrade()` creates
exactly four tables — `planner_event_settings`, `planner_event_runs`,
`planner_event_claims`, `planner_event_groups` — and its `downgrade()` drops those
same four, after refusing to run when either settings or run identities are
populated. It never references `planner_reminders` or `notification_deliveries`;
those belong to `0143_planner_reminders.py`, which creates and drops them itself.

The revision graph is `0142 → 0144 → 0145 → 0143 → 0146`. `0145` sits *below*
`0143`, so any downgrade that passes `0145` runs `0143`'s downgrade first. `0143`
drops its own two tables before `0145` is ever reached, which is the opposite of
"`0145` drops tables created by `0143`".

## What was probed

Isolated scratch schemas in `social_manager`, each dropped afterwards. Alembic was
driven through `migrations/env.py` with an injected synchronous connection (the
pattern `tests/files/test_p12_t12_migration.py` uses), because `POSTGRES_URL` is
`postgresql+asyncpg://` and plain `alembic` cannot use it.

| # | Probe | Result |
|---|---|---|
| 1 | `upgrade head` into empty `p11t34_check` | **OK**, reaches `p17t08_onec_history_status`; `0145` and `0143` both applied |
| 2 | `downgrade 0144` from head | **OK**; order applied `0146 → 0143 → 0145 → 0144` |
| 3 | `upgrade head` again | **OK**, back at head |
| 4 | Second `downgrade 0144` → `upgrade head` cycle | **OK** |
| 5 | `scripts/setup_test_db` fresh bootstrap into empty `p11t34_boot` | **OK**, models + guards + reference rows seeded |
| 6 | `upgrade 0145` then `downgrade 0144` on isolated `p11t34_iso` | **OK**; `planner_reminders` and `notification_deliveries` did not exist at `0145` at all (count 0), so nothing of `0143`'s could be dropped |

Probe 6 is the decisive one for the recorded wording: at revision `0145` the `0143`
tables have not been created yet in a linear upgrade, so `0145.downgrade()` has no
way to drop them.

## Inventory evidence

- Pre-run inventory of the empty scratch schema: `/tmp/p11t34-before.json`.
- Post-upgrade baseline: `/tmp/p11t34-upgraded.json`.
- After a full downgrade/re-upgrade cycle, `schema_inventory.py --diff` against the
  upgraded baseline reported exactly one line: `model_types_max: 40 -> 41`.
- That line is not a lost or extra table. Row count stayed at 39 in both schemas;
  the `on_version_apply` hook (`scripts/migrations/register_model_types.py`)
  re-inserts a managed model type on each revision step, so one row
  (`documentapproval` / `documents.approval`) received a fresh id while
  `workspaceoffboardingevent` kept its original. No relation, type, function,
  trigger or permission row was added or removed by the cycle.

## Limits of this closure

- The closing evidence is the absence of a reproduction across six invocation
  shapes on three scratch schemas, plus a source reading that contradicts the
  recorded description. It is not a root cause for whatever the original reporter
  observed.
- The original failing command was never recorded — the registration carries only
  the one-line description. If the failure returns, capture the exact command and
  the revision it started from; a downgrade that begins *below* `0143` is the
  shape that would exercise `0145` before `0143` and is the first thing to try.
- `model_types` id churn on every revision step is a real, separate observation
  about `register_model_types`, not a defect this card covers. It is idempotent in
  row count and does not affect schema layout.

## Disposition

- No code change. `0145` is correct as written.
- Scratch schemas `p11t34_check`, `p11t34_boot` and `p11t34_iso` were dropped and
  verified absent from `information_schema.schemata`.
- Shared `test_schema` was read only (revision `p17t08_onec_history_status`,
  matching `alembic heads`); it was not migrated, reset or written.
- ROADMAP row removed; this note is the only remaining record.
