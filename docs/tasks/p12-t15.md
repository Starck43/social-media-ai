## Goal and sequencing

Let users see and manage what the agent may do in each connected folder, protecting
original files from accidental deletion. This is a future staged task, not a grant
to request provider write credentials or to change or delete any file. The
read-only pilot supplies the restrictive-only foundation first.

## Scope

- Provide a clear folder policy editor and effective-rights display: no access or
  read-only initially; show inherited parent restrictions and where a restriction
  comes from. A child cannot override a parent denial. Enforce server-side for
  every read/list, cached result and queued operation, not just in the UI.
- Define a separately reviewed stage for optional create, modify and delete rights.
  All are off by default and independently scoped; no action is enabled merely
  because the provider token has write access. Owner policy changes require normal
  authorization, CSRF protection and a durable audit record.
- Destructive actions require explicit, informed per-operation confirmation bound
  to actor, tenant, target, exact operation, expected version and expiry; recheck
  authorization and current version at execution. No bulk or agent-autonomous delete
  by default. If version-safe execution or provider recovery is unavailable, fail
  closed and explain it rather than promising undo.
- State honestly that application restrictions cannot constrain other applications
  or a provider-wide OAuth token outside this application. Provider scopes should
  remain least privilege; enabling write requires a separately reviewed workflow
  and explicit user consent. Distinguish provider ACL, workspace sharing and agent
  policy; effective rights are their intersection.

## Acceptance

- Assembled authenticated UI/API tests: inherited denial, sibling isolation, actor/
  tenant/owner isolation, CSRF, revoke during queued work, filtered listing and
  cached content. Deny unknown, missing or corrupt policy configuration.
- Tests for each subsequently enabled mutation include preview, explicit approval,
  version conflict/reapproval, idempotency, unknown-after-timeout reconciliation,
  cancellation, audit and unsupported provider behavior; no blind retries or
  silent overwrite. Explicitly verify deletion remains disabled until approved.
- Include migration/rollback, retention, permission lifecycle, usability and
  recovery evidence; never apply a public migration without separate authorization
  and backup. Mock remote writes in tests.

Dependencies: a reviewed, accepted read-only pilot and security/connection
contracts. Any mutation requires its own scoped implementation authorization and
provider capability proof; this card alone is not that authorization.
