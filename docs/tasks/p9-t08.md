## Scope and acceptance

`bot_actions` is the only persisted "proposed external action" record, but it
is a half-finished social ledger (audit in P10-T26):

- Only the analyze handler creates rows; nothing approves or executes them
  (manager transitions have no production caller; `action_send` is preview).
- `source_id`/`agent_scenario_id` are NOT NULL → cannot represent business
  actions (mail reply, document send, CRM update) or chat-originated proposals.
- No idempotency key, target identity, expiry, actor-bound approval binding
  (payload hash/version), kill switch or per-target outcome; `confirmed_by` alone
  is not approval evidence (MODELS.md).
- Rate limit counts every created row, including REJECTED/PENDING; cooldown
  counts only EXECUTED rows, which never exist today.
- Admin form edits `status` freely, bypassing the transition rules.

Proposal (choose with P9-T01): evolve into a capability-neutral
`agent_actions` ledger — `capability`, `target_ref`, `payload` + `payload_hash`,
`idempotency_key` unique per tenant, `status` draft→validated→approved/scheduled→
claimed→confirmed/failed/unknown, `approved_by`/`approved_at`/`approval_expires_at`
bound to payload hash, `origin` (task/chat/manual) with nullable source/scenario.
Admin becomes read-only + cancel. Guards count approved/executed per task.

Accept: owner-approved contract, migration validated on test_schema, one
capability wired end-to-end behind a kill switch, replay/idempotency and
cross-tenant tests. Depends: P9-T01, P10-T26.
