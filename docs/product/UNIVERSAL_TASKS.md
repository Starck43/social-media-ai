# Universal tasks

[Implementation sequence](../phases/p22-universal-tasks.md) · [Workspace journeys](WORKSPACE_UX.md#tasks-as-the-universal-tool)

## Product decision

Every user-authored piece of work has one Task identity, detail page and command contract. A title is enough to save a personal note. A deadline, delegation, repeat rule, data source, processing step or destination can be added to that same task later. Personal and team lists are authorized views. People can work on a task together while automation executes some of its steps. The interface asks what result the person wants. It never requires them to classify the task as planner or agent work.

This is the P22 target. The baseline [P20-T10](../audit/p20/p20-t10.md) joins independent planner and agent records at the UI. Its link and confirmation behavior are migration inputs. [D24–D26](../audit/q/q-21-source-authority.md) still govern upstream facts, resource identity and explicit source choice. An external issue can appear directly in the same list with a provider-backed detail view. A local task is created only for local work or an explicit follow-up. Project-management systems retain their workflows and permissions.

## Task aggregate and storage

Proposed relational names below define ownership and cardinality. Extend existing tables in place where that preserves their contracts. Use tenant-qualified FKs and matching unique keys throughout, with protected fields encrypted under existing privacy and erasure policies. Keep optional dimensions out of the initial form. Store queryable identity, lifecycle, grants and schedules in typed columns. Limit versioned JSON to validated operation-specific inputs.

| Record | Relationship and owned facts |
| ---|---|
| Task | One local identity. Workspace, named user or proven workspace/system principal, title, description, visibility, priority, status, dates and version. Owner and assignee have distinct roles. Support date-only deadlines and offset-aware instants with an IANA timezone. Preserve categories, tags, contact and parent task. Reject hierarchy cycles. Internal maintenance jobs stay operator-only. |
| Participation | One responsible assignee, optional collaborators and watchers under active workspace membership. Unique membership per task and role. Private, explicitly shared and workspace-visible are access policies. Watching supplies notifications within existing access. Assignment, following a link or team view cannot convey account credentials. |
| Occurrence and relationships | Preserve planner's concrete occurrences, series template, previous/next constraint, reminder links and per-occurrence edits. A recurring human deadline creates the next occurrence on completion. A scheduled execution creates a run against its task at trigger time. Subtask, dependency and execution-for links have explicit meanings. Link permissions are checked at both ends. |
| Execution profile and steps | A task has zero or one current profile, with a bounded ordered list of typed operations. Each step names a registered capability, typed parameters, input/output bindings and optional scenario revision for LLM processing. Deterministic steps run through existing services. Define explicit stop/continue-on-partial behavior and typed output contracts. Start with existing collect/analyze/digest and communication steps. Extend by registering a validated operation and handler. |
| Task bindings | A task has zero to many bindings. Each identifies a named port, read or write direction, resource kind and authorized selection. Steps may reuse a binding. Bind social lanes to Source, provider objects to SourceObject, internal sinks to a registered service, local paths to a paired root grant. Use typed FK associations or checked exclusive FK columns for stored references. Disallow unchecked generic table-name/ID pairs. Discovery/all-authorized is an explicit bounded selection mode. |
| Trigger | Manual availability follows runnable capabilities. Optional automatic schedule stores timezone, rule, enabled state and next due time. Keep execution window, due date, calendar recurrence and trigger separate. A scheduled task can also run now. Existing triggers, limits, cooldowns and dry-run settings must round-trip. |
| Run and Job | One task to many runs, one run to one or more existing queue Jobs. Run owns trigger identity, admitted plan revision, immutable effective inputs, authorized principal, payer, outcome and references to result evidence. Job owns attempts, claims, progress and worker errors. Store only bounded permitted evidence and version/digest references in snapshots. Keep existing retention and spend receipts. |
| Decisions | Typed association from task and optionally run to the owning ledger, e.g. BusinessCommand or DocumentApproval. The ledger owns actionable state, payload revision, eligible actors and final decision. For a local workflow that explicitly requests acceptance and has no ledger, use a local task decision with reviewer, pending/accepted/rejected/expired state, version and decision time. |
| External work | Existing SourceObject identifies an upstream item per tenant and connection. Use distinct task-reference variants for local Task and external SourceObject in the command/read contract. A local follow-up can link to an upstream item without becoming its mirror. Materialize a source reference for a durable link or decision; browsing alone need not create a local Task. |
| Legacy identity | Unique mapping (tenant, old namespace, old ID) to canonical task, with typed references to any legacy execution profile/occurrence needed for old URLs. Numeric IDs from two legacy tables can coincide. Do not match by title, time or numeric ID alone. |

A change to assignees, visibility, plan, schedule or bindings uses an expected version. List queries enforce workspace, role, visibility and source rights before pagination and counts. Index workspace with owner/assignee, status and due date, scheduler due time, and run/decision lookup keys. Expose indexed filters for Mine, Team, Due, Needs my decision and Recent runs. Source outages appear alongside the results as unavailable coverage.

### Proposed keys and write ownership

| Storage target | Key or invariant | Write owner |
| --- | --- | --- |
| tasks | PK id, unique (tenant_id, id). Nullable same-tenant parent, assignee as active member, optional contact. Positive version. At most one of due_date and due_at. completed_at agrees with done. | Task service |
| task_participants, task_links | Unique (tenant, task, member, role) and (tenant, from_task, relation, to_task). Keep the responsible assignee only on Task. Lock hierarchy/dependency changes and reject self-links and cycles in those relations. | Task service |
| task_plan_revisions, task_steps, task_bindings | Unique (tenant, task, revision), unique step position and port within revision and step respectively. Immutable after publication. Plan revisions can pin an immutable scenario version or a protected effective-method snapshot. A binding references exactly one target kind. | Plan service |
| task_triggers, task_runs, jobs | Scope trigger to task, pin each run to a revision of that same task. Unique scheduled (tenant, trigger, due_instant) and manual (tenant, actor, request_key) admission keys with fingerprint checks. Add nullable same-tenant run FK to existing jobs. Keep valid standalone maintenance jobs. | Admission transaction, existing scheduler and worker |
| task_decision_links | Same-tenant task/run and exactly one typed ledger target. Unique task/target association. Local decisions carry their own reviewer and version. Derive actionable counts and labels at read time. | Owning workflow |
| task_source_links, legacy_task_ids | Reference existing source_objects for durable external links. Unique (tenant, task, source_object, relation). Map old IDs using unique (tenant, legacy_namespace, legacy_id); many aliases may resolve to the same Task. | Source owner and migration adapter |

Reuse planner recurrence, reminders, messages, analytics, calendar events, provider grants and business commands through their owning services. T01 and T06 inventory their existing references before selecting FK changes. A provider-owned item rendered in Tasks uses a tagged source reference and read-through fields. Keep provider statuses and permitted transitions native on detail, with an explicit optional mapping only for common list filters.

## Execution and decisions

1. Preview resolves supported operations, permitted inputs and destinations, window, scope, estimated use and required confirmations. A saved note with no steps has no Run action. A missing account, grant, scope, payer consent or implementation produces a specific corrective action.
2. Run now and the scheduler use one admission service. Lock and verify revision, tenant, actor or delegated principal, resource grants, spending policy and active capability. Insert one run/initial job or durable enqueue intent atomically. Use a manual request key plus input fingerprint, or a scheduled occurrence key unique per task and trigger instant. A replay returns the original receipt. A new manual request leaves the cron cursor alone. Define overlap explicitly, defaulting to report an active run and avoid duplicate effects.
3. Pin scenario revision and validated plan for the admitted run. Recheck grants, cancellation, routing boundaries and budgets before each side effect. Apply worker fencing, bounded retries and existing command/outbox idempotency. A worker crash after an uncertain external write yields an unknown outcome for reconciliation. Suppress automatic replay. Show partial coverage and preserve completed steps on retry.
4. Show the work status (to do, in progress, done, cancelled), last run outcome, next scheduled run and pending decisions separately. Derive “Needs your decision” and the available action list from fresh ledger state and current rights. A task owner can be different from the approver. Multiple decisions may be outstanding. Preview binds target, payload hash/version and expiry. Decide atomically, reject stale or repeated conflicting input, and record actor, time and reason. Rejection ends that proposal and returns the defined follow-up action. Run success attaches evidence. Close a human obligation only through its explicit completion policy, preserving confirmation for existing linked work.
5. Delete previews the affected occurrence/series, schedules, jobs, links and reminders, then requires an authorized, version-bound confirmation. Stop future scheduling, cancel safely stoppable work, fence late results, preserve retention-bound evidence and report in-flight uncertainty. Removing a local link cannot delete an upstream issue, message or file. Deleting upstream is a separate supported provider command with its own preview and authorization.

## Platform, connector, connection and resource

| Question | Owner and decision |
| --- | --- |
| Which ecosystem? | Retain Platform and existing Source.platform_id for shared social identity, display and existing operator-managed non-secret transport defaults. VK and Telegram already have stable IDs. Platform is an optional grouping for multiple connectors. Adding a provider or a local driver need not create a Platform row. Avoid destructive Platform deletion through its source cascade. |
| Which operation exists? | Extend the code-owned provider catalog with versioned connector capabilities, resource types, input/output schemas, auth method, implementation key and read/write/approval policy. A driver is the implementation behind that key. Examples are Yandex Mail/IMAP, Yandex Disk/files, Bitrix24/tasks, Telegram bot transport, Telegram account reading, and paired local files. Mail.ru Mail and Cloud can have different capabilities under the same brand. |
| What does the operator configure once? | One installation configuration per connector integration/instance when needed. Keep existing Platform.params as the sole owner for current social endpoints/version; connector-specific validated non-secret overrides belong to installation settings only when actually required. Deployment app ID, OAuth secret or shared bot token resolve via the existing protected deployment settings/secret resolver. Admin shows configured/missing and rotation scope. Never copy a deployment credential into each workspace, task, catalog entry or public params. Personal bot/account and workspace-specific installations use their own grant. |
| Who may use which account? | WorkspaceConnection owns non-secret account identity and state. WorkspaceConnectionSecret or existing personal vault plus explicit WorkspaceAuthorizationGrant owns secret access under the current credential model. A connection selects an installed catalog capability. Check actor, account, workspace, capability, read/write scope and current revocation state. Configuring a VK app or Telegram bot once does not authorize personal inbox access. |
| Which data? | A resource is a mailbox/folder, chat, VK source/query, tracker issue, approved local root, etc. Reuse Source for existing collection semantics and SourceObject for upstream identity. Access to a local root goes through the paired LocalConnector and its grant. A task binds an exact resource or a validated selection to a step. Preserve an explicit user choice among overlapping accounts, with reauthorization or unavailability visible. |
| Where is the output? | Internal Messages, analytics and documents are owned services. Write through their normal validation and deduplication. An external destination uses a separately admitted write capability on the selected connection; read access never grants write access. Scenarios own reusable LLM methodology and output schemas. Source selection, destinations, trigger, payer and approvals belong to the task/run. |

## Representative journeys

- **Note due Friday.** Enter a title, optionally pick Friday and save. It appears in Mine and on the due-date calendar. Assign or share later if permitted. Editing the date produces one versioned change.
- **Review correspondence by sender.** Select authorized mailboxes and messenger conversations and a time window. Choose “Group by sender” and “Save in Messages”. Fetch or reuse admitted message metadata through each real channel adapter. Upsert through the messaging service by tenant, connection, channel and original ID. Group confirmed identities across channels only through verified contact links; keep ambiguous senders separate and preserve thread membership. Retain encrypted permitted headers, provenance, hash and original links under D3/D11. The result links to the filtered Messages view. Show processed/skipped/unavailable per source. No LLM is needed for grouping. Optional analysis adds a scenario and follows model/data boundaries.
- **Recurring VK analysis.** Choose authorized communities or explicit discovery, a rolling window, analysis scenario and destination. Preview limits, then schedule. “Run now” produces a separate receipt. Opening an old result shows its admitted inputs even after the plan changes.
- **Team issue from an external tracker.** Browse in the common list and open the provider-backed card. Show source, assignee, freshness and permitted transitions. Resolve actions from that issue's current workflow and actor grants. An approved transition is submitted through the command ledger and refreshed from the provider. A Slack message can be context for a local task or tracker issue. An explicit link preserves provenance. A chat message by itself does not establish tracker state.

## Shared interfaces

Use one application service for list, get, create, preview change, update, preview/delete, run now, runs/results, complete, available actions and decide. Use a versioned API namespace for canonical IDs while legacy /api/v1/tasks and /api/v1/planner/tasks keep their existing typed IDs and response shapes. CLI and agent tools use the same commands, structured reasons, dry-run and idempotency keys. Agent tools accept opaque server-issued references for decisions. Admin can manage catalog-backed settings and diagnose runs with redacted values. Domain changes, even from admin, use normal commands and tenant/actor checks.

The web app has one Tasks list, one detail route and one Create/Edit entry. Start with “What needs doing?” and offer Save immediately. Ask “When?” or “Who is involved?” when requested. If the user wants the service to do work, progressively ask what to read, what to do, whether AI is needed, where to save, and when to run. Recommend only capabilities authorized for the actual selection. Summarize defaults, scope, cost and effects in plain language. Back preserves compatible answers; changing a previous answer identifies invalidated choices and clears them before submit. Editing starts at a readable summary with direct links to each applicable step. Keyboard/mobile navigation, field-level errors, stale version recovery and a single final confirmation use the existing shell and both themes. Detail actions include Edit, confirmed Delete, Run now when runnable and Accept/Reject when actionable.

The pinned «Задачи» entry also holds approved commitments captured from correspondence or documents.
Use the canonical task card for the deadline, evidence and reminder. [P22-T15](../tasks/p22-t15.md)

### Task conversations

`/chat` opens the user's global workspace conversation. Every task card shows the link «Поручить агенту» when a usable agent scenario has been explicitly configured for that task and the viewer can use it. The link opens a right-hand chat drawer on the task's topic. Reopening it resumes that user's conversation for the same task. Selecting a task in the right sidebar of `/chat` immediately opens that same task session in the center. «Основной чат» restores the main session. Both are personal to the user within the active workspace and use the same renderer, composer and runtime. Invited members enter through [workspace AI access](../platform/TENANCY.md#web-ownerguest-context-and-membership-disable); their role and task access bound the available actions. ## Transition and reversibility

Expand beside the legacy schema. Inventory every writer and inbound FK before switching. Backfill and shadow-compare per workspace with resumable checkpoints and a change watermark or locked catch-up. Each phase of rollout has **one authoritative writer**; compatibility projections updated with the write share its transaction. Flip all write paths for a workspace together, including runtime, legacy forms and admin. Preserve an auditable mapping, receipts and differences. A rollback after new writes requires proven reverse compatibility or a scoped write freeze with forward recovery for new-only features. Never blindly toggle back to stale rows. Details and acceptance are assigned in the [phase](../phases/p22-universal-tasks.md).
