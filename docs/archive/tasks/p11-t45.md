# P11-T45 — Credential rotation refuses the current migration head

Archived 2026-11-18. Accepted as `ddcb3a12`, merged `9ee17d04`; findings F-1 and the evidence are in the
[audit](../../audit/p11/p11-t45.md).

**Status:** see [ROADMAP../../../ROADMAP.md. Tooling follow-up (not phase work).

## Problem

`scripts/ops/rotate_credentials_key.py` keeps an explicit `generations` map of supported Alembic
heads and fails closed for unknown ones:

```python
if len(revisions) != 1 or revisions[0] not in generations:
    raise RotationError("Apply the reviewed encrypted-refresh migration first and use a supported single head")
```

The map ends at `0153` and lists none of the heads accepted since:
`p21t13_catalog_storage`, `p21t14_rate_limits`, `0157`, `p12t15_policy_audit`. A database migrated
to the current `dev` head therefore cannot be rotated — the utility refuses before any work.

## Reproduction

```bash
env -u DEBUG DB_SCHEMA=public DB_TEST_SCHEMA=<isolated schema at dev head> \
  .venv/bin/python -m pytest \
  tests/integrations/test_p12_t12_private_storage.py::test_credential_rotation_requires_explicit_private_result_purge_and_rolls_back -q
```

Observed on `dev` `8c96f961` (117/121-table schemas, `alembic_version` at `p21t14_rate_limits` or
`p12t15_policy_audit`) and on P12-T15's accepted revision: `RotationError: Apply the reviewed
encrypted-refresh migration first and use a supported single head`. Independent of the P12-T15
branch — it reproduces in the main worktree without it.

## Second defect in the same test

`tests/integrations/test_p12_t12_private_storage.py` calls `rotate_in_transaction(...,
schema="test_schema", ...)` with a hard-coded schema instead of the configured one, so the test
inspects the shared `test_schema` whatever `DB_TEST_SCHEMA` points at. That makes the check
non-isolatable and couples it to shared-schema bookkeeping.

## Expected change

1. Extend `generations` with `p21t13_catalog_storage`, `p21t14_rate_limits`, `0157`,
   `p12t15_policy_audit`; all four keep the same encrypted-store layout `(True, True, True)`
   (`personal_connector_authorizations`, `telegram_login_attempts`, `telegram_login_request_keys`
   present, private result tables present). Verify the layout per head instead of assuming it.
2. Drive the test's `schema=` argument from the configured schema.
3. Add a deterministic check (offline, no DB) that every migration head in
   `migrations/versions` has a `generations` entry, so a future migration cannot silently make
   rotation unavailable.

## Boundaries

Rotation still requires owner authorization, a stopped-service window and two different keys; this
follow-up changes only the supported-head map and the test wiring. No public migration, no key
material and no production run belong to it. Reproduce first, then fix: a wrong layout tuple is
worse than a refusal, because rotation would silently skip an encrypted store.
