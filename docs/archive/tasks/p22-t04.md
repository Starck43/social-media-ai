## T05/T07 run receipt and result interface

Use `app.services.task_launch.launch_published_task(task_id, expected_revision=..., request_key=...)` for an explicit run and `task_run_service.get_receipt(run_id)` to reread it. Both are application-service calls under the caller's normal workspace and permission scope; callers must not bypass their checks or read the encrypted snapshot/checkpoint directly. A receipt has `run_id`, `task_id`, `revision`, `job_id`, `status`, `result` and `replayed`. The job ID is the historical initial Job ID, not proof that its queue row still exists; a terminal Job can be pruned while the Run and idempotent manual receipt survive.

The permitted result is `null` or bounded progress: `reason: active_run` for a skipped overlap, `coverage: complete|partial` when known, a fixed safe `code`, and up to 12 named steps with `status: done|unavailable|previewed` and an optional non-negative bounded `count`. It never includes raw headers, provider payloads, credentials or checkpoints. The returned run status is distinct from the human Task work status; a successful run does not complete that Task. VIEW permission, workspace membership and Task visibility are checked again when reading the receipt. T05/T07 must preserve these checks and treat unknown result fields and unsupported operations as unavailable, not invent content or claim provider effects.

**Overlap example.** A user runs an enabled scheduled task immediately before its due time. The manual admission does not change `next_due_at`. If that Run is still pending/running when the scheduler consumes the occurrence, it records a distinct `skipped` Run with `result.reason = active_run`, enqueues no second Job, and advances the cursor to the next occurrence. Repeated manual use of the same key and fingerprint returns the original Run receipt.

**Explicit limitations and follow-ups.** The T04 worker allows only bounded, read-only `mail.read_headers` and `mail.group_by_sender`; write operations, social operations, legacy effects and LLM/paid execution fail closed. `messages.store_groups` and the two-channel correspondence result belong to T10; unified API/CLI/AI presentation belongs to T07. The progress projection is not a Messages link or provider data. Any future effectful or paid implementation must establish its own admitted authority, idempotency, spending and reconciliation boundaries; these mocks do not establish those provider guarantees.
