## READY evidence

Source SHA carrying the implementation: the commit that follows the claim
commit `c0bdf5b` on `fix/p10-t20-digest-confirmation-dedup`.

### What the two failing cases actually encoded

Both asserted `replacement["intent_id"] != old["intent_id"]` after a repeated
identical `digest_send_now` stage. That is the pre-`82555f2` behaviour, when a
repeat always minted a twin. `82555f2` answers the repeat from the pending
intent instead, so the `intent_id` is deliberately reused and the stored
snapshot is unchanged — the stale half of the acceptance.

There is a second, weaker assertion in the same cases that stays true for the
right reason: consuming an *observed* snapshot of an intent which was genuinely
*changed* (or replaced by another scope) must fail. That half is kept.

### The real defect found on the way (`82555f2`)

`_same_pending_intent` compared only name + `arguments_digest`. A **expired**
intent therefore also matched: the runtime answered «Это действие уже ждёт
вашего ответа — повторно не создано», left the dead intent in state, and the
owner's following «да» was rejected by `pending_rejection` as `expired_intent`.
That is exactly the silent dead end `82555f2` set out to remove, reintroduced
through the dedup path.

Reproduced before the fix (staging `digest_send_now`, backdating
`expires_at` by one second, repeating the identical call):

```text
REPEAT ON EXPIRED -> 'Это действие уже ждёт вашего ответа — повторно не создано.\nconfirm digest'
pending still present?  True
publisher awaited?      0
```

Fix (`app/agent/runtime.py`, `_same_pending_intent`): the digest match is now
insufficient on its own — the stored intent must still be answerable. A missing,
non-string, malformed or naive `expires_at` dates, or an expiry not in the
future, means "not the same pending intent", so the repeat stages a fresh
question (`make_pending_intent` always sets `expires_at`, so the live path is
unchanged).
