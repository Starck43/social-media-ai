# P21-T06 — Credential boundary and rotation hardening

Registry: [ROADMAP](../../ROADMAP.md); parent: [P21](../phases/p21-ai-operations.md).

## Goal

Verify and harden secret custody across LLM providers and social connectors while
preserving the accepted separation of `CREDENTIALS_KEY` and `PII_ENCRYPTION_KEYS`.

## Owner gate

Changing Fernet to AES-256-GCM, merging credential tables, changing key families,
or changing who may decrypt is an accepted security/crypto contract change. Ask
the owner before implementation; otherwise limit the first increment to audit,
tests, masking and the existing rotation procedure.

## Steps

1. Inventory every secret-bearing ORM field and every serializer/admin projection.
2. Verify owner/tenant authorization before decrypt and redacted error handling.
3. Test `scripts/ops/rotate_credentials_key.py` with synthetic records, backup,
   writer-stop and zero-plaintext-log evidence.
4. Decide whether versioned envelope metadata is necessary; do not add a generic
   vault table merely to match the external proposal.
5. Add regression checks for API omission, admin masking, rotation failure and
   cross-owner denial.

## Acceptance

- No public response or error contains ciphertext, plaintext, access/refresh
  token, API key or key material; UI receives only safe configuration metadata.
- System-level provider secrets remain environment/deployment secrets unless an
  owner-approved BYOK contract says otherwise.
- Synthetic rotation re-encrypts all supported stores, preserves data, and
  rejects wrong/old keys according to the documented cutover procedure.
- Key separation and the existing PII rotation path remain intact.
- No `.env*`, real credential or secret value is read into evidence.

## Rollback and boundaries

Keep the old key and backup under the operator procedure until verification is
complete. Do not delete old ciphertext, rotate production keys, or deploy a new
crypto algorithm from this planning card.
