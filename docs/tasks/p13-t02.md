## Goal

Provide one reusable mechanism for storing personal data encrypted at rest while keeping exact-match lookup, deduplication and safe logging possible.

## Baseline

- `app/utils/crypto.py`: single-key Fernet for the credential vault (`CREDENTIALS_KEY`), no rotation.
- `workspace_connection_secrets` (0121) encrypted with the same key.
- No field-level encryption for personal data in business tables.

## Plan

1. Add settings `PII_ENCRYPTION_KEYS` (comma-separated Fernet keys, first = active) and `PII_INDEX_KEY` (HMAC-SHA256 key); fail closed at startup of any feature that needs them; document in CONFIGURATION.
2. Implement `app/core/pii.py`: `encrypt_pii`/`decrypt_pii` on `MultiFernet`, `blind_index(kind, value)` with per-kind normalizers (email: lowercase/IDNA; phone: E.164 via a small normalizer, default region RU; username: lowercase without `@`).
3. Add a SQLAlchemy `EncryptedText` type decorator and a `BlindIndex` column helper; ciphertext never appears in `repr`, admin lists or API responses.
4. Add `redact_pii()` for logs/exception text and a logging filter used by new business adapters; unit tests assert that seeded emails/phones never reach captured logs.
5. Write a key-rotation CLI (`cli` command) that re-encrypts rows of registered encrypted columns in bounded batches with resumable progress; dry-run by default.
6. Document the contract (`docs/PII_PROTECTION.md`): what is encrypted, what is indexed, what cannot be searched, backup/rotation, and how modules register columns.

- Same normalized value → same blind index; different tenants still separated by tenant filter; index never reversible from logs.
- No plaintext personal data in logs in adapter tests.
- Coverage ≥ 80% for the new modules.
