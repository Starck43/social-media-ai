# Q-16 audit — Shared Platform catalog and canonical JSON configuration

**Verdict: NOT ACCEPTED at audit time — every finding is now fixed on `dev`; see the task card for the closing evidence.**
Candidate: `d3a4a40c287d137eb1efe9b3ba03e72e82398b31` (already on `origin/dev`).
Audit date: 2026-11-02. Dialogue: https://app.notion.com/chat?t=40bd5248ae66806fba4a00a9d3a3af96

The core design is sound: one global row per platform type, `Platform.params` as the
only runtime source, no env fallback, SQLAdmin-only management, and a migration that
aborts rather than silently picking a winner. The rollback snapshot and the
`_migration_0120` archive are good work.

The migration does not, however, produce a configuration that the runtime can
actually read for VK OAuth, and it silently drops platform types that had no row.
Both are rollout blockers on a real deployment.

## Blocking findings

### 1. `0120` never materializes the VK OAuth keys, so VK OAuth dies after migration

`app/services/social/platform_config.py` defines six VK bootstrap keys, including
`oauth_base_url`, `oauth_token_url` and `redirect_uri`. The migration's `defaults`
map (`migrations/versions/0120_shared_platform_config.py:103`) contains only
`api_base_url`, `api_version` and `auth_type`.

Pre-0120 rows hold exactly that smaller set — the `params` example in the base
revision's model documents only `api_base_url` / `api_version` / `auth_type`. So
`_plan`'s `{**defaults.get(kind, {}), **params}` produces a VK record with no OAuth
keys at all.

Verified by loading the migration module and running `_plan` over a realistic
pre-migration VK row:

```
migrated VK keys: ['api_base_url', 'api_version', 'auth_type']
  redirect_uri:     RAISES platform_configuration_missing
  oauth_base_url:   RAISES platform_configuration_missing
  oauth_token_url:  RAISES platform_configuration_missing
```

Runtime then fails: `vk_oauth.build_authorize_url` calls
`require_config_param(config, "redirect_uri")` and `require_config_param(config,
"oauth_base_url")`; `_post_form` calls `require_config_param(config,
"oauth_token_url")`; `complete_authorization` reads `redirect_uri` again. Every VK
OAuth path — web, API and CLI — is dead on any migrated database.

This also makes the documentation false. `docs/CONFIGURATION.md:524` states that
`VK_OAUTH_BASE_URL` and `VK_REDIRECT_URI` "remain accepted only as legacy one-time
migration inputs for missing JSON keys". The migration never reads either one; it
reads only `VK_API_BASE_URL`, `VK_API_VERSION` and `TELEGRAM_API_BASE_URL`.

**Recommended fix:** add `oauth_base_url`, `oauth_token_url` and `redirect_uri` to
the VK `defaults` in `upgrade()`, sourced from `settings.VK_OAUTH_BASE_URL` and
`settings.VK_REDIRECT_URI` (and the current token endpoint for `oauth_token_url`),
so the documented legacy-input contract is actually implemented. Add a migration
assertion that a migrated VK record satisfies every key `_BOOTSTRAP["vk"]` declares.

### 2. `0120` does not create rows for platform types that have none

`_plan` iterates `groups` built from existing rows only. A deployment whose
`platforms` table has a VK row but no Telegram row gets no Telegram record after
migration. `load_platform_config("telegram")` then raises
`platform_catalog_not_unique`, and `app/channels/telegram.py`,
`app/services/notifications/messenger.py`, the credential diagnostics in
`app/api/v1/endpoints/credentials.py` / `cli/commands/credentials.py` and the
bounded Telegram action all fail closed.

Before this change those paths worked from `settings.TELEGRAM_API_BASE_URL`, so this
is a behavior regression for any deployment relying on env-only configuration —
which is exactly the configuration the migration is meant to absorb.

**Recommended fix:** after merging existing groups, insert a bootstrap row for each
`PlatformType` that has no row, using `initial_platform_params`, and record it in the
rollback snapshot so `downgrade` removes it again. Document the created rows.

## Correctable findings

### 3. `PlatformConfigurationError` is a `ValueError`; callers catch `RuntimeError`

`PlatformConfigurationError(ValueError)`. The OAuth entry points catch only
`RuntimeError`:

- `app/web/connections.py:58` — `except RuntimeError` around `build_authorize_url`
- `app/api/v1/endpoints/social.py:49` — same
- `app/api/v1/endpoints/credentials.py:131` — same
- `cli/commands/credentials.py:208` — same

A missing or invalid platform configuration therefore escapes to the generic
`Exception` handler in `app/main.py:108` and surfaces as an unhandled 500 instead of
the intended "not configured" message. The message text is value-free, so nothing
secret leaks, but the fail-closed diagnostic the card claims is not what an operator
sees. `app/services/actions/telegram_message.py` already translates this correctly
to `PermissionError`; the OAuth callers should do the same.

### 4. A `NULL` `is_active` is silently converted to inactive

`_plan` sets `canonical["is_active"] = all(row["is_active"] is True for row in group)`.
The column is `nullable=True` with `server_default=text("true")`, so legacy rows can
hold `NULL`, which the model treats as unset/default-on. Verified:

```
is_active after migration for NULL input: False
```

`require_platform_param` then raises `platform_inactive` and blocks all provider I/O
for that platform. A `NULL` should be treated as active, not as an explicit
disablement.

### 5. The migration test pre-drops the constraint it is meant to create

`tests/migrations/test_q16_shared_platforms.py:31` calls
`module.op.drop_constraint("uq_platforms_type", ...)` in the fixture before
`upgrade()` runs. That means the test never exercises `create_unique_constraint`
against a schema where the constraint already exists.

This matters because the model now declares
`UniqueConstraint("platform_type", name="uq_platforms_type")`, and
`scripts/setup_test_db.py:157` builds the schema with `Base.metadata.create_all`.
On that path the constraint already exists, so `0120`'s
`op.create_unique_constraint` would fail with a duplicate-relation error. The
fixture's drop masks exactly that case. **This is inference from reading the code,
not a reproduced failure — it needs a check** (see below).

### 6. Three docs still present `VK_REDIRECT_URI` as the live OAuth callback

The card claims current configuration docs were updated, but these still describe
the env var as authoritative:

- `docs/CONFIGURATION.md:14` — credentials table, "registered OAuth callback"
- `docs/CONFIGURATION.md:313` — env reference table
- `docs/COLLECTION.md:408` — "VK redirects to the public callback `VK_REDIRECT_URI`"
- `docs/VK_STANDALONE_APP.md:37` — "set `VK_REDIRECT_URI` to ..."

After this change an operator following any of these sets an env var that does
nothing and gets a broken OAuth flow. `docs/CONFIGURATION.md:524` contradicts them.

### 7. `tests/web/test_web_ui.py:281` still asserts the retired contract

`test_vk_oauth_redirects_to_authorize` asserts the redirect starts with
`settings.VK_OAUTH_BASE_URL`. Runtime now reads `params.oauth_base_url`. The test
passes only because the bootstrap default coincides with the env default, and it is
skipped entirely when `VK_APP_ID` is unset. It is also absent from the card's focused
check list, so it was not part of the recorded evidence. It should assert against the
shared configuration.

### 8. Behavior change bundled with a whole-file reformat

`app/services/social/base.py` and `app/services/social/vk_client.py` show 703 and
2249 changed lines raw, but only 43 and 71 with `git diff -w`. The tabs-to-spaces
reformat is committed together with the configuration change, which
[AGENTS.md](../../../AGENTS.md) asks to keep separate. Not a defect in the result, but
it makes the security-relevant diff much harder to review than it needed to be.
