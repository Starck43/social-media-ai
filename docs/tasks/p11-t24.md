# P11-T24 — Reproduce schema guard objects in the metadata-built test schema

Registry: [ROADMAP](../../ROADMAP.md#p11). Parent: [P11](../phases/p11-structure.md) (navigation only).

## Scope, evidence and acceptance

**Evidence:** `scripts/setup_test_db.py` creates the test schema with
`Base.metadata.create_all`, then stamps the Alembic head. `create_all` produces
tables, columns and constraints only: immutable-receipt triggers, personal
billing guards and task-binding guards exist solely in the migration history
(`0093`+), so they never reach the test schema. On 2026-10-27 `test_schema` had 0
triggers against 42 in `public`, and seven personal billing acceptance cases
failed. The gap was repaired directly in the live database, so it recurs on every
metadata rebuild.
**Change:** keep one reviewed source of the guard DDL, apply it idempotently
after `create_all` for the resolved test schema, and bind every trigger to a
function in that same schema.
**Acceptance:** a schema rebuilt from metadata carries the same guard objects as
`public`; each trigger executes a function in its own schema; the personal
billing acceptance suite passes with no exclusions on the rebuilt schema;
applying the step twice is a no-op; the build path fails closed instead of
silently skipping guards; and the drift test that pins the module to migration
history is deterministic — it must produce the same verdict on a cold bytecode
cache and in any test-run order.

## Delivered so far (branch `fix/p11-t24-test-schema-guards`, accepted source `04429f7c`)

`scripts/schema_guards.py` holds the 26 trigger functions and 42 triggers with a
`{s}` placeholder instead of a schema literal, and quotes the target identifier.
`scripts/setup_test_db.py` applies them after `create_all`/stamp and before the
reference rows, raising instead of continuing when that fails.
`tests/tooling/test_p11_t24_schema_guards.py` re-derives the inventory from the
migrations by AST. On a scratch schema the rebuilt database carried 42 triggers
and 26 functions, none bound to another schema, and the personal billing suite
passed 46/46.

## Open defect — the drift test is order dependent

`_executes()` walks the module AST breadth-first, and `migration_function_bodies()`
takes the last body it sees per function. Revision `0103` legitimately installs
two bodies of `check_personal_llm_dispatch_account` from one helper: the
`upgrade` call passes `allow_platform_operator=True`, `downgrade` passes
`False`. Which one the walk yields second depends on node depth and on whether a
previous test already imported the revision, so the test passes on a warm
bytecode cache and fails on a cold one. Reproduced: with
`tests/tooling/__pycache__` removed the file fails, without removal it passes;
`python -m scripts.ci.run_offline` failed on `0850009a` in hosted CI.

Sorting the call sites, sorting the expanded text and restricting the scope to
module-level assignments were each tried and each either failed other tests or
left the ambiguity in place.

**Required fix:** decide the final body by revision semantics — the body the
`upgrade` path installs is the one a migrated database has — instead of by
traversal order. The test must fail loudly if that cannot be decided, never pick
silently. Acceptance for this slice adds: the file gives the same result on a
cold and a warm cache, and `scripts.ci.run_offline` stays green when the tooling
tests run before and after the other manifest entries.
