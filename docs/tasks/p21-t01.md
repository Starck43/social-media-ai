## Critical verdict

The proposed four-table rewrite is not justified. Providers/models already share
`llm_providers`/`llm_models`; analysis methodology is `agent_scenarios`, while
workspace chat policy is on `tenants`. There are no separate modality catalog
tables or the proposed nullable `aspect_ratio`/`top_k`/`negative_prompt` columns.
Historical provider/model strings in accounting are intentional snapshots, not
live configuration duplication. Do not delete them or accepted ledgers.

Confirmed risks are inconsistent parameter resolution, a soft read-then-compare
workspace cap, legacy unwired budget foundations alongside the gated personal
billing path, and process-local LLM throttling. Source review is not a deployed
schema audit or proof of capacity/security. The existing personal-owner guards
must not become a broad `owner OR platform` bypass.

## Recommended data delta

| Relation | Change and reason |
| --- | --- |
| `llm_catalogs` | New ownership root: platform or personal, with enforced owner constraints. Shared schema, separate authorization. |
| `plan_model_grants` | New many-to-many plan/capability/model relation, with ordering and one default per plan/capability. No per-user copies of managed models. |
| `llm_rate_buckets` | New operational state for upstream quota pools shared across workspaces. Existing social-connection buckets cannot represent a platform LLM key. |
| `llm_providers`, `llm_models` | Reuse tables and global IDs; add catalog/reference/validation metadata only when its consumer is specified. |
| `llm_model_health` | Conditional only: move hot counters if measured contention justifies the extra relation. |
| `tenants.agent_model` | Candidate legacy-column removal after usage/data inventory, compatible mapping and approval; ambiguous names never auto-backfill. |
| Existing accounting/credential tables | Retain accepted contracts, evidence and key-family separation; no generic replacement vault/quota table. |

Baseline recommendation: three additional relations, not a smaller four-table
database. A fourth operational relation requires measurement. Columns increase
for ownership and actual supported capabilities; obsolete columns may decrease
after consumer migration. Every migration records additions, removals, consumers
and rollback; fewer tables alone is not an optimization criterion.

## Model, agent and credential conclusions

- One model/provider schema serves managed and personal catalogs; model identity
  remains distinct from execution identity, payer, plan allowance and credential.
- Model rows describe API identity, supported input/output capabilities, real
  limits and versioned pricing. Image input is not image generation; a single
  modality enum cannot describe all multimodal models.
- Tenant/scenario policy supplies generation defaults and restrictive overrides.
  Provider-aware typed validation omits unsupported parameters; temperature is
  not mandatory for every endpoint. `model_params` cannot contain credentials,
  arbitrary URLs, permissions, budgets or retry authority.
- Existing consent-bound personal task execution stays compatible. New plan
  defaults cannot silently replace personal keys or change the payer; arbitrary
  tenant/scenario FKs do not constitute personal-key consent.
- Managed credentials stay in an allowlisted deployment secret store; BYOK stays
  encrypted and owner-scoped. Fernet is authenticated encryption, not plaintext.
  AES-GCM/envelope migration requires a concrete threat model and rotation design.
- Atomic spend reservation/settlement, provider RPM/TPM, workspace fairness and
  execution guardrails are different controls. Preserve the accepted explicit
  UNDEFINED-price policy; token counts alone cannot price every modality.
