## Problem

At the planning baseline, the plan contract declares `social.collect`, `social.cached`,
`social.analyze`, `social.digest`, `mail.read_headers`, `mail.group_by_sender` and
`messages.store_groups`. The canonical runtime map implements the two mail read/group operations.
Admission and trigger configuration reject operations without runtime support. Admission also
rejects LLM steps with `payer_unavailable`; the worker separately refuses runs with a non-null
payer. The worker already passes the literal `Step` and pinned methodology through its execution
context. The missing LLM executor must use that snapshot.

The existing social handlers run collection and analysis through the legacy dispatcher and
`task_pipeline`. The canonical execution plan publisher has no production caller at this baseline.
T10 implements `messages.store_groups` and sender-group persistence on its own branch
(`6b052806`, unmerged at this review).

## Deliverable

Complete the canonical execution path using the existing collection, cache, analysis and digest
services. Preserve the accepted Task identity, immutable plan revisions, TaskRun admission,
capability and authorization checks, and run receipts. Keep existing legacy dispatch available
during rollout. Replacement or retirement of legacy execution requires explicit owner approval
and belongs to T12 after parity, alias and schedule reconciliation, single-dispatch verification
and a tested rollback. Record the approved transition separately if one is chosen.

1. Provide a permission-checked shared preview/publication command through the authenticated v2 task API.
   Preview effective operations, authorized resource bindings, selected methodology and version,
   execution mode, destination and payer requirements. Preview has no publication or launch side
   effects. Publish against the actor's current edit rights and the expected `Task.version`. Revalidate
   the selections and attach the immutable plan revision to the existing Task ID. Execution resolves
   the published revision and pins it to the run under the accepted admission contract. Publication
   creates no run.
2. Implement `social.collect`, `social.cached`, `social.analyze` and `social.digest` through
   canonical admission and the worker.
   Execute the literal step against its pinned methodology; resolving the mutable scenario ID
   alone is insufficient. Recheck actor, resources, capability and payer at admission and execution.
   Fail closed on revoked rights, binding drift or an unavailable payer. Record approved paid
   usage with the run and use existing fencing and idempotency contracts so retry or replay cannot
   duplicate results or paid work. Dry-run follows the accepted contract and must not create paid
   usage or external effects.
3. Distinguish parseable plans, runnable plans and schedulable plans. Graph validation can accept
   a known operation whose runtime is unavailable; availability must be reported explicitly by
   preview and consistently enforced by publication for executable plans, admission and the
   worker. A runnable on-demand plan can run once without a trigger. Scheduling additionally
   requires a supported schedule, authorized execution context and a published runnable revision.
   Run Now is separate and preserves an existing schedule and its cursor.
4. Validate selections against the supported graph. The prototype permits multi-select but
   `check_graph` rejects mixed mail/social routes. Support selections representable by the current
   graph and show an explicit disabled state or explanation for incompatible combinations.
   Preserve the user's draft, keep multi-select for compatible resources and report mixed-route
   execution as unavailable in this slice. Coordinate
   correspondence availability with T10.

## Scope

Resource schema redesign and new providers belong to separate work, including T23. T22 owns typed
optional automation parameters. T10 owns mail ingestion and `messages.store_groups`. Preserve
existing write-action consent and idempotency boundaries.

## Acceptance

Through a user-accessible canonical task surface, create a title-only task, preview and publish
automation on the same ID, and explicitly run it. Use no preseeded plan revision or direct
service-only setup for publication. Verify a collection-only route stores results with no LLM scenario or LLM charge. Existing
connector entitlements, budgets and quotas still apply. Verify cached reads,
paid analysis and digest, including pinned methodology, attributable payer and visible receipt. Hand this
flow and its evidence to T08 for the full editor. Verify that publishing alone creates no run,
that manually launching a scheduled task preserves the schedule, and that a scheduled occurrence
dispatches only once.

Check the declared/runtime capability boundary, including mixed-route selection, as well as
revoked access and payer between publication, admission and execution. Verify dry-run and replay
behavior, including result and paid-usage idempotency. Use T10's separate correspondence evidence
when integrating that route.

## Verification at implementation

Run focused execution plan, admission, worker, trigger and legacy social regression suites.
Record the exact revision and user-accessible publication-to-receipt evidence. Use an isolated
test schema for database scope.
