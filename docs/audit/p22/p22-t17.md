## What was accepted

Closing and reopening are confirmed commands over one exact task version. The
preview states the effects first — status change, successor occurrence, stored
and enabled schedules, an already admitted run, retained receipts, next due —
and returns a signed token bound to tenant, actor, task, version, operation and
the reopening's schedule choice (600 s). Confirmation rechecks the actor, locks
workspace → task → trigger in the scheduler's order and compares the effect
fingerprint before writing, so an occurrence admitted after the preview forces a
re-preview.

- Closing a human recurrence without a schedule creates its successor; a task
  under automation (armed or paused) closes without silently generating another
  occurrence, and a repeated close reuses the occurrence it already admitted
  instead of inserting a second one.
- Future triggers are disabled in the same transaction; every run receipt is
  retained and an already admitted `pending`/`running` run is reported rather
  than cancelled. Admission itself refuses closed work (`task_closed`, `409`).
- Reopening restores `todo` and re-arms a paused published schedule only when the
  confirmation asked for it, through the accepted T04 arming path. An unavailable
  schedule refuses the reopening instead of half-opening the task.
- Replay converges without a second version bump or duplicated effects.
- `close`, `reopen` and `schedule` exist as API routes, CLI commands and agent
  tools over the same services; the acceptance surface exposes them with an
  `enabled` flag and keeps manual `run` independent of scheduling.
