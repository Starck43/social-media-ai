# P10-T03 — (AUD-03, P1) — separate self-service profile updates from privilege updates

Registry: [ROADMAP](../../ROADMAP.md#p10); current status/owner live there.

## Scope and acceptance

(AUD-03, P1) — separate self-service profile updates from
  privilege updates; accept: profile updates cannot elevate authority; fresh
  privileged operator policy and endpoint/manager negative controls;
  depends: shared lane with P10-T02

Source of truth for the finding: `docs/audits/2026-10-15-dev.md#aud-03` on the
audit branch (`audit/dev-contracts-2026-10-15`), row AUD-03.

## Context

The audit was written against `7ba5fe4`. `eb6cad6` already replaced the model it
described: `UserUpdate` carries `username`/`email` only, `UserManager.update_user`
refuses any other key and re-reads the acting account, and platform-role changes
moved to the dedicated `PUT /api/v1/users/{id}/platform-role` route. The audit
branch itself records this as a *source replacement, not an independent
acceptance claim*, so what remains for this task is the bounded proof that the
separation actually holds on the current integrated revision — through the real
endpoint and the real manager, not only at the schema.

Legacy evidence at `7ba5fe4`: `UserUpdate` accepted `is_superuser` and
`is_active`, and the endpoint forwarded every field to `update_by_id` after a
self-or-superuser check, so a holder of `user.update` could set `is_superuser` on
itself. That path must not come back through the schema, the manager or the
privileged route.
