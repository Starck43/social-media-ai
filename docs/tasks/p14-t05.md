## Goal

Schedule and deliver approved birthday and anniversary greetings via email, Telegram bot, or MAX bot through the existing `P15-T05` persistent outbox (`OutboxStore`), enforcing `greeting`-purpose opt-in consent (`D15`), `comms.outbox` `CONFIGURE` approval (`D14`), and once-per-year repeat prevention (`GreetingHistory`).

## Plan

1. **Greeting delivery service (`app/services/crm/greetings.py`, `app/services/crm/messaging.py`)**:
   - Accept an existing `GreetingHistory` draft (`greeting_id`) or `(contact_id, event_type, year)`, target channel (`email`, `telegram`, `max` — never `phone`, `bitrix24`, or MTProto per `D7`), `connection_id`, `identity_id`, `scheduled_at`, and `idempotency_key`.
   - Enforce `D15`: require an active, non-withdrawn `ContactConsent` row for `(contact_id, channel, purpose="greeting")`. A channel or identity merely present on a Bitrix24 CRM card without a recorded `ContactConsent` row is rejected (`consent_required`).
   - Append a tamper-evident one-click unsubscribe footer (`D7`/`D16`) with an absolute URL (`settings.PUBLIC_BASE_URL`) and TTL-bounded HMAC-SHA256 token (`settings.UNSUBSCRIBE_TOKEN_TTL_SECONDS`) bound to `(tenant_id, contact_id, channel, purpose="greeting")`. Keep `GreetingHistory.draft_text_encrypted` as the clean approved greeting draft text; store the body with the expiring unsubscribe URL only in `OutboxMessage.content_encrypted`.
   - Schedule the greeting through the existing `P15-T05` `OutboxStore` (`draft` + `schedule` with `purpose="greeting"`), binding `GreetingHistory.command_id = target.command_id`, updating `GreetingHistory.channel` and `GreetingHistory.status = "approved"`, and recording `ActionAuditEvent` (`comms.campaign_approve` / `comms.campaign_send`).
   - **D10 / D14 approval semantics:** Invoking `send_greeting` (`POST /api/v1/integrations/bitrix/greetings/send`, gated by `comms.outbox` `CONFIGURE`) is the operator's explicit approval action for a previously generated `GreetingHistory` draft (`status="draft"`). Per `D10`, approval state, `approved_hash`, `approval_expires_at`, and cancellation live in `OutboxStore` (`OutboxMessage` / `OutboxTarget` / `BusinessCommand`), so transitioning `GreetingHistory.status` from `"draft"` to `"approved"` inside `send_greeting` records the operator's `OutboxStore.schedule` approval rather than silent auto-approval.
   - **Year-scoped unsubscribe semantics:** When a recipient clicks the one-click unsubscribe link for `purpose="greeting"`, `process_one_click_unsubscribe` records the withdrawal via `ContactManager.record_consent` (under `SELECT ... FOR UPDATE` row lock on `Contact`) and cancels/skips only unclaimed `OutboxMessage` / `OutboxTarget` and `GreetingHistory` rows for the current year (`effective_now.year`), preserving historical rows from prior years.
   - **Token reuse:** An unsubscribe link can be submitted repeatedly until its signed `iat` reaches the configured TTL. Each successful request appends a withdrawal; therefore a still-valid link can withdraw consent again after a later grant. A newly scheduled message receives a newly issued token.
   - Synchronize and project `GreetingHistory` delivery state (`approved`, `sent`, `failed`, `unknown`, `skipped`) from the linked `OutboxMessage` / `OutboxTarget` / `BusinessCommand` via SQL `WHERE` filters without building a second outbox or sender.
2. **API endpoints (`app/api/v1/endpoints/bitrix.py`)**:
   - `POST /api/v1/integrations/bitrix/greetings/send` (requires `comms.outbox` `CONFIGURE` and `source` `VIEW`).
   - `GET /api/v1/integrations/bitrix/greetings/{greeting_id}/status` to inspect real-time delivery status from the linked outbox/command row.
