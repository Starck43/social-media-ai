## Defect

`0149_outbox_reply_evidence` creates `outbox_reply_evidence.contact_pii_marker` with
explicit DDL. A schema rebuilt from metadata (`scripts/setup_test_db.py`) cannot create
migration-only objects and replays them from `scripts/schema_guards.py#GUARD_TRIGGERS`,
which never gained that table.

Measured before the fix:

```text
public        outbox_messages.contact_pii_marker, outbox_reply_evidence.contact_pii_marker, outbox_targets.contact_pii_marker
p20t12_audit  outbox_messages.contact_pii_marker, outbox_reply_evidence.contact_pii_marker, outbox_targets.contact_pii_marker
test_schema   outbox_messages.contact_pii_marker,                                        outbox_targets.contact_pii_marker
```

`outbox_reply_evidence` stores reply text, so a missing marker means those writes never
advance the contact PII marker that retention and erasure read. The gap was found while
applying `public` `0145` → `0151`; the migration apply was clean and is unrelated to the
cause.

The detector already existed and was red on `dev`:
`tests/tooling/test_p11_t24_schema_guards.py::test_frozen_baseline_and_post_baseline_migrations_match_guard_module`
reported `migration-only=[("contact_pii_marker", "outbox_reply_evidence")]`.

## Fix

1. `scripts/schema_guards.py`: `outbox_reply_evidence` added to the PII-marker table
   tuple, next to the other outbox tables, with a comment naming `0149` as the owner of
   the DDL.
2. The live `test_schema` schema replayed that trigger through the module's own
   `function_ddl` + `GuardTrigger.definition` (idempotent drop/recreate; test-schema
   setup is pre-authorized), so current evidence and future rebuilds agree.
3. `0149` untouched: a fresh migration run already creates the trigger, and rewriting
   applied DDL is forbidden.
