## Goal and existing boundaries

Protect personal connection secrets, make the credential used for each source
explicit and auditable, and give operators a clear separation between deployment,
platform and personal configuration. Avoid breaking existing users or silently
changing the identity used by a source.

- **Deployment:** one application's identities, service and bot credentials,
  encryption key and infrastructure settings, provided by deployment configuration
  (`.env` or equivalent secrets manager). Never commit or display secret values.
- **Shared catalog:** non-secret platform API endpoints, version, OAuth URLs and
  callback in one shared `Platform.params`, managed by authorized operators. Code
  bootstrap values and legacy environment inputs are initialization/migration
  inputs, not competing runtime overlays; see [Q-16](../audit/q-16.md).
- **Personal and workspace connections:** VK/Telegram personal credentials use
  `user_credentials`; mail connections use `workspace_connections` plus encrypted
  `workspace_connection_secrets`, scoped to both tenant and owner. This is not
  currently one universal table. Any unification requires its own reviewed design
  and data-preserving migration; do not silently merge scopes. See
  [P12-T08](../audit/p12-t08.md) and [connector configuration](../CONNECTOR_CONFIGURATION.md).

At source snapshot `279e23bae487f8e1be75da4168993266c146331a`,
[`vk_oauth.py`](../../app/services/social/vk_oauth.py) encrypts the VK access token
but stores its refresh token in `user_credentials.meta` as plain text on create
and refresh. This is a source-code finding, not a claim about the values or rows
in any deployment. The same file's pending PKCE verifier uses encrypted storage.
The existing rotation and renewal behavior must not be weakened by the fix.

## Ordered implementation slices

### 1. Protect refresh tokens — first priority

- Design a single encrypted canonical refresh-token representation with the
  existing key-management conventions; do not expose tokens in `meta`, admin,
  logs, exceptions, diagnostics, exports or API responses. Metadata may carry
  a non-secret availability/state indicator, not the token itself.
- Inventory every read, write, refresh, status and revoke path before changing
  it. Preserve owner scoping, expiry, provider rotation semantics and OAuth/PKCE
  state. Prevent concurrent refresh callers from replaying a rotated token:
  specify and test the actual locking/compare-and-set and failure semantics.
- Add a reviewed Alembic data migration or an explicitly authorized equivalent
  migration procedure with safe handling of null, malformed and pre-existing
  values. No secret values in migration output; do not leave plaintext as a
  parallel runtime source of truth. Define idempotence, transaction boundaries,
  backup retention and a forward-recovery plan before changing stored secrets.
  Inspect the real Alembic head; do not reserve a revision number here.
- Validate upgrade and recovery on an exclusively owned synthetic test schema;
  verify synthetic records and full schema inventory cleanup. Public/production
  apply requires separate owner authorization after validation and backup.
  Encryption-key replacement requires a separately tested re-encryption and
  recovery plan; losing the current key is not a routine rotation.
- Assess whether legacy database backups, exports or access require restriction
  and whether affected VK sessions need revocation/re-authorization; do not claim
  an actual exposure or revoke credentials without owner approval.

### Confirmed refresh-token design inputs

Owner-supplied update in the linked dialogue supersedes the earlier PR comment's

| Surface | Role | Required change |
| --- | --- | --- |
| `vk_oauth.py:249` | OAuth login writes `meta["refresh_token"]` | Use encrypted canonical storage in every `_store_vault_token` branch. |
| `vk_oauth.py:332` | Rotation writes `meta["refresh_token"]` | Persist the new encrypted state; never retain the old refresh as fallback. |
| `vk_oauth.py:298` | Reads the secret for the refresh request | Read canonical encrypted storage under refresh coordination. |
| `connections.py:299` | Selects `renewable` versus `reauth` from token presence | Read the non-secret availability/state indicator instead. |
| `vk_connections.py:315`, `_vault_state` | Selects `renewal_available` versus `reauthorization_required` | Read the same non-secret indicator with consistent semantics. |
| `connections.py:58`, `_SECRET_KEYS` | Metadata sanitizer; not a logic reader | Preserve secret redaction, including legacy input. |

Two writes, three operational/status reads and one sanitizer reference are listed.
`meta` currently serves both secret storage and UI status. The storage cutover must
switch BOTH status readers to a non-secret indicator in `meta` in the same delivery;
otherwise valid sessions will permanently appear to require reauthorization.
Maintain the indicator transactionally with canonical encrypted state; it is derived
status, not a second secret or an independent authority. Define unavailable,
revoked and unreadable-key states without claiming renewability from a stale flag.

**Confirmed concurrency defect:** `refresh_user_token` / `renew_if_expiring` use
`newest()` → HTTP refresh → `update_by_id` without row locking or CAS in
`user_credential_manager.py` / `vk_oauth.py`. Two callers can reuse a refresh token;
the losing request then writes `refresh_failed_at` and falsely marks a successfully
rotated session as `reauth`. This is an owner-confirmed defect, not a theoretical
risk or a new live-provider observation.

- Coordinate the full refresh cycle across processes BEFORE HTTP: choose a row
  lock or atomic single-flight claim with bounded recovery, re-read after acquiring
  ownership, and specify transaction/network timeout boundaries. A CAS only after
  duplicate HTTP requests does not prevent token replay.
- Bind success/failure persistence to the credential generation or claim used.
  A stale failure must never poison a newer valid session; waiting callers reuse
  the new state instead of replaying a consumed refresh token.
- Preserve `_store_vault_token` behavior on existing-row update AND
  create-then-update branches; change representation, not the established contract.
- Preserve `_mark_refresh_failed`, `meta["refresh_failed_at"]` and
  `REFRESH_FAILURE_COOLDOWN` across metadata rewrites. Real current failures retain
  their cooldown; stale failures cannot overwrite newer success.
- Preserve no-old-refresh-token-fallback in any new column/table. Define recovery
  for missing replacement or failed persistence; never restore a consumed token.
- Required focused tests: both UI readers report renewable using the new indicator
  without plaintext; every persistence branch preserves failure metadata; parallel
  callers do not reuse one refresh generation; stale failure cannot override
  success; genuine failures retain cooldown; absent rotated refresh does not fall
  back to the old token. Provider calls remain mocked.

### Delivered in the draft concurrency increment

- `user_credential_manager.py::locked_vk_token` takes a short transaction with
  a bounded lock wait, locks the active user then re-reads/locks their newest
  active VK token. The stable user lock also serializes OAuth row creation.
  Every write receives that exact manager-owned session.
- OAuth storage now creates a complete row atomically or updates the existing
  row under the same lock. Unrelated metadata survives; successful explicit
  reauthorization deliberately clears only obsolete failure/claim state.
- All automatic/direct refresh paths share one claim implementation. The pending
  attempt is COMMITTED before HTTP; finalization re-locks/re-reads and checks row
  and attempt IDs. Stale success/failure cannot overwrite a newer OAuth login.
- Failed/ambiguous/cancelled attempts are not automatically reclaimed: the provider
  might already have consumed their token. Reauthorization is the recovery path;
  a timer that blindly retries would reintroduce replay. Existing legacy failures
  retain the six-hour cooldown; claim failure remains fenced even after it.
- Overlapping callers seeing a pending attempt return no renewed token rather
  than submitting duplicate HTTP. A caller reaching the newly renewed row gets
  the current access token. Waiting/polling UX and pending/crash status must be
  finalized with both status readers before deployment.
- No fallback to an old rotated refresh. Diagnostics remain bounded/secret-free.
  New focused tests cover orchestration interleavings, SQL lock compilation,
  cancellation, failed commits, stale writes, OAuth branches and metadata.
  Existing privacy tests were adapted to claim/finalization writes without
  dropping secret-leak, hostile-exception or cancellation assertions.
