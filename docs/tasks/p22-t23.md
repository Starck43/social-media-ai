# P22-T23 — Generalize the resource binding so a new platform is data, not code

[Phase](../phases/p22-universal-tasks.md) · [Target architecture](../product/UNIVERSAL_TASKS.md) ·
[Connector extension seam](../connectors/CONNECTOR_JOB_EXTENSION_SPEC.md)

**Dependencies.** [P22-T02](../audit/p22/p22-02.md) (connector capabilities and grants),
[P22-T03](../audit/p22/p22-03.md) (execution plans and bindings), [P22-T06](../audit/p22/p22-06.md)
(legacy mapping), [P22-T08](p22-t08.md) (create editor).

**Blocks.** Adding any social platform beyond VK and Telegram — MAX, Instagram, or a
user-account action on either. Also blocks scheduling a `DISK_FOLDER`, `PORTAL` or
`PAIRED_ROOT` resource, because those kinds cannot be pinned at all.

## Problem

`Binding` hardcodes two providers' credential shapes:

```python
class Binding(Contract):
    name: Name
    capability: str = Field(max_length=80)
    resource_id: PositiveID
    path: str | None = Field(default=None, max_length=1024)
    vk_access: dict[str, JsonValue] | None = None          # VK only
    telegram_grant: tuple[PositiveID, PositiveID] | None = None  # Telegram only
    workspace_account: str | None = Field(default=None, pattern=r"^[a-f0-9]{64}$")
```

`app/services/execution_plan_contracts.py:34-56`. The same two fields are repeated in
`ResourceSelection` (`app/integrations/task_resources.py:53-59`), and the generic
`WorkspaceAccountPin` is **explicitly refused for social resources**:

```python
selection.workspace_account is not None
and (capability.kind in (ResourceKind.SOCIAL_SOURCE, ResourceKind.PAIRED_ROOT) or ...)
```

`app/integrations/task_resources.py:167-170`. That exclusion is the reason VK and Telegram each
needed a bespoke pin: the generic one was closed to them.

So `Platform` is a working data table — `platform_type`, `base_url`, `params` — but it is **not an
extension seam for code**. A new row in `platforms` changes nothing, because the pin shape, the
resolver and the adapter factory are all keyed on the provider name in Python.

Twelve sites, and two of them are **latent bugs**: the ternary
`PlatformType.VK if capability.provider == "vk" else PlatformType.TELEGRAM` silently maps *any*
non-VK provider to Telegram. It is correct only because no third social provider exists yet.

## Answers to the owner's questions

**Is `Platform` wasted?** No. It correctly holds per-platform data: `base_url`, API params,
`is_active`, and `platform_type` is already an eight-member enum including `EMAIL`, `BITRIX24`,
`ONEC`, `YANDEX_DISK`, `MAILRU_CLOUD` and `LOCAL_GATEWAY`. What it cannot do is teach the code a
new provider. Keep the table; the missing piece is a pin schema on `Capability`.

**What is `Source`, and is it needed?** `Source` is a collectable social object on a `Platform`:
`platform_id` + `external_id` (unique per tenant and platform) + `source_type` + `params` +
`last_item_id` (push watermark) + `owner_task_id` (task-scoped query lane) + `owner_user_id`.
It is load-bearing: `_social_issue` resolves it by id and platform type, `_dynamic_sources` selects
it for all-authorized scope, `agent_task_sources` is an M2M to it, and `AIAnalytics` holds an FK to
it. Dropping it would cost the Telegram push watermark, per-source search params, analytics
attribution and the query lane.

**Should it be dropped?** No — and more importantly, **dropping it would not buy the extension
goal.** The blocker for MAX or Instagram is the pin and the binary resolver, not the `Source`
table. Cutting `Source` is a large migration that leaves the actual problem untouched. `Source`
stays as the social-object registry; the generic resource concept is `WorkspaceConnection` +
`ResourceKind` + a selection.

## Deliverable

One generic pin, declared by the capability, validated by the capability.

1. **Add a pin schema to `Capability`.** `Capability` today is
   `(provider, kind, handler, method, installation_keys, direction)`
   (`app/integrations/catalog/task_capabilities.py:22-30`) and says nothing about how a resource
   is pinned. Add a declared pin kind — a small tagged union, e.g. `service_credential`,
   `personal_credential`, `grant_pin`, `account_pin`, `path_only` — so the catalog states what a
   provider needs instead of `Binding` enumerating providers.
2. **Replace the two named fields with one.** `Binding` and `ResourceSelection` carry a single
   `credential_pin` (tagged, bounded, secret-free) validated against the capability's declared pin
   kind. `vk_access` and `telegram_grant` become two values of that union, not two columns.
3. **Open `workspace_account` to social resources.** The exclusion at
   `task_resources.py:167-170` exists because social pins were special-cased; once the pin is
   generic, a social resource may use the opaque account pin like mail and disk do.
4. **Make the resolver provider-agnostic.** `_social_issue` must dispatch on the capability's pin
   kind and the platform row, not on `provider == "vk"`. Fix the two
   `VK if ... else TELEGRAM` ternaries (`task_resources.py:82`,
   `task_execution_plans.py:146`) so an unknown provider fails closed with
   `unsupported_capability` instead of silently becoming Telegram.
5. **Register adapters, do not branch on them.** `collection/context.py` `_CAPABILITIES` and
   `adapter()` become one explicit allowlisted registration per provider, matching the decision
   already recorded in `docs/connectors/CONNECTOR_JOB_EXTENSION_SPEC.md`: "one explicit factory
   registration", no dynamic plugin loader.
6. **Prove it with a third provider that does not exist yet.** Add a test-only provider to the
   catalog with a different pin kind and assert that: it parses in a `Binding`, it resolves, it
   refuses when its pin is wrong, and it appears in a plan without touching `Binding` again. That
   test is the acceptance of this card — if adding it still requires editing `Binding`, the
   generalization failed.

## Out of scope

- **Implementing MAX or Instagram.** This card makes them possible; it does not add a provider,
  an adapter, an operation or a credential flow. A real provider is its own card with its own
  security review.
- **Write actions.** `agent/toolset/actions.py` branches VK vs Telegram for comments, replies and
  DMs. Generalizing writes needs its own consent, idempotency and ambiguous-outcome contract
  (`CONNECTOR_JOB_EXTENSION_SPEC.md`, rule 2). This card may leave that branch in place and say so.
- **New resource kinds.** `DISK_FOLDER`, `PORTAL` and `PAIRED_ROOT` still have no `Operation` in
  `execution_plan_contracts.py:94`. Making them schedulable is separate work.
- **Publishing an execution plan.** `execution_plan_service.publish` still has no caller in
  `app/`; see [P22-T08](p22-t08.md)'s audit record. Nothing here depends on it.
- **`AgentTask` payload and form shape.** That is [P22-T22](p22-t22.md). Do not touch it here.

## Acceptance

A test-only third provider, added only to the catalog, binds and resolves through `Binding` and
`resolve_task_resource` with no edit to `Binding`, `ResourceSelection` or the resolver's provider
dispatch. A wrong pin for that provider is refused with a bounded code. An unknown provider fails
closed rather than resolving as Telegram.

VK and Telegram keep working unchanged: the existing suites for `task_resources`,
`execution_plan_contracts`, `task_execution_plans`, `task_plans`, `collection/context` and the
VK/Telegram adapters pass without modification to their expectations. A stored plan revision
written before this change still loads and resolves — the pin union must read the old
`vk_access` / `telegram_grant` shape, or the migration must rewrite it, and the choice is recorded.
