## Goal

One reusable server-side workflow for every external write in P14–P19 (CRM, messaging, calendar, 1C, documents): nothing writes without an approved, unexpired, unchanged command.

## Baseline

- P9 `telegram.bound_message.v1`: preview → approve → separate execute with rechecks ([ACTION_ACTIVATION](../ACTION_ACTIVATION.md)).
- P9-T08 action ledger and `bot_actions.history`.
- P12-T04/T05 pure approval binding helpers (outbox, cases).

## Plan

1. Define a capability registry: `domain.operation.vN` with risk class, required workspace permission, default `enabled=False`, per-capability kill switch setting and approval policy (`per_item`, `per_batch`, `connection_consent`).
2. Persist `business_commands` (tenant, capability, actor, target refs, canonical payload JSON, payload hash, preview snapshot, state `draft→previewed→approved→claimed→succeeded|failed|unknown|cancelled|expired`, idempotency key, TTL, approver, timestamps).
3. Approval binds actor, tenant, capability version, payload hash and TTL (default 15 min, max 24 h for scheduled sends); any payload change requires a new approval.
4. Execute admits only the approved command, rechecks membership/role/connection state/kill switch inside the claim transaction, calls the adapter once and records the outcome; timeouts → `unknown` with a reconcile hook, never blind resend.
5. Batch support: one approval over an explicit frozen target list; per-target child rows with their own outcome and idempotency.
6. Expose service API + `/api/v1/commands` (preview, approve, reject, execute, status) and a minimal `/app` review list reusing existing action-review UI patterns; audit every transition ([P13-T05 accepted](../audit/p13-t05.md)).

## Acceptance

- Changed payload, expired TTL, revoked membership, disabled capability or kill switch → execution denied and audited.
- Concurrent double execute claims once.
- Timeout yields `unknown`; reconcile can settle it; no automatic resend.
- Cross-tenant command IDs are not found.
