## Recorded choice for the request-cost surface

The card allowed either sharing the read service or removing `cache_ttl_seconds` from the public API. **Sharing the read service was chosen.** It restores the accepted P17-T02 contract ("optionally cached in-memory only when the caller explicitly requests a positive `cache_ttl_seconds`"), which the per-request construction had silently broken, and it keeps the accepted public surface intact. The default stays `0`, so no rows are cached unless a client asks for it; the cache key carries tenant, actor, connection, account, catalog hash and plan fingerprint, and the bound is the caller's TTL (≤ 300 s) over ≤ 128 entries. A client that asks for a TTL now receives rows up to that TTL old — the behaviour the field always promised.

## Boundary review

The read-only transport, the shared provider budget policy, the connection allowlist and the tenant/actor scoping are untouched. The shared service holds no per-request state: the caches are keyed by tenant (the result cache by actor as well), the limiter and the managers are stateless, and every cache mutation happens between awaits. The catalog is still served only after the authorization check, and a changed `metadata_sha256` pin still never serves a stale catalog. A continuation with a foreign `history_id` is refused before any provider request — the ordering test proves that the catalog is not fetched for such a row.

## Findings

None blocking. Residual, recorded for a later task: a connection edited outside the three mutation paths keeps its catalog for at most the 60 s TTL (the `metadata_sha256` pin already forces a fresh catalog after a re-verification); the shared result cache can hold up to 128 × 1000 rows in memory when a client opts in — the bound is the accepted P17-T02 design.

## Limitations

No live 1C base and no provider LLM call. The in-process query metadata deque is now process-wide and holds PII-free metadata only (entity set, plan fingerprint, counters).
