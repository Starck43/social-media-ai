## Findings

### F-1 — P13-T05 needs a migration, but the queue says it has none

`BUSINESS_MODULES` and the Wave 0 row say P13-T05 has **no migration** ("No
migration; start from current `dev` after #308"). The audit-code allowlist is
not application-only: `app/models/audit/action_audit_event.py:41` enforces
`CHECK (action = 'scheduling.task_admit')` in
`ck_action_audit_events_action`, mirrored by `_SAFE_ACTIONS` in
`app/models/managers/action_audit_event_manager.py:17`, by the baseline SQL
(`migrations/versions/baseline_0118.sql`). The guard objects in
`scripts/schema_guards.py` do not repeat it, so the model plus the baseline
DDL are the source of truth.

Adding `crm.*`, `comms.*`, `planner.*`, `calendar.*`, `onec.*`,
`files.connector.*`, `documents.*`, `commands.*` therefore requires a DDL
change to the CHECK constraint — a migration. With that, P13-T05
(a) becomes the **first** migration in the business queue, (b) cannot be a
remote task without a local DB check, and (c) invalidates the
"T03 → T04 → T07 → P14-T02" order unless T05 is placed before T03.

Severity: blocking for the dispatch order, not for the documentation itself.

### F-2 — Wave 0 says "while PR #327 remains open", but two Wave 0 tasks depend on it

The Wave 0 heading is `### Wave 0 — while PR #327 remains open`, yet
`P18-T01` states "Depends on: P12-T12 integrated (PR #327)" and P13-T02 is in
Wave 1 gated by "#308 and #327 merged". Reading the two Wave 0 rules together,
P18-T01 is claimable only for preparation ("draft contracts; final work and
acceptance wait for P12-T12 integration" is in the table, but the card's
dependency line is unconditional), and P13-T02 formally belongs to a later
wave. The card and the phase table disagree, which invites a claim before the
trigger holds.

Severity: minor, wording.

### F-3 — P13-T02 has no migration, but the blind index does

P13-T02 (Wave 1) and its card are marked "No migration". A keyed HMAC blind
index for exact-match lookup needs a stored index value per protected field,
i.e. new columns and a migration. The rate-limiter (P13-T03) and the contact
core ([P13-T07 accepted](p13-t07.md)) are already migration-bearing; if the blind index lands in new
tables owned by T07 (rather than in new tables of its own) the queue rule
still needs one sentence saying where the columns live, otherwise T02 and T07
will both try to be the second migration.

Severity: minor, but it affects the concurrency rule.

### F-4 — FTS availability is assumed, not checked

D3 and P15-T04/P19-T06 propose a PostgreSQL full-text index over an encrypted
content cache. No `to_tsvector`/`tsvector`/`pg_trgm`/`unaccent` usage exists in
`app/` or in the migrations, and the deployment target and the accepted
search locale are not recorded, so whether a Russian-language FTS
configuration is available is an open assumption — acceptable for a draft, but
D3 should be answered with that dependency stated.

Severity: informational.

### F-5 — P19-T01's "changes existing 0122 data" is the wrong reason

The P13 phase Wave 4 table and the P19 card put P19-T01 on the local lane
because it "changes existing 0122 data". `0122_knowledge_evidence.py` creates
tables and the `guard_document_revision_content()` trigger and writes no rows.
The real constraint is the trigger: it refuses in-place content changes, so
P19-T01 must define how new revision rows are appended, and that is a schema
decision (a migration extending the model), not a data backfill. The local
lane is still right — for the migration and the guard, not for data.

Severity: minor, reasoning only.

### F-6 — `P8-T34` is `IN_PROGRESS`, not `READY`, in the merged `dev`

Not caused by this PR, but it is what the new plan inherits. Commit
`8334cdab docs: claim owner-reassigned P8-T34/P12-T13 admission contract batch`
reverted my `a05a272c` (READY) to
`**IN_PROGRESS** · codex-p12-pr-completion (reopened for exact-read capability
contract; PR #327)`. `P12-T13` was set to READY in the same commit. The owner's
live run and browser E2E for P8-T34 are still the only missing evidence, and
the exact-read contract is now carried by #327.

Severity: informational; the plan should treat P8-T34 as IN_PROGRESS until the
owner closes it.
