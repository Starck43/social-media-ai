# P12-T16 — Personal source ownership, auth preflight and actionable authorisation notices

Registry: [ROADMAP](../../ROADMAP.md); parent: [P12](../phases/p12-domain-workspace-expansion.md).
Priority `P0` · complexity `C4`. Owner: `opencode-p12-t16`.
Branch: `feat/p12-t16-personal-source-ownership`.
Owner dialogue: local chat, 2026-11-02.

## Owner request

1. A user who has not authorized a platform is collected with the deployment
   service credential (L1) only. The run must say so plainly per platform, so the
   person knows L1 was not enough and authorises personally when it matters.
2. That must arrive as a real notification with a working link, not merely a
   banner that only appears on the sources page.
3. A source collects under the individual user who added it. The workspace owner
   provides the tools; the credentials are the members' own. The current silent
   fallback to "the newest workspace owner" must go.

## Current behaviour (source snapshot `ffb8a91a`)

- `app/services/social/owner.py::resolve_source_owner` returns
  `Source.params["token_owner"]` when it names an active web member, and
  **otherwise the newest workspace owner**. Every source therefore collects with
  the owner's personal token by default — the exact inverse of the owner's rule.
- `app/services/social/connections.py::source_uses_personal_token` accepts
  `mode in ("pull", "user")` and omits `auto`, which is the stored default for
  imported lanes (`lane_import.LANE_PARAMS`). Sources created with `mode` absent
  also fall outside it, so the sources page reports no blocked platform for them.
- `app/jobs/handlers.py` records `outcome: "auth_required"` per source and the job
  notification is a generic `API_ERROR` ("завершена с ошибками"). Nothing names
  the platform, the missing authorisation or a way to fix it.
- `notify.create(recipient_user_ids=[...])` already publishes per-user inbox rows
  (`notification_receipts`), so a personal, linkable notice needs no new delivery
  machinery.

## Scope

### 1. Personal source ownership

- Add `sources.owner_user_id` (FK `users.id`, `ON DELETE SET NULL`, indexed) with
  an Alembic migration following `0122`; the head is discovered at implementation
  time, not reserved here.
- `owner_user_id` is assigned from the authenticated actor on every creation path
  (web `/app/sources`, API, lane import/migration). It is not client-supplied.
- `Source.params["token_owner"]` remains honoured as the explicit override and is
  still validated against active web membership; the column is the durable,
  queryable record, the param is the operator's pin.
- `resolve_source_owner` no longer substitutes the workspace owner. With no
  explicit owner the source has no personal credential and collects through L1.
- An owner who is removed from the workspace (or whose membership is deactivated)
  leaves the source without L2 rather than silently borrowing someone else's token.
- Existing rows keep `owner_user_id = NULL` (no backfill: guessing an author from
  history would repeat the defect). They continue to use an explicit
  `token_owner` if set, and otherwise L1 only. The sources page must show that
  state, and the owner can assign an owner per source.
- The owner still seeds sources for a workspace by creating them as themselves
  and handing the workspace over; ownership is a property of the creating actor,
  never of the role.

### 2. Honest "L1 only" reporting

- `source_uses_personal_token` recognises every mode that can consult L2 —
  including `auto`, an absent mode and `pull` — while `push` stays exempt. Today
  those sources are invisible to both the banner and the preflight.
- A source whose owner has no usable personal credential is reported as
  *service-only*: collection is not blocked, but the result must state that the
  L1 view may be narrower (closed communities, personal search, hidden walls).
- The distinction between `missing`/`reauth` (blocking) and `renewable`
  (self-healing) is preserved: an expiring token must never be presented as a
  problem the user has to fix.

### 3. Preflight before a manual run

- Before a manually started collect/analyze run, resolve the blocking set: sources
  whose owner credential is `missing` or `reauth`. Returns a per-platform
  summary with counts and the one-click authorisation target.
- The run is not blocked by `renewable`, by L1-only sources, or by sources that
  need no personal credential (`push`).
- The confirmation names the platform and how many sources will fall back to
  the service credential, so the person can authorise first and get the wider view.

### 4. Actionable authorisation notice

- New `NotificationType.SOURCE_AUTH_REQUIRED`. `notification_type` is a native
  PostgreSQL enum stored as member names, and Alembic does **not** autogenerate
  new members, so the migration must issue an explicit
  `ALTER TYPE ... ADD VALUE 'SOURCE_AUTH_REQUIRED'` (PostgreSQL 12+ permits this in
  a transaction; the implementation verifies it on the disposable test schema).
- After a run that produced `auth_required` sources, publish one notification per
  affected personal owner, naming the platform, the source count and the action:
  `ВКонтакте: 3 источникам нужен ваш личный доступ` with a destination to
  `/app/connections/vk/authorize?next=/app/sources`.
- `dedup_key` is scoped to workspace, platform and owner so a repeated run does not
  multiply rows; a successful authorisation clears the condition on the next run.
- The notice is per user, never broadcast to the workspace, and carries no token,
  no provider response and no owner identity of another person.
- An unauthorised source still **collects**, narrowly, rather than failing: when
  `mode=auto` finds L1 unusable *and* no usable L2, `VKClient` returns an empty
  list with `narrowed_by` set (`NarrowedAccess`: platform, person-facing hint,
  bounded reason). The collector carries it as `narrowed_access`, the handler
  stores it on the per-source row, and `_job_summary` groups those rows into
  `narrowed_platforms`. The run modal renders one amber block per platform —
  «Собрано узко · N источник(ов)» plus the hint — with the authorisation link
  rendered inline, so fixing it never leaves the modal. Counts stay real; the
  modal does not claim a failure it did not have.

### 5. Surfaces agree

- The sources page banner, the task source row, the job result message and the
  inbox notification must derive from the same resolver and say the same thing.
  A source that is service-only is labelled as such, not silently green.
- The history slice (`app/jobs/handlers.py:1583`) labels a service-only source in
  the same row so the run reads without needing the source to be listed.

## Non-goals

- No change to how L1 (`VK_SERVICE_KEY`) itself is configured or granted.
- No re-authorisation, revocation or migration of any stored credential value;
  refresh-token storage is [P12-T14](p12-t14.md).
- No automatic creation of `oauth_pending` rows or token refresh beyond the
  existing `renew_if_expiring` path.
- No change to Telegram push sources, bot delivery or digest recipients.

## Acceptance

1. Migration adds `sources.owner_user_id` with FK and index; upgrade, downgrade and
   re-upgrade verified on the disposable test schema; `public` untouched and
   requiring separate owner authorisation plus a backup.
2. A source created by a member collects under that member; a source with no
   owner and no `token_owner` never uses an unrelated person's token. Tests cover
   the removed owner, a deactivated membership, a forged `token_owner` and an
   owner who is also the workspace owner.
3. Focused tests prove `auto`, absent mode and `pull` are recognised as
   L2-capable, and that `push` stays exempt.
4. Preflight returns blocking platforms only for `missing`/`reauth`, ignores
   `renewable`, and the confirmation text is covered by a route test.
5. `auth_required` runs publish one personal notification per platform and owner
   with a resolvable destination, deduplicated across attempts, and none when
   authorisation was already valid. The new enum member exists after migration.
6. The sources page, task row and notification agree on label and destination for
   the same source; UI claims are proven by route/DOM tests, not unit tests alone.
7. A source with no usable personal credential collects narrowly instead of
   failing, and the run modal names the platform, the reason and an in-place
   authorisation link.
