# P8-T36 — VK connection capabilities and access selection

Registry: [ROADMAP](../../ROADMAP.md#p8); current status/owner/dialogue live there.
Parent: [P8](../phases/p8-first-value-ui.md).
Related: [P8-T29](p8-t29.md), [Q-5](q-5.md), [P8-T37](p8-t37.md).

## Scope and acceptance

Make VK authorization a visible, selectable and revocable connection that tasks
can use under explicit method capabilities. Reuse existing credential and OAuth
routes/settings where possible. Keep the entity boundaries clear: platform is
the provider type; connection is an authorized account/profile plus scopes and
health; source is a content target; people/apps/market search results are typed
results and do not become Sources automatically.

Define and implement the supported VK L1 service-token and L2 user-OAuth access
capabilities using the existing credential paths. Show the selected mode, account/profile,
granted scopes, health/expiry and reauthorization state. Task preview and all
execution surfaces must resolve the selected mode deterministically, fail
closed when a required capability is missing, and never silently fall back
between user and service credentials for a selected task operation. Preserve
the existing source collector's documented `auto` behavior for its limited
L1-to-L2 fallback cases; do not extend that fallback to global-search profile
or method errors such as historical 1051. Refresh, revoke and error handling
must not leak tokens. Keep task authorization separate from VK API permissions.

Accept when a method/profile/credential capability matrix is visible and used
consistently by web, API, CLI, admin and agent tools; selection, missing-scope,
expired/revoked and cross-workspace cases are covered with mocked credentials;
permission changes are rechecked at execution; no secret appears in logs or
results. Q-5 owns bounded live evidence for the base global-search methods; this
card may build mocked capability handling before Q-5 resolves, but makes no live
availability claim until then.
