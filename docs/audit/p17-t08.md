## Scope

`OneCMetadataCache` in `app/services/onec/query.py` serves a parsed `$metadata` catalog from a bounded (32 entries), TTL-bounded (60 s) store keyed by tenant, connection and the `metadata_sha256` pin, so a question costs one provider request instead of two. `app/models/onec/query_history.py` narrows the status check to `('executed','exported')` and drops the `planned` column default; `migrations/versions/p17t08_onec_history_status.py` replaces the constraint, **refusing** while rows still carry a removed status. `tests/integrations/test_p17_t02_service.py` was adapted so the provider-error paths run against a cold cache and the warm-cache path is asserted as well.

## Database evidence (isolated schema, run by the auditor)

- Migration cycle `upgrade p17t03_onec_history` → `head` → `downgrade -1` → `upgrade head`: one head `p17t08_onec_history_status`; the constraint goes `4 statuses + default 'planned'` → `2 statuses, no default` → back → narrowed again.
- **Guard proven fail-closed:** with a synthetic `planned` row present the upgrade raised `RuntimeError: Upgrade refused…` and left both `alembic_version = p17t03_onec_history` and the old constraint untouched. After deleting the row the upgrade applied, and the new constraint rejected a `planned` insert.

- Both isolated schemas dropped; no synthetic rows left anywhere.

## Security and correctness review

- **Authorization precedes the cache**: `fetch_metadata_catalog` calls `_load_authorized_connection` (RBAC `require_source_view`, active/verified state, approved host, credentials) before any lookup, so a revoked or unauthorized caller never reads a cached catalog.
- **Tenant isolation** is structural: `tenant_id` is part of the key, and a cached catalog is accepted only when its `metadata_sha256` matches the connection's current pin (checked twice — in the key and on the returned object).
- **What is cached** is the parsed 1C schema (entity sets and fields) — no tenant rows, credentials or query results — and only after the same authorization that would have allowed fetching it.
- **The migration is data-safe**: no row is rewritten or deleted, the narrowing is guarded, and the offline mode is refused explicitly.
- **No assertion was weakened** in the adapted T02 test: the provider-error assertions are unchanged and only a cache reset plus a warm-cache assertion were added.

## Findings (non-blocking)

All three findings below are tracked as [P17-T09](../tasks/p17-t09.md).

**N1 (low) — `invalidate_connection` has no production caller.** It exists and is tested, but a connection whose endpoint or login is edited keeps a warm catalog for at most the 60 s TTL (the pin protects pinned connections). Recommend calling it from the connection update/re-verify path.

**N2 (low) — eviction is insertion-ordered, not LRU.** With 32 bounded entries this is adequate; noted so a future cache does not inherit the assumption.

**N3 (carried) — N1 of the [P17-T06 audit](p17-t06.md) is still open.** `answer()` fetches the catalog before loading the stored plan, so a continuation with a foreign `history_id` still spends one budget token before being refused. The cache makes this cheap but does not reorder it; `app/services/onec/nl_query.py` was owned by P17-T07 during this task.
