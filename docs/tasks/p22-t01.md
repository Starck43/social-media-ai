# P22-T01 — Task identity, ownership and human work

[Phase P22](../phases/p22-universal-tasks.md) · [Design](../product/UNIVERSAL_TASKS.md) · [Queue](../../ROADMAP.md#p22)

**Dependencies.** Can be claimed immediately.

**Implementation ownership.** app/models/planner/, app/services/planner/, canonical task models and application service; additive Alembic revision.

## Deliverable

Start with the local title-only task. Implement canonical IDs, tenant-qualified references, encrypted content, work status, optimistic concurrency, visibility, assignment and participant roles. Reuse planner occurrence, reminder and calendar behavior through the aggregate. Keep parent hierarchy cycle-safe. Preserve private and workspace-managed work distinctly.

## Implementation sequence and handoff

1. Start at app/services/planner/tasks.py and trace create, list and recurring completion. Write the access matrix for owner, assignee, collaborator, watcher and manager against the existing tenant rules.
2. Introduce the canonical service behind an additive schema. Route a new local note through create → assign → complete while the legacy planner continues serving existing callers.
3. Give T03 and T06 a callable task lookup and versioned mutation contract, plus examples of a private task and a manager-visible legacy occurrence.

## Acceptance

A note can be created, dated, assigned, shared, completed or cancelled with no execution profile. A recurring completion creates at most one successor. A watcher cannot acquire private visibility by subscribing. Team filters, counts and pagination never reveal an inaccessible item. Two writers using one revision cannot silently overwrite each other.

## Verification at implementation

Compare owner, assignee, manager and unrelated member on personal and team tasks, including date-only and timezone-sensitive recurrence. Additive schema can be left unused with legacy entry points active.
