## Goal

Request and record approval of an exact document revision.

## Baseline

- Edits invalidate approval (P12-T03); case approvals bind document hash (P12-T05).

## Plan

1. Model `document_approvals` (tenant, document, revision, requester, approver, status `pending|approved|rejected|revision_requested|expired`, comments, requested/responded/expires at).
2. Approval binds the revision content hash; any new revision makes pending/approved approvals invalid for the new content (TZ: immutable hash).
3. Notifications to the approver via TG/MAX/email/web; expiry job.
4. API `POST /api/v1/documents/{id}/request-approval`, `GET …/approvals/pending`, `POST …/approvals/{id}/approve|reject`.
5. UI copy states that approval is not an electronic signature (R-19).

- Columns: `id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`; `tenant_id INTEGER NOT NULL`; `document_id INTEGER NOT NULL`; `revision_id INTEGER NOT NULL`; `revision_hash VARCHAR(71) NOT NULL`; `requester_user_id INTEGER NULL`; `approver_user_id INTEGER NULL`; `status VARCHAR(24) NOT NULL`; `comment_encrypted TEXT NULL`; `request_idempotency_key VARCHAR(128) NOT NULL`; `request_hash VARCHAR(71) NOT NULL`; `decision_hash VARCHAR(71) NULL`; `requested_at TIMESTAMPTZ NOT NULL`; `responded_at TIMESTAMPTZ NULL`; `expires_at TIMESTAMPTZ NOT NULL`; `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`; `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`; `pii_updated_at BIGINT NOT NULL DEFAULT 1`.
- FKs: `tenant_id -> S.tenants(id) ON DELETE CASCADE`; `(tenant_id,document_id) -> S.knowledge_documents(tenant_id,id) ON DELETE CASCADE`; `(tenant_id,document_id,revision_id) -> S.document_revisions(tenant_id,document_id,id) ON DELETE CASCADE`; requester and approver each reference `S.users(id) ON DELETE SET NULL`. A deleted/inactive approver cannot decide: the service must freshly check tenant membership and the dedicated permission, under locks.
- Constraints: `status IN ('pending','approved','rejected','revision_requested','expired')`; `revision_hash` and `request_hash` match `^sha256:[0-9a-f]{64}$`, and `decision_hash` is NULL or matches the same pattern; `expires_at > requested_at`; `((status IN ('approved','rejected','revision_requested') AND responded_at IS NOT NULL AND decision_hash IS NOT NULL) OR (status IN ('pending','expired') AND responded_at IS NULL AND decision_hash IS NULL))`; `UNIQUE (tenant_id, requester_user_id, request_idempotency_key)`.
- Indexes: unique partial index `(tenant_id,document_id) WHERE status = 'pending'` (one open request per document); index `(tenant_id,approver_user_id,status,expires_at,id)` for inbox and expiry. Existing `S.bump_contact_pii_marker()` via `contact_pii_marker` BEFORE INSERT OR UPDATE trigger, with comment encryption and CLI PII rotation registration; no new function.
- Coordination beyond DDL: add a separate approval resource/right in the access catalog and its model type, permissions and workspace presets; use existing notification/receipt/delivery mechanisms, not a second notification queue. Proposed decision idempotency compares the stored exact decision hash under row/document locks; same actor/payload replay returns the same decision, different payload fails closed. Current revision identity and hash are rechecked; a metadata-only new revision invalidates old approval too. New requests expire any superseded pending row while holding the document lock. No claim that these behaviours exist yet.

Confirm the role presets/explicit grants before implementation. This is a proposed dedicated right, not an owner-only shortcut.
