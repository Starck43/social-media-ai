# P11-T24 — Reproduce schema guard objects in the metadata-built test schema

Registry: [ROADMAP](../../ROADMAP.md#p11). Parent: [P11](../phases/p11-structure.md) (navigation only).

## Scope, evidence and acceptance

**Evidence:** `scripts/setup_test_db.py` creates the test schema with
`Base.metadata.create_all`, then stamps the Alembic head. `create_all` produces
tables, columns and constraints only: immutable-receipt triggers, personal
billing guards and task-binding guards exist solely in the migration history
(`0093`, `0094`, `0095`, `0099`, `0100`+), so they never reach the test schema.
On 2026-10-27 `test_schema` had 0 triggers against 42 in `public`, and the
personal billing acceptance suite failed seven guard cases with
`Cutover requires configured account and active platform reviewer`. The gap was
repaired directly in the live database, so it recurs on every metadata rebuild.
**Change:** make the guard objects part of the metadata build path. Keep one
reviewed source of the guard DDL, apply it idempotently after `create_all` for the
resolved test schema, and bind every trigger to a function in that same schema
(the migration copies are schema-qualified through `settings.DB_SCHEMA`, so a
naive copy silently keeps pointing at `public`).
**Acceptance:** a schema rebuilt from metadata carries the same guard objects as
`public`; each trigger executes a function defined in its own schema; the personal
billing acceptance suite passes with no exclusions on the rebuilt schema; applying
the step twice is a no-op; the build path fails closed instead of silently
skipping guards.
**Dependency/risk:** P8-T15/T17/T18/T20 acceptance evidence depends on those
guards. Migrations are history and must not be rewritten. Public schema and
production data are out of scope; only the test-schema build path changes.
