## Blocking findings

### B-1 — A trusted host bypasses the static policy in the OAuth guard

`app/core/outbound.py`, `acquire_outbound_target`:

```python
if entry is None and not policy.matches(normalized):
    raise OutboundRefusal(HOST_NOT_TRUSTED, normalized)
```

A registry entry short-circuits `policy.matches`. Every generic OAuth provider passes
its own static allowlist (`method.allowed_hosts`): Mail.ru, Yandex, VK, Telegram,
Yandex Disk, the 1C OAuth method. One trusted entry therefore makes
`https://<that host>/…` acceptable as an authorization endpoint for any of them, and
the client credentials of that provider — which the installation holds — are then
sent there by `start_authorization`.

This contradicts the card: "the static provider allowlist (cloud suffixes and known
endpoints stay code-owned)". It is the same class of finding as the Bitrix
`allowed_onprem_domains` path that this task exists to make reachable under control,
reintroduced one layer above it.

Required: a trusted entry may **add** destinations, never **widen** an existing
static policy. A call that passes a non-empty allowlist keeps allowlist-only
semantics; installation-level hosts are reachable only from a call whose policy is
open by design (Bitrix on-premise form, a self-hosted 1C/IMAP endpoint). Bind a
regression test: with `allowed_hosts=("*.yandex.ru",)` and a trusted entry for an
unrelated host, that host's authorize URL stays `untrusted_oauth_host`.

### B-2 — An installation-level registry is audited into a tenant ledger

`action_audit_events.tenant_id` is `NOT NULL` with `ON DELETE RESTRICT`, so the
manager writes each add/remove into **whichever workspace the administrator has open**,
and `0138`'s downgrade itself refuses to proceed while those rows exist. Consequences:

- deleting the workspace deletes the record of who trusted a client's internal host;
- the same audit trail is read by that workspace's members, who have no business with
  installation egress;
- there is no way to answer "what is trusted right now, and by whom" for the
  installation as a whole.

This is the same shape as the earlier lessons about platform-wide rows: a
platform-wide fact needs a platform-wide home. Required: a platform audit location
for `admin.trusted_host_*`, either the existing platform tenant concept or a small
installation-level evidence table, with a migration; and the downgrade guard reading
that location. If the platform home is a new decision rather than a bug fix, say so
and record the rollback in the card — but "open a workspace to change the
installation" cannot ship.

### B-3 — For a non-administrative platform operator the admin route silently does nothing

`add_host` / `remove_host` raise `TrustedHostError("admin_required")` when there is no
active workspace context. The web route opens `tenant_scope(tenant_id)` and sees the
error; the immediate manager call does not (reproduced: `add_host` with a valid
non-admin actor created row id 3 and an audit row with no active workspace). The
route that returns `admin_required` reads as a successful write, so someone will
eventually copy this sequence into a background job where nothing refuses.

Required: either deny an installation-level write that has no platform audit context
outright, or make the missing tenant an explicit, separately named error. Silent
success on a security control is not acceptable.

## Non-blocking findings

- **N-1 (second consumer is weaker than claimed).** `mail_check.py` now goes through
  the seam, but `_PinnedIMAP._create_socket` still calls `socket.create_connection`,
  which resolves the name again instead of connecting to the validated address. The
  comment reads "connect to the validated IP", the code does not. The `is_global`
  classification was removed, so nothing is lost, but the DNS-pinning guarantee the
  card asks for is not there yet.
- **N-2 (a dormant second resolver).** `app/integrations/file_workspace/yandex_network.py`
  resolves DNS and classifies `is_global` on its own and is not in the "no connector has
  its own resolution path" list. The module is dormant (documented as a future
  transport), which is exactly when it will be wired in without noticing.
- **N-3 (Bitrix refusal cap).** In `oauth/network.py` the seam's `address_not_authorized`
  is wrapped by `Bitrix24Error` with `status_code=502`, whereas the card asks for a
  422 naming the host and the installation administrator. Native platforms need a
  422, self-hosted platforms need a 422, but a 502 says "the server failed" to the user.
- **N-4 (health check is symbolic).** `/app/admin/trusted-hosts` resolves `host:443`
  for every entry; an IMAP host authorized for 993 is irrelevant, so "current
  addresses" means "what 443 would be". Document the port or check the actual ports.
- **N-5 (entry limit, unstated).** Unreadable registry → cloud-only, and the reader is
  limited to `MAX_HOSTS = 200` with no error above it. The behaviour is safe but
  undocumented.
- **N-6 (downgrade guard is severe by design).** `0138` refuses to downgrade while a
  single audit row of the new codes exists, and evidence cannot be deleted except by a
  retention flow, so `0138` is effectively forward-only. Acceptable for this task, but
  the card said "the table drops in the downgrade" — correct it.
- **N-7 (`test_access_policy.py` red).** `test_migration_catalog_and_presets_match_runtime_without_database`
  fails on base `ee70ffa8` as well; I did not verify independently whether it is
  pre-existing or catalog drift from a recent task. Not a reason to hold this PR, but
  it must be named in the landing notes.

## Landed as-is and correct

Seam purity over injected boundaries; per-operation registry scope (nested calls
share the snapshot, a forgotten scope stays cloud-only instead of failing open);
typed, value-safe refusals naming the installation administrator; `private` entries
refusing loopback, link-local, multicast and this server's own addresses; the
installation-level row with the 2026-11-04 citation in the docstring; audit codes
frozen into the migration and kept in sync by a test; removal requiring the exact
host typed; cloud-only behaviour with an empty registry.
