## Goal

Persist drafts and scheduled messages with exact approval binding and per-target outcomes.

## Baseline

- P12-T04 outbox state machine and approval binding as pure functions over dicts; follow-up quiet hours.

## Plan

1. Models `outbox_messages` (tenant, author, contact, content encrypted, content hash, state, scheduled at, command ref) and `outbox_targets` (channel, connection, recipient identity, idempotency key, state, attempts, provider message ID, error code).
2. Port P12-T04 transitions to the persistent model; keep the pure functions as the single transition table.
3. Runtime job `comms.outbox.dispatch`: claims due approved targets with `FOR UPDATE SKIP LOCKED`, rechecks approval/consent/connection, calls the channel sender ([P15-T06](../audit/p15-t06.md)), records outcome; quiet hours defer.
4. Multi-channel: one message → several targets, each independently tracked; cancel before claim.
5. API `POST /api/v1/communication/outbox/draft|schedule`, `GET …/outbox/scheduled`, `DELETE …/outbox/scheduled/{id}`.

**Implemented:** encrypted message/recipient snapshots; empty subject stored as
NULL and projected as `""`; immutable exact JSON intent hash (in addition to the
legacy pure target hash); actor/TTL/credential binding; independent target
commands in the central ledger (hashes only, no plaintext); explicit CONFIGURE
on scheduling in API and fresh database authority; UPDATE on draft/cancel; bounded
scheduled list and GET-by-ID outcomes; timezone-aware quiet-hour deferral;
`comms.outbox.dispatch` handler and per-workspace one-minute default task.

**Atomicity actually provided:** parent row locks serialize schedule/cancel/claim;
due selection uses `FOR UPDATE OF outbox_messages SKIP LOCKED`; database unique
keys fence duplicate drafts/targets. A claim is committed before I/O. A second,
one-time durable `delivery_started_at` fence consumes its ticket before provider
I/O. Outcome write failure, cancellation or a lost worker never authorizes a
second provider invocation through the dispatcher, even with the original ticket.
Abandoned claims become `uncertain_delivery` after five minutes; active I/O holds
the parent/revocation locks and is skipped by recovery. This is conservative
at-most-once admission, NOT exactly-once delivery: a crash before the provider
call can leave an unsent target uncertain. There is no automatic retry or resend
endpoint; confirmed/uncertain/failed targets are never eligible again. New
content/route/credential requires a new draft and explicit review.

**Migration:** only `0141_outbox.py`, literal parent `0140`, both owned tables,
indexes, per-table PII marker triggers, and the single idempotent `comms.outbox`
registry entry with VIEW/UPDATE/CONFIGURE permissions and the approved workspace
presets. The generic post-migration scanner is skipped for 0141, so no second
`outbox_messages` model type is created. No ALTER to existing tables and no edit
to 0139/0140. Downgrade removes registry links/permissions before dropping children;
tables own their constraints/indexes/triggers/sequences. No planner FK is needed.
Deploy migration before starting the new default task; stop runtime before downgrade.

**Activation:** SMTP still defaults off. The new central capability uses the
existing P15 transport enable/kill controls; sender additionally requires the
exact released workspace/connection pair and connection `send_enabled is True`.
Connection/identity/consent/actor are freshly re-read; revocation locks span I/O.
