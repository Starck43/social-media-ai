# P8-T52 — VK wall collection loses photo media URLs and legacy permalinks

Registry: [ROADMAP](../../ROADMAP.md); parent: [P8](../phases/p8-first-value-ui.md).
Registered while answering [Q-2](../audit/q/q-2.md), whose live check proved
the provider returns what we fail to store.

## Problem

For VK source 2939 (`annastrizhovadesign`, tenant 1) the stored rows carry
`attachments: [{"type": "image", "url": null}, …]` and, on older rows, no
permalink, while the same posts at the provider carry `photo.sizes[]` for every
photo. Measured 2026-11-18:

- 1 087 attachment snapshots for the source, only 5 with a URL (all 2019 data);
  860 `image` and 182 `video` placeholders.
- Live `wall.get` over the audited window: 61/61 photos had `sizes[]`,
  0 reposts, 33 video attachments — the same 33 video placeholders we store.
- A local reproduction of `VKClient._normalize_response` with a synthetic
  `wall.get` item does emit the largest photo URL, so the loss happens on the
  collection path that produced these rows (older normalizer or a path that
  never passes the provider attachment bodies), not in the staging validator.

Video previews are placeholdered **by design** and are not part of this defect.

## Scope and acceptance

- Identify which collection path stages VK wall rows without photo URLs (source
  collection for `USER`/group walls; include the search adapter and the chat task
  foundation), and make that path persist the largest `photo.sizes[]` URL and the
  `https://vk.com/wall{owner}_{post_id}` permalink for new rows.
- Keep the existing staging guarantees: no downloads, provider bodies or
  credentials stored; `{"type": "video", "url": null}` stays as designed;
  `normalize_attachments` remains the only writer of the snapshot shape.
- Acceptance needs one bounded live read-only check on the owner's own source
  (same credential route as Q-2), proving a freshly collected post stores a
  non-null photo URL and its permalink, plus mocked tests for the mapping.
  No backfill of historical rows unless the owner asks for it separately.
- Do not change retention, category status or provider permissions here.

## Boundaries

Collection/staging code and its tests only. No migration unless a stored field
must change (none is planned), no live provider writes, no public-schema mutation
beyond synthetic test-schema records, no secret value in code, card or commit.

## Rollback

Revert the mapping change; rows collected afterwards return to URL-less
placeholders, and the previous staging behaviour is restored without data loss.

## Root cause (2026-11-18, executor investigation)

The loss is in the shared staging guard, not in the VK client mapping:

- `app/services/social/vk_client.py::_normalize_direct_attachments` already picks
  the largest photo size and validates each candidate through
  `normalize_attachments`; the surviving URL is whatever that guard returns.
- `app/utils/content_attachments.py::_staged_media_url` **rejects every URL that
  carries a query string** (`parsed.query` must be empty), together with fragment
  and userinfo, precisely so that signed or tokenised links, which it calls
  `?access_token=PRIVATE`/`?sig=PRIVATE` in its tests, never reach storage.
- Modern VK photo CDN links always carry a query (`?quality=…&as=…&cs=…&u=<opaque
  access key>`). The only five VK photo URLs this database ever stored are the
  pre-2020 query-less form (`sun9-39.userapi.com/...jpg`, 2011–2019); every later
  wall photo was nulled by the guard while `photo.sizes[]` was present at the
  provider (61/61 in the Q-2 live check).
- `ContentClassifier.classify_content` treats a URL-less attachment as not-media
  and `analyzer.py` passes surviving URLs to the vision provider as `media_urls`,
  so a stored URL is something the provider is expected to *fetch*. A
  `https://vk.com/photo…` page link would therefore be wrong there.

This makes the fix a policy choice rather than a mapping bug: the current guard is
an accepted contract (`tests/collection/test_vk_direct_photo_snapshots.py` asserts
that `…jpg?access_token=PRIVATE` and `…jpg?sig=PRIVATE` stay URL-less), and any
VK photo URL that the provider can actually fetch violates it.

## Owner decision required

| Option | Change | Effect | Cost / risk | Rollback |
| --- | --- | --- | --- | --- |
| A — descope | none | VK wall photos stay placeholders; posts analyze as text (today's behavior); document the policy | no media analysis for VK; the Q-2 finding becomes "by policy" | n/a |
| B — allow provider queries | relax `_staged_media_url` for allowlisted provider hosts (`*.userapi.com`, `vk.com`), keeping https, no fragment/userinfo, length bound | VK photos become fetchable → real image analysis; the guard's "no query" rule narrows to those hosts | signed CDN links (with their opaque access key) persist in `collected_items.attachments`; links expire on their own | revert the guard and the tests; stored links stay but go stale |
| C — separate reference field | snapshot gains a `ref` value (`https://vk.com/photo{owner}_{id}`) that analysis never fetches | UI can link media; analysis unchanged | snapshot-shape contract change (guard, classifier, docs, tests); no migration | revert the shape change |

Recommended: **B**, because it is the only option that restores the media analysis
the product already pays for, and the persisted value is a time-limited reference
to the owner's own source rather than a credential. B is nevertheless a
security-relevant change to an accepted staging contract, so it needs the owner's
choice before implementation; A and C are recorded here for comparison.

holds the invitation evidence only.
